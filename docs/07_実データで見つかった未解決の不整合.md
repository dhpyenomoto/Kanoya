# 実データで見つかった未解決の不整合

2026年2〜9月の実績（営業168日・実売237室夜）をエンジンに突き合わせた際に
見つかった不整合のうち、**サンプルが小さいため今回は修正しないもの**を記録する。

修正しない理由は共通している。5室規模では1室夜で稼働率が4ポイント動き、
月あたり数十室夜しか出ない。数十件の偏りを「構造」と読んで係数を動かすと、
翌年の実績で逆向きに動かし直すことになる。**1年分の実績が貯まってから
再評価する。**

再現手順:

```bash
cd engine
python3 scripts/validate_real_otb.py \
    --otb ../../kanoya-data/otb.csv \
    --reservations ../../kanoya-data/reservations.csv
```

数値はすべて「部屋代（1室2名1泊・税サ込）」基準。食事は差し引いてある。
営業日の判定は `calendar.json` の `closed_days`（例外営業8日を含む）に従う。

## 不整合1：季節係数と実勢が逆転している

`property.json` の `season_factor` は PEAK 1.38 > HIGH 1.18 だが、実勢の
室夜単価は逆になっている。

| シーズン | 実勢の室夜単価（中央値） | 室夜 | season_factor |
|---|---|---|---|
| PEAK | **47,001円** | 53 | 1.38 |
| HIGH | **51,685円** | 32 | 1.18 |
| SHOULDER | 41,800円 | 83 | 1.00 |
| LOW | 36,145円 | 62 | 0.86 |
| DEEP_LOW | 18,000円 | 1 | 0.76 |

PEAK のほうが HIGH より安く売れている。係数どおりなら PEAK は HIGH の
1.17倍で売れているはずで、実勢はその逆である。

### 満室日に値下げしている形跡がある

実売5室（満室）の日を並べると、繁忙日ほど高いという関係になっていない。

| 宿泊日 | 曜日 | シーズン | 平均室夜単価 |
|---|---|---|---|
| 2026-03-28 | SAT | PEAK | **37,995円** |
| 2026-03-29 | SUN | PEAK | 36,319円 |
| 2026-05-03 | SUN | PEAK | 51,281円 |
| 2026-05-04 | MON | PEAK | 62,759円 |
| 2026-08-10 | MON | HIGH | 63,643円 |
| 2026-08-13 | THU | HIGH | 70,460円 |
| 2026-08-22 | SAT | LOW | 34,921円 |

PEAK の土曜に満室を作りながら 37,995円で売っている。同じ PEAK でも
GW（5/3・5/4）は5万〜6万円台であり、シーズン区分の中でばらつきが大きい。
**繁忙日に埋めるため値下げしていた可能性がある。**

### 修正しない理由

- HIGH は32室夜しかない。8月の数日の偏りで中央値が動く
- 春（3月下旬の桜）と夏（お盆）を同じ PEAK に入れている区分自体が
  正しいかどうか、この母数では判定できない
- 提示価格の記録が無いため、「安く売った」のか「安くしか売れなかった」のかを
  区別できない（提示価格の日次記録＝P17 が先に要る）

### 見直すときの手順

1. 提示価格の日次記録を貯める（P17）
2. 1年分の実績でシーズン区分そのものを引き直す
3. そのうえで season_factor を再算出する

係数だけを先に触らないこと。区分が間違っているなら、係数を直しても
別の日にずれが移るだけになる。

## 不整合2：2食付きの部屋代が素泊まりより安い

食事の売価を差し引いた部屋代を商品形態ごとに見ると、2食付きが最も安い。

| 商品形態 | 部屋代（中央値） | 室夜 |
|---|---|---|
| 素泊まり | 43,326円 | 126 |
| 朝食のみ | 47,001円 | 73 |
| 夕食のみ | 43,219円 | 4 |
| **2食付き** | **35,773円** | 28 |

同じ部屋を同じ日に売っているのだから、部屋代は形態によらず同じはずである。
実勢では2食付きが素泊まりより 17% 安い。

考えられる説明は2つある。

1. **パッケージで部屋を実質値引きしている。** 2食付きプランの総額を
   抑えるために、部屋代側を削っている
2. **食事単価での分解が実態と合っていない。** 実測の夕食16,500円・
   朝食5,500円（税込・1名）は明細の平均であり、プランによっては
   これと違う配分で計上されている

どちらであっても、エンジンの前提（部屋代は形態によらず同一、食事は固定加算）
とは食い違う。

### 影響

いまのエンジンは部屋代を1つ出し、4形態の販売価格を「部屋代＋食事加算」で
導く。実勢がこのとおりでないなら、2食付きの推奨価格は実勢より高く出る。

ただし2食付きは実売の12%（28/237室夜）であり、主力ではない。
主力の素泊まり（53%）と朝食のみ（31%）については、部屋代の差は
43,326円 vs 47,001円 と 8% に収まっており、前提は概ね成り立っている。

### 修正しない理由

- 28室夜しかない。プラン設計を変えるには母数が足りない
- 明細の内訳がどう作られているか（値引きをどの科目に寄せているか）が
  社内の運用に依存しており、データだけでは判別できない

### 見直すときの手順

1. 2食付きプランの値引きを、部屋代と食事のどちらに寄せているかを確認する
2. 寄せ方が決まっているなら、形態ごとの部屋代係数として明示する
3. 決まっていないなら、まず計上ルールを決める（データの問題であって、
   価格モデルの問題ではない）

## あわせて記録：内部需要シグナルの有効帯が狭い

不整合ではないが、実データで判明した設計上の制約として記録する。

最終稼働の見込みを実測へ下げた結果（`expected_final_occupancy`）、
期待室数が `min_expected_rooms`（1.0室）に届くリード帯が
**リード0〜2日まで縮んだ**。実データ・リード7日時点では
内部需要が有効なのは 19 / 160 日である。

つまり遠い日付については、自社の売れ行きを価格に反映していない。
価格は競合・イベント・曜日季節だけで決まっている。推奨出力に
「内部需要の有効日数」を毎回表示しているのはこのためで、
寄与0円が「想定どおりだった」のか「そもそも見ていない」のかを
区別できるようにしている。

`min_expected_rooms` を下げれば有効帯は広がるが、価格が動く変更になる。
5室規模で期待0.5室に対して実測が0室か1室しか取れない、という離散化の
問題は残るため、閾値を下げる前に「予約1件でどれだけ価格が跳ねるか」を
測ること。
