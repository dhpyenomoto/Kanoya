00要旨

エグゼクティブ・サマリー

本提案の結論は一点に尽きます。レベニューマネジャーという「人」を採用するのではなく、その人が行っている判断を分解し、機械が担う部分・ルールが担う部分・人が担う部分に再配置する。これを「レベニューOS」と呼びます。

優秀なレベニューマネジャーの市場価値は年収800万〜1,500万円。5室の施設が単独で抱えるのは経済合理性がありません。しかし単価が高いがゆえに、価格判断の巧拙が収益に与える影響は大規模ホテル以上に大きい。この構造的ジレンマを解くのが本構想です。

投資回収期間6〜12ヶ月ハイブリッド構成・初期¥2.5〜5.0M想定

本提案が置く5つの前提認識

  1. 最適化対象はRevPARではなくTRevPAR／GOPPAR。 オーベルジュの真のボトルネックは客室ではなく厨房とレストラン席数です。客室単価だけを最適化すると、原価率の高い日に安く売るという誤りを犯します。
  2. 5室では「統計的最適化」より「機会費用の管理」が効く。 大型ホテル向けRMSの連続需要曲線モデルは過剰です。必要なのはペース監視 × 決定表 × ガードレールという、検証可能で説明可能な構造。
  3. 価格は下方硬直・上方弾力に設計する。 ラグジュアリー小規模宿の最大リスクは、直前値下げによるブランド毀損と既存予約者への不公平です。需要が弱い日は値段を下げるのではなく、価値を足すルールに翻訳します。
  4. Googleマップは価格の情報源にはならない。 ご指摘のGoogleマップ活用は、需要・評判・混雑のシグナル源としては極めて有効ですが、競合の宿泊単価そのものの取得手段としては技術的にも規約的にも成立しません。詳細は第4章。価格は正規ライセンスで取得するのが唯一の持続可能解です。
  5. ノウハウは社内資産として保有する。 意思決定ロジックを外部SaaSに預けきると、2施設目の展開時に同じ費用を再度払うことになります。データ取得は買い、判断ロジックは持つ。
投資判断のコア

年間1,825室夜。ADRが1泊あたり4,000円（基準比5%）改善するだけで、稼働65%なら年間約475万円の増収です。この増分にはほぼ変動費が伴いません。つまりほぼ全額が営業利益。これが本投資の経済的な核心であり、システム構築費を1年以内に回収できる根拠です。

02問題定義

「属人化」の正体を分解する

属人性を排するには、まず何が属人的なのかを特定しなければなりません。レベニューマネジャーの業務は、次の4つの意思決定に分解できます。

意思決定内容属人度置換方法
D1 需要予測この日は何室売れるか、いつ埋まるか高機械に渡す。 ピックアップ曲線＋外部シグナルによる残需要予測モデル
D2 価格決定いくらで出すか中決定表に落とす。 5係数の乗算式＋ガードレール。完全に再現可能
D3 在庫・条件制御どのチャネルに、どの条件で、何室出すか中ルール化する。 レートフェンス設計＋配信ポリシー
D4 例外裁定団体、一棟貸し、直前キャンセル、特殊イベント高人が残す。 ただし権限マトリクスと理由コードで記録・監査可能に

ここで重要なのは、D4を無理に自動化しようとしないことです。属人性排除を「全自動化」と読み替えた瞬間、システムは現場に拒絶されます。目指すのは判断の外部化であって、判断の消滅ではありません。

組織設計としての結論

レベニューマネジャーの役割は消滅せず、「パラメータの管理者」と「例外の裁定者」へ再定義されます。求められるスキルは相場観からルールの検証能力へ移り、必要工数は週2〜3時間程度まで圧縮されます。支配人または運営責任者が兼務可能な水準です。これが「経験・力量に左右されない」の実質的な意味です。

Googleマップに関する重要な訂正

ご提案いただいた「Googleマップからの宿泊データ収集」については、正確に切り分ける必要があります。

取得できるもの（Places API・正規）：施設名・所在地・カテゴリ・星評価・レビュー件数・レビュー本文と投稿日・写真・混雑時間帯。これらは需要と評判のシグナルとして極めて有用で、実際に本システムの重要な入力です。

取得できないもの：宿泊単価。Googleマップに表示される宿泊料金は、OTAおよびホテルがGoogle Hotel Center／Travel Partner API経由で入稿した広告・予約リンク由来のデータであり、Places APIのレスポンスには含まれません。自社の料金は入稿できても、他社の料金を引き出すインターフェースは存在しません。

さらに、Google Maps Platformの利用規約はコンテンツのキャッシュ・再利用を原則制限しており（一部項目のみ30日以内の例外）、表示画面のスクレイピングは明確に禁止されています。したがってGoogleは「需要シグナル源」、価格は「レートショッパー」という役割分担が唯一の持続可能な設計です。

条件正規化 ── ここが最大の技術的キモ

鹿のやは2食付、競合の多くは素泊まりや朝食付を併売しています。この条件差を吸収しないまま価格を比較すると、システムは構造的に誤った値下げを推奨し続けます。 多くの安価なツールが実務で使い物にならない最大の理由がここです。

基準商品（Reference Product）の定義

-- すべての比較はこの1商品に射影する
REFERENCE_PRODUCT = {
  occupancy: 2 -- 2名1室
  meal_plan: 'DINNER_BREAKFAST' -- 夕朝食付
  cancel_policy: 'FLEXIBLE' -- 返金可
  lead_time: 30 -- T-30時点の観測
  price_basis: 'TAX_INCL_TOTAL' -- 税・サービス料込
}

競合が基準条件で販売していない場合は、補正ルールで射影します。補正には必ず信頼度スコアを付与し、低信頼な観測値は価格判断への寄与度を下げます。

奈良市場の構造的論点

奈良の宿泊需要における最大の競合は、実は奈良市内の施設ではなく京都です。「奈良を観光するが京都に泊まる」層が厚く、これが奈良の稼働率と単価の天井を押さえてきました。セカンダリに京都の同価格帯を入れる理由はここにあります。逆にいえば、「奈良公園内に泊まる」という代替不可能な体験こそが鹿のやの価格根拠であり、価格設定はこの非代替性を前提に強気に置くべきです。京都の価格に引きずられて下げる必要はありません。

競合価格指数（CRPI）の定義

CRPI(d) = P_own(d) / Σi [ wi × confi × P_norm(i,d) ] / Σi [ wi × confi ]

w = コンプセット重み（上記）
conf = 条件正規化の信頼度スコア
P_norm = 基準商品へ射影済みの競合価格

目標帯： CRPI_target = 1.05 〜 1.15 （市場中央値に対し5〜15%上位）

CRPIの目標値をどこに置くかが、経営としての価格ポジショニングの意思表示です。「奈良公園内・5室・2食付」という希少性に対して、市場中央値の5〜15%上を定位置とする。これを一度決めれば、日々の価格判断はこの目標への収束問題に還元されます。属人性が消える理由の半分はここにあります。

06算出ロジック

推奨ADRの算出アルゴリズム

推奨価格は、基準価格に5つの係数を乗じ、上下限で切り取る形で算出します。乗算構造を採る理由は、各係数の寄与を独立に検証・調整できるためです。加算式は解釈が難しく、機械学習の単一モデルは説明できません。

BAR(d, t) = clip(
    P_base(season(d), dow(d), room_type)
    × f_pace     -- 予約ペースの先行/遅行
    × f_comp     -- 競合価格との相対位置
    × f_scarcity -- 残室の希少性
    × f_lead     -- 残日数（非対称）
    × f_event    -- イベント需要
  , Floor(d), Ceiling(d) )

T-7 〜 T-01.00 – 1.10値下げ禁止価値付加（Value-add）に変換
本提案で最も主張したい設計思想

直前期に価格を下げてはいけません。 理由は3つあります。①既に定価で予約した客との不公平が、レビューと再訪率を毀損する。②「待てば安くなる宿」という学習をリピーターに与える。③6万円の宿が4万円になっても、需要は思うほど増えない（この価格帯の需要は価格弾力性が低く、意思決定は先行して行われる）。

代わりに、値下げ相当額を価値に変換します。上位客室へのアップグレード、駅送迎、ワインペアリング、レイトチェックアウト、館内クレジット。これらは原価が定価より小さく、ADRを毀損せず、体験価値とレビュー評価を上げる。システムは「−¥8,000」ではなく「アップグレード付与を推奨」と出力します。この変換ルールを持つことが、ラグジュアリー小規模宿のレベニューシステムの品格です。

Floor と Ceiling

Floor(d) = max(
  変動費(食材・アメニティ・清掃・OTA手数料) + 目標貢献利益,
  ブランドフロア -- 経営が決める「これ以下では売らない」線。絶対不可侵,
  前年同曜日ADR × 0.92
)

Ceiling(d) = min(
  過去実績最高ADR × 1.25,
  コンプセット最高値 × 1.40
)

安全装置（サーキットブレーカー）

  • 日次変動幅の制限：同一滞在日の価格変更は1日あたり±10%以内
  • 値下げ回数の上限：同一滞在日に対する値下げは通算2回まで
  • 異常値の自動停止：前回配信比±30%を超える推奨が出た場合、配信せずアラート
  • 完売時の自動処理：全室売止後はCeiling側へ自動移動、キャンセル発生時の再販価格を確保
  • 収集失敗時のフェイルセーフ：競合データが2日連続で欠損した場合、f_compを1.00に固定（前日価格を維持）

説明可能性 ── 理由コードの必須化

すべての推奨には理由コードと日本語1文を必ず添えます。これがない推奨は現場に採用されず、システムは3ヶ月で放置されます。

コールドスタート ── データが2年半しかない前提での設計

開業から日が浅く、機械学習に十分な周期数がありません。これを正直に扱うのが実務の分かれ目です。

期間予測手法f_compの重み自動化度
〜6ヶ月ルールベース（ペース＋競合追随）高（β=0.50）推奨のみ、全件人が承認
7〜12ヶ月ベイズ更新型ペースモデル中（β=0.40）±5%以内は自動承認

並行して、時間分割による価格弾力性テストを実施します。同曜日・同季節の枠を隔週で±8%振り、12週分の予約速度差から弾力性を推定。5室では同時A/Bテストが成立しないため、この設計が唯一の実務解です。

一棟貸し価格の算式化

5室の施設ではバイアウト需要（記念日、企業リトリート、インバウンドの家族・グループ）が高単価機会になります。ここは最も属人的な交渉領域ですが、算式化できます。

Buyout(d) = Σrooms BAR(d) × 1.15 -- 貸切プレミアム
    + 専用サービス原価 -- 貸切対応の追加人件費等
    − 機会損失調整 -- 当日の予測稼働が低い場合のみ減算

機会損失調整 = Σ BAR(d) × (1 − 予測稼働率(d)) × 0.5
→ 予測稼働40%の平日なら実質的に約17%の割引余地。
　 予測稼働90%の繁忙日なら割引ゼロ＝プレミアムのみ。

この式があれば、問い合わせを受けた担当者が誰であっても、同じ日付には同じ見積りが出ます。これが「力量に左右されない」ということの具体的な意味です。

10運用統制

ガバナンス ── 属人性排除の本丸

システムは半分にすぎません。残り半分は運用規程です。 ここを整備しない導入は、必ず「誰かが毎日全部上書きする」状態に退化します。

RMポリシー（意思決定の憲法）

条項内容
第1条 目的関数最大化対象はTRevPAR。同一の予測稼働なら、料飲売上を含む総客単価が高い商品を優先する
第2条 ブランドフロアいかなる状況でも下回らない価格を経営が年1回決定。システムはこれを構造的に破れない
第3条 直前値下げの禁止T-7以内の価格引き下げを禁止。需要不足には価値付加で対応する
第4条 パリティ全OTAで表示価格を同一に保つ。直販の優位は非価格特典で構成する
第5条 上書き推奨価格の上書きには理由コードの入力を必須とする。月次で上書き内容をレビューし、妥当なものはルールへ昇格させる
第6条 パラメータ変更係数・重み・目標CRPIの変更は月次レビューでのみ実施。日々の思いつきでの変更を禁止する

第5条が制度設計の要諦です。 上書きを禁止するのではなく、記録して学習源にする。現場が繰り返し同じ理由で上書きするなら、それはシステムが捉えていない現実があるということ。その上書きパターンをルール化すれば、システムは自動的に賢くなります。属人的な暗黙知を、組織の形式知へ吸い上げる回路がここです。

前提と出典について

本提案における鹿のやのADR・稼働率・収益構成は、公開情報および同カテゴリー施設の相場からの推計値であり、実データによる置換を前提としています（Phase 0で確定）。施設概要は公開検索結果および各OTA掲載情報に基づきます。競合各施設の価格帯は公開情報からの参考値です。

チャネル手数料率は業界の一般的レンジであり、実契約条件による確認が必要です。ベンダー費用（メトロエンジン等）は公表情報に基づく参考値で、2026年8月時点。奈良市の宿泊税は現時点で未導入・継続検討中です。楽天ウェブサービスの旧形式トラベルAPIは2026年2月に提供を終了しており、新API系列への移行が必要です。第78回正倉院展は2026年10月24日〜11月9日開催。

本書は議論の出発点となる企画提案であり、実装前に実データによる検証、契約条件の確認、および各サービス利用規約の法務レビューを行うことを推奨します。
