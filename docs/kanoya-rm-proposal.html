01

「属人性」の正体は、4つの別問題である

Problem Decomposition

「レベニューマネジャーの経験に左右される」という一言のなかには、性質のまったく違う 4つの問題が混ざっている。まとめて扱うから解けない。分解すれば、3つは機械で消える。

属人性の正体現場での症状解法
A 情報の属人性 競合価格を「見に行った人」しか知らない。見た日と見ない日がある L0 自動収集＋全履歴保存
B 判断基準の属人性 「この日は高くいけそう」の“そう”が言語化されていない L4 Pricing Policy Document
C 計算の属人性 残室数と残日数から機会費用を暗算している（人間には不可能） L3 Bid Price 動的計画法
D 検証の属人性 結果の良し悪しを誰も測らないので、経験が蓄積も否定もされない L6 学習ループ

重要なのは A・C・D はシステムで完全に消せるが、B は消せない という区別である。 B ── どういう宿でありたいか、いくら以下では売らないか、誰に売りたいか ── は経営判断であり、 機械に委譲してはならない。

したがって本提案における属人性排除とは、人を排除することではない。 B を「個人の勘」から「文書化され承認された経営方針」へ移し、人が担当する層を上に押し上げることである。

02

5室は制約ではなく、優位である

Structural Diagnosis

「小規模だからレベニューマネジメントは不要」は誤りである。むしろ逆で、 5室という条件はRMの理論的な旨味を最大化する。

200室のホテルのRMは「どう埋めるか」＝稼働の問題である。5室のRMは 「その日の1室を、誰に、いくらで売るか」＝機会費用の問題になる。 1件のキャンセルがOCCを20pt動かす環境では、判断1回あたりの重みが40倍になる。

不利：データのスパース性

5室×365日＝1,825室夜。「5月3日は満室だった」から「5月3日は強い」を学ぶのは n＝1 の推論であり、素朴な機械学習はほぼ確実に過学習する。

  • 階層ベイズ（partial pooling）で、奈良市場・高価格帯全体の需要曲線を親分布として借りる
  • データが薄い日付は自動的に市場平均へ引き寄せられ、厚い日付は自施設実績を信じる
  • 「データが足りないときどうするか」を人が悩まなくて済む

有利：厳密最適化が解ける

在庫制御の本質は「今の ¥45,000 を受けるか、将来の ¥80,000 を待つか」である。 状態空間は 残室 r∈{0..5} × 残日数 t∈{0..365}。

  • 状態数はわずか 2,196。365日分回してもノートPCで数秒
  • 大規模ホテルが EMSR 等の近似に頼る領域を、鹿のやは正解で解ける
  • 本提案 最大の技術的差別化点
オーベルジュ固有の論点

館内にレストランとバーを持つ以上、客室単体の RevPAR 最大化は誤った最適化である。 素泊まり ¥45,000（粗利 ¥40,000）と2食付 ¥62,000（食材原価 ¥9,000 → 粗利 ¥53,000）は、 OTA手数料率がプランで異なれば Net で逆転しうる。 ダッシュボードの主KPIは ADR ではなく Net TRevPAR（手数料・原価控除後の総売上／販売可能室数）に置く。

03

アーキテクチャ ── 6層のRM-OS

System Architecture

下から積む。ただし 投資の重心は L4 にある。 L0〜L3 は L4 を実行可能にするための装置であり、L6 は L4 を更新し続けるための装置である。

L6 検証・学習ループ 予測精度（MAPE）／Override 成績スコアボード／価格実験（Thompson Sampling）→ パラメータ更新 → 月次RM会議へ自動レポート
L5 配信 サイトコントローラーAPI 経由で一休・楽天・じゃらん・Booking.com・Expedia・Relux・直販へ反映。ドライラン → ガードレール再検証 → 配信 → read-after-write 検証 → 自動ロールバック
L4 ガバナンス 属人性排除の中核。 Pricing Policy Document をコード化したルールエンジン。フロア／シーリング、日次変動幅、ブランド保護、期限付き Override、全件監査ログ
L3 最適化エンジン Bid Price 動的計画法で受注可否の下限を厳密算出。期待収益最大化による提示価格探索。MinLOS／CTA／CTD による在庫・連泊制御
L2 需要予測エンジン 階層ベイズによる非定常ポアソン到着過程。出力は日別 λ(価格, 残日数)、予測OCC・ADR、そして信用区間（不確実な日は価格を動かさない）
L1 データ基盤 BigQuery ＋ dbt。中核は as_of_date × stay_date の二次元スナップショット設計
L0 データ取得 競合レート（商用取得API）／Google Places（評点・口コミ）／自社PMS・サイトコントローラー／イベント・天候・公的統計

UI は Streamlit のRMダッシュボードと、Slack／LINE への日次サマリ通知。 実行基盤は Cloud Run Jobs ＋ Cloud Scheduler による深夜バッチ。

Data Acquisition ／ 事実確認

ご指摘のとおり Google からの収集は成立する。ただし 取得物の種類を分けて理解する必要がある。 ここを曖昧にしたまま自前スクレイパーを組むと、利用規約・著作権・不正アクセス禁止法の三方向でリスクを負う。

法務ポジション

Google Hotels に公式の一般開発者向け価格APIは存在しない。 「Googleから価格を取る」とは、実務上は商用取得APIのライセンス購入を意味する。 著作権法第47条の5は情報解析目的の軽微利用に一定の余地を与えるが、 利用規約による契約上の制約は著作権法とは別軸で効力を持つ。 本提案はリスクを自社に取り込まず、商用API／SaaSのライセンス契約に外部化する方針を採る。 年間数十万円は、法務リスクと運用工数の保険料として妥当である。

設計上の最重要ポイント ── 二次元スナップショット

「今日の12月24日の価格」ではなく、 「11月1日時点で見た12月24日の価格」「11月2日時点で見た12月24日の価格」… をすべて保存する。

comp_rate_snapshot ( as_of_date, stay_date, property_id, channel, meal_plan, occupancy, los, price_per_room_night, is_sold_out, is_closed_out ) PARTITION BY stay_date CLUSTER BY property_id, as_of_date

これにより 競合がいつ値上げし、いつ売り切れたか ── すなわち競合の販売ペースが見える。 価格そのものより情報価値が高い。競合が90日前に満室になる日は、鹿のやが強気に出るべき日である。 単純な価格比較しかしないRMツールは、この情報を捨てている。

収集グリッドは Primary 6 ＋ Secondary 8 施設 × 宿泊日 +0〜+120日 × LOS 1・2泊 × 2名基準。 日次 3,400〜6,800クエリ、年間 124〜248万レコード。毎日、同じ方法で、撮り続けることが要件である。

予測と最適化 ── 暗算できない判断を機械に渡す

Forecast & Optimization

需要モデル

宿泊需要を非定常ポアソン到着過程として定義する。宿泊日 d、残日数 t、提示価格 p に対する予約到着率：

λ(d, t, p) = λ_base(d) × g(t) × ( p / p_ref(d) ) −ε λ_base(d) 宿泊日固有の需要水準 ── 曜日・季節・イベント・市場OCC・競合売切率を説明変数とする階層ベイズ g(t) ブッキングカーブ ── チャネル別に推定（一休・直販は短く、Booking.com・Agoda は長い） ε 価格弾力性 ── 事前分布 LogNormal(log 1.8, 0.4)（高価格帯宿の業界レンジ 1.2〜2.5）から出発 p_ref(d) 参照価格 ── Primary Comp Set の中央値。高い／安いは絶対額でなく市場相対で決まる

自社の5室だけでは需要は見えない。しかし Primary Comp Set 6施設・平均40室＝240室分の消化速度は見える。 60日前に競合3施設が売り切れている日は、統計的に強い需要日である。 自社の予約がまだ0件でも、機械はこの日を強気と判断できる。 人間のRMが「肌感」と呼んでいるものの正体は、多くの場合これである。

Bid Price ── すべての受注判断を1つの数値に還元する

V(0, r) = 0 宿泊日到来。残室の価値はゼロ V(t, r) = maxp { λ(d,t,p)·[ p + V(t−1, r−1) ] + (1 − λ(d,t,p))·V(t−1, r) } bid(t, r) = V(t, r) − V(t, r−1) ← 残り r 室・残り t 日で、1室を今売ることで失う将来価値

bid(t, r) を下回る価格の予約は、受けてはいけない。 団体照会、旅行会社のアロットメント、直前の値引き要請、連泊割引 ── すべてこの1つの数値で機械的に答えが出る。

現場でRMが最も間違えるのが、まさにこの判断である。 「30日前でまだ2室空いている。¥45,000 のリクエストが来た。受けるか？」に対し、 人間は不安だから受けるかもったいないから断るを気分で決めている。 DPは「bid(30, 2) = ¥52,300 なので断るべき。受ければ期待値ベースで ¥7,300 の損」と即答する。

連泊化 ── 奈良で最大のレバー

奈良は「1泊で通過される」土地である。連泊化は ADRを下げずにOCCを上げ、同時に清掃コストを下げる 唯一のレバーであり、その可否もまた bid の比較で決まる。

2泊受注の可否: 2泊の合計収益 ≥ bid(t, r) + bid(t′, r′) 制御手段: MinLOS 高需要日の前後で1泊予約をブロック（例：土曜が強く金曜が弱い → 土曜に MinLOS=2 を置き、金土の2泊を作りに行く） CTA その日の到着を締め、連泊の中日として使う ／ CTD 出発を締める

設計原則 ／ Decision Rights

誰かが価格を直接触りたくなったら、それは「ポリシーが現実を捉えていない」というシグナルである。 価格を直すのではなく、ポリシーを直す。この規律だけで属人性の8割は消える。

Pricing Policy Document ── 価格の憲法をコードにする

年1回、オーナーが承認する。承認された文書がそのままシステムの実行規則になる。

approved_by: "総支配人"

positioning:

  never_be_cheapest: true             # Primary の最安値を下回らない

  ceiling: 145000
  max_daily_change_pct: 12            # 1日の変動幅上限（信頼性の毀損防止）

  min_price_duration_hours: 24

  discount_must_be_fenced: true       # 値引きは必ず条件付き（連泊/平日/会員）

  direct_advantage: true              # 直販は常に最良条件
  channel_floor_net: { booking_com: 40000, expedia: 40000 }

  requires_reason_code: true
  max_duration_days: 14                # 無期限Overrideを禁止

禁止すると現場が壊れる。代わりに全件記録し、成績を毎月可視化する。

思想

優秀なRMの勘は、捨てるものではなく 回収して仕様書にするものである。 RM-OS は「人を置き換える装置」ではなく、「人の判断を資産化する装置」として設計する。

説明できない価格は、OTAに出さない

価格は必ず分解可能な乗算モデルで構成し、日次の決定に人間可読の説明を自動付与する。 経営会議で「なぜ4月18日が ¥78,000 なのか」に3秒で答えられることが、システムの受け入れ条件である。

最終価格 = BASE(室タイプ, 曜日, 季節) × f_demand × f_comp × f_pace × f_event → GUARDRAIL でクリップ（下限／上限／日次変動幅） → BID PRICE で下限を再確認（機会費用を下回る価格は出さない） → 予測の信用区間が広い日は前日価格とブレンド（不確実なときは動かさない） ────────────────────────────────────────────────────────────── 2026-11-03（火・文化の日） ¥98,000 (前日比 +8.0%) └ 正倉院展会期 × 紅葉ピーク（f_event 1.22） Comp Set 中央値 ¥86,000 に対し RGI 1.14（方針 1.15 に整合） 残2室・残21日 → Bid Price ¥91,400 を上回るため受注可 競合6施設中3施設が既に満室（market_pressure 高） ──────────────────────────────────────────────────────────────

OTA戦略 ── 「多く出す」ではなく「正しく選ぶ」

Channel Portfolio

5室に10チャネルを繋ぐと、在庫の奪い合いと運用負荷で Net 収益が落ちる。 チャネルは粗利率ではなく 増分貢献 で評価する。

チャネル役割想定手数料目標構成比
自社直販最重要。Net最大3–4%40%
一休.com国内高価格帯の主戦場8–10%20%
Booking.com / Agoda / Expediaインバウンド（奈良公園立地は必須）15–18%20%
楽天トラベル / じゃらん国内リーチ、ポイント需要8–12%10%

Booking.com の手数料15%は高いが、そのチャネルがなければ埋まらなかった室夜なら Net 貢献はプラスである。 逆に、直販で取れたはずの客がOTAに流れているならカニバリであり、手数料は純損失になる。 この論争を終わらせる唯一の方法は、低需要期に チャネル・ホールドアウト実験 （年1回、特定チャネルを一時停止してOCC変化を測る）を行うことである。

CRM／リピーター 宿泊後フォロー、記念日データ保持、非公開先行案内。5室規模なら個別対応が現実的で、大手より強い
5室の宿にとっての最終形

年1泊するリピーターが200人いれば、1,825室夜のうち11%が固定需要になる。 RM-OS の最終形は、CRMと統合された「顧客別・機会費用ベースの価格提示」である。 なお国内では公正取引委員会の調査を経て広域レートパリティ条項の是正が進んでおり、直販を優位に置く余地がある。 各OTA契約書のパリティ条項を棚卸しし、PPD に許容範囲を明記して、システムはその範囲内でのみ配信する。

08

KPI ── Override率が、成功指標そのものである

Measurement

事業KPIツリー

  • Net TRevPAR（最上位）── 手数料・原価控除後の総売上／販売可能室数
  • 客室 Net RevPAR ← ADR × OCC
  • RGI = ARI × MPI ── 市場に対する総合競争力
  • ブッキングペース（vs STLY, vs Forecast）、LOS Mix
  • F&B Capture Rate、Spend per Guest
  • 加重平均手数料率、直販比率

システム健全性KPI

  • 予測MAPE（30日前OCC予測誤差）── < 12%
  • Override率 ── < 15%
  • Override勝率（人 vs 機械）
  • データ収集成功率 ── > 98%
  • 配信成功率（read-after-write一致）── > 99.5%
  • 価格変更頻度が適正レンジ内（過剰変動はブランド毀損）

Override率が下がり続けるなら、暗黙知が順調にシステムへ移管されている。 下がらないなら、モデルかポリシーに欠落がある。 目指すのは「使わなくなった」ではなく「使う必要がなくなった」状態である。

月次RM会議もアジェンダを固定し、資料はシステムが自動生成する。 会議で決めるのは PPDパラメータの変更承認だけであり、 「今日いくらにする？」は会議の議題ではない。それはシステムの出力である。

09

Build vs Buy ── 買うものを買い、作るものに集中する

Make-or-Buy Decision

買う ── リスクと汎用性の高い部分

  • 競合レート収集（商用レートショッパー／Google Hotels 取得API）
  • サイトコントローラー（既存があれば継続）
  • クラウド基盤（BigQuery / Cloud Run）

レート収集は完全なコモディティであり、自作する意味がない上に法務リスクだけ増える。

作る ── 差別化と施設特性の部分

  • Bid Price DP による機会費用計算（既製品にない）
  • 階層ベイズ需要予測（5室のスパース性に対応）
  • TRevPAR最適化（オーベルジュ固有）
  • PPDのルールエンジン（属人性排除の本体）
  • 監査ログと Override スコアボード

既製RMSは「100室のビジネスホテルを埋める」ために設計されている。 5室・高単価・2食付・世界遺産立地という鹿のやの構造には最適化されていない。 ただし Phase 1 で既製RMSを導入して即座に効果を出しつつ、並行して自社エンジンを構築し、 Phase 3 で意思決定層を差し替えることで、「効果が出るまで1年待つ」を回避できる。

選択肢初期月額評価
A. Buy（既製RMS）低¥30k–100k即日開始できるが、5室オーベルジュ向けのチューニング不可。TRevPAR最適化・厳密機会費用計算なし
B. Build（フルスクラッチ）¥3.0M–6.0M¥50k–150k完全適合・多施設横展開の資産化。ただし立ち上げ期間と法務リスクを自社が負う
C. ハイブリッド（推奨）¥1.5M–3.5M¥80k–200k収集は買い、意思決定は自作。 統合の設計が必要だが、投資が差別化領域に集中する

投資対効果

Economics ／ すべて仮定値・要差替

前提: 5室 ／ 年間販売可能室数 1,825室夜 ／ 現状 ADR ¥55,000・OCC 70% → RevPAR ¥38,500 年間客室売上 ≈ ¥70,300,000 年間システムコスト ≈ ¥1,500,000 シナリオ RevPAR改善 年間増収 純増 ROI 保守（RevPAR +5%） +¥1,925 +¥3,510,000 +¥2.0M 2.3x 標準（RevPAR +10%） +¥3,850 +¥7,030,000 +¥5.5M 4.7x 目標（RevPAR +16.3%） +¥6,160 +¥11,240,000 +¥9.7M 7.5x さらに 直販比率 25% → 40% により、1,278室夜 × ¥60,500 × 手数料差 8pt ≈ +¥6,200,000 の Net 貢献（増収ではなくコスト削減）が上乗せされる 損益分岐は RevPAR +2.1%。 RM未整備の施設で初年度に +2% が出ないケースは実務上ほとんどない。

数値にならない価値

事業継続性

RM担当が退職しても運営品質が落ちない。5室の宿にとって、キーパーソン依存は経営リスクそのものである。

横展開資産

複数施設を運営するポートフォリオにおいて、2施設目以降の導入限界費用はほぼゼロ。1施設のROIが控えめでも、全体では極めて高い。

企業価値

レベニュー実績とデータ基盤が整った施設は、Cap Rate 評価で有利に働く。投資家から見た事業の再現性が異なる。

総括

Conclusion

鹿のやのレベニューマネジメントを担当者の力量から解放するために必要なのは、高度なAIではない。

必要なもの消える属人性
1毎日、同じ方法で、競合と市場を観測し続ける仕組み ／ L0–L1「見た人しか知らない」が消える
25室という制約を、機会費用の厳密計算という優位に転換する数理 ／ L2–L3「暗算できない判断」が機械に渡る
3経営方針を文書化し、システムがそれを強制執行する統治構造 ／ L4「勘」が「承認された方針」に昇格する
4人の介入を測り、当たった勘をルールへ回収し続けるループ ／ L6「経験」が「資産」に変わる

このうち 3 が本質であり、1・2・4 はその実装手段にすぎない。

システムを作る前に、「鹿のやは、どういう価格で、誰に、どう売る宿なのか」を1枚の文書に落とすこと。 そこから始めれば、レベニューマネジメントは属人技能ではなく、経営の再現可能な機能になる。
