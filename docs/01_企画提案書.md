## 0. エグゼクティブサマリー

### 0.1 問いの再定義

ご相談は「ADRを上げ、稼働を最大化する仕組みをどう作るか」ですが、**5室という規模**がこの問いの性質を根本的に変えます。

- 1室の販売可否が稼働率を **20ポイント** 動かす。連続的な需要曲線ではなく**離散最適化**の問題。
- 年間販売可能室数は **1,825室**。100室ホテルの **約29日分**。統計的学習に使えるサンプルが決定的に少ない。
- オーベルジュ（1泊2食）は厨房・サービスキャパが客室数と連動し、**客室在庫の最適化だけでは解けない**。
- 一方で、**意思決定の回数は100室ホテルと同じ**（毎日 × 365日先 × 複数プラン × 複数チャネル）。

つまり本件の本質は「高度な予測AIを導入する」ことではありません。**少人数のオペレーションが、毎日発生する数百の値付け判断を、経験に依存せず、抜け漏れなく、再現可能に処理し続けられる仕組みを作る**ことです。

### 0.2 提案の骨子 — 4つの設計原則

| # | 原則 | 内容 | 属人性排除への効き方 |
|---|---|---|---|
| 1 | **判断のコード化** | 値付けの意思決定を「基準価格 × 5つの補正係数」という決定論的モデルとして外部化 | 担当者が誰でも同じ入力から同じ価格が出る |
| 2 | **説明可能性の強制** | 全推奨価格を「基準価格＋各要因の円建て寄与」に分解して出力 | 「なぜこの価格か」が引き継ぎ可能な形で残る |
| 3 | **例外管理への転換** | ガードレール内は自動配信、逸脱分のみ人が承認 | 毎日の意思決定コストを1日15分に圧縮 |
| 4 | **記入漏れの構造的排除** | イベント表への人手入力に頼らず、競合の売止・価格急騰から需要を**逆算検知** | 「イベントを知らなかった＝取りこぼし」が起きない |

### 0.3 中核となる価格算定式

```
log P = log(P_base) + b₁·z_pace + b₂·z_comp + b₃·z_event + b₄·z_lead + b₅·z_remain
```

| 項 | 意味 | 主なデータ源 |
|---|---|---|
| P_base | 基準価格（シーズン × 曜日 × 連休前夜） | **自動校正**（市場整合 × 予算整合の2条件から解く） |
| z_pace | 予約進捗の対ベンチマーク乖離 | PMS／サイトコントローラー |
| z_comp | 競合NAR中央値に対する位置 | レートショッパー／Google Hotels API |
| z_event | 需要イベント強度（登録＋自動検知） | 需要カレンダー＋競合挙動 |
| z_lead | リードタイム補正 | 予約日 − 宿泊日 |
| z_remain | 残室の希少性 | PMS |

対数加法形を採用したのは、各要因の寄与が**乗数として独立に解釈でき、円単位のウォーターフォールに分解できる**ためです。ブラックボックスのAI予測ではなく、経営が読める構造にすることを優先しました。

### 0.4 想定効果（※仮定値ベース）

前提：客室売上（1泊2食総額ベース）**1.1億円/年**、稼働65%、ADR 95,000円 ※仮定

| 効果項目 | 根拠 | 年間インパクト |
|---|---|---|
| RevPAR改善 +7% | RM導入の業界一般レンジ（+5〜12%）の保守側 | **+770万円** |
| 直販比率 20%→35% | 平均OTAコスト15.0% vs 直販3.5%（本提案の設定値） | **+190万円** |
| 合計（GOP寄与） | ※重複計上を避けるため直販効果は手取り差のみ計上 | **約 +960万円** |

| 投資 | 金額 |
|---|---|
| 初期構築（Phase 0〜2） | 350〜600万円 |
| 年間運用（データ調達＋インフラ＋保守） | 100〜180万円 |
| **投資回収期間** | **8〜12ヶ月** |

### 0.5 調達方針 — Build と Buy の切り分け

フルスクラッチも、フルSaaSも、5室オーベルジュには適合しません。

| レイヤ | 方針 | 理由 |
|---|---|---|
| 競合レート収集 | **Buy** | 自前スクレイピングはOTA規約違反リスク。商用レートショッパー／公式API経由が唯一の健全解 |
| データ基盤 | **Buy（マネージド）** | BigQuery等。運用要員を置けない規模 |
| **正規化・価格ロジック・ガードレール** | **Build** | 人数課金／2食付き／MLOS／貢献利益フロアという施設固有事情は汎用RMSが吸収しきれない。**ここが唯一の差別化資産** |
| 配信 | **既存活用** | 現行サイトコントローラーのAPIに接続 |

## 1. 現状認識と課題構造

### 1.1 施設プロファイル（公開情報ベース）

- 全5室のオーベルジュ。奈良市春日野町、奈良公園・春日大社の至近。
- 1泊2食を基本商品とし、朝食単体は約6,600円/名の水準（公開情報）。
- 販売チャネルは一休.com、楽天トラベル、じゃらんnet 等の主要OTA＋自社サイト。
- 高付加価値・低客室数という、**価格弾力性より希少性で勝負する**ポジション。

### 1.2 このクラスの施設に典型的な5つの課題

| # | 課題 | 症状 | 本提案での対処 |
|---|---|---|---|
| 1 | **料金表の解像度不足** | 季節3区分 × 平日/週末の6階段程度で年間を運用。需要のピークと価格が一致しない | 日次365日の価格解像度へ（§2） |
| 2 | **競合把握が目視・断片的** | 週に数回、担当者が主要OTAを目で見る。網羅性も再現性もない | 日次自動収集＋正規化（§3） |
| 3 | **比較が非対等** | 競合の「素泊まり28,000円」と自社の「2食付き95,000円」を並べて意味を成さない | NAR正規化（§3.3） |
| 4 | **見えない値引きの放置** | OTAのポイント原資・クーポン・タイムセールが手取りをどれだけ削っているか未把握 | Net ADR一元管理（§5） |
| 5 | **判断の属人化** | 値付けの理由が個人の頭の中にあり、退職・異動で消える | 決定論モデル＋意思決定ログ（§2、§6） |

### 1.3 「レベニューマネージャーを雇う」が解にならない理由

5室規模で専任のレベニューマネージャー（年収600〜900万円）を置くと、想定効果 約960万円をほぼ食い潰します。かつ、その人材が退職した瞬間に運用が停止します。

**採るべきは「人を雇う」ではなく「判断をシステムに移設し、運用を1日15分に圧縮する」設計**です。人の役割は、値付けそのものではなく、①ガードレールの設定、②例外の承認、③四半期のモデル校正、の3点に限定します。

## 2. プライシング設計

### 2.1 基準価格の自動校正 — 最も属人的な判断を機械化する

「基準価格をいくらに置くか」は従来、最もベテランの勘に依存してきた判断です。本提案ではこれを**2つの条件から機械的に解き、両者の差分を経営課題として可視化**します。

- **条件A（市場整合）**：標準期の基準価格が、競合NAR中央値の目標ポジション倍（例 1.15倍）となる値
- **条件B（予算整合）**：想定稼働のもとで年間RevPAR目標を満たす値

参照実装（`engine/scripts/calibrate_base.py`）の実出力：

```
現行アンカー                :     95,000 円
競合NAR中央値（全期間中央値）:     69,100 円
現行の含意ポジション        :       1.37 倍
--------------------------------------------------------------------
条件A 市場整合アンカー      :     81,000 円（目標ポジション 1.15 倍）
条件B 予算整合アンカー      :     87,000 円（RevPAR 62,000 円 / 稼働 72%）
乖離（予算 ÷ 市場 − 1）     :      +6.3%
--------------------------------------------------------------------
▶ 推奨アンカー              :     82,000 円
  判定: 予算が市場を上回る。価格だけでは目標未達。
        商品価値（食事・体験・アップセル）か稼働前提の見直しが必要。
```

重要なのは最後の判定です。**市場が許容する価格と事業計画が要求する価格のギャップを、エンジンは埋めずに経営へ上げます。** ここを暗黙に埋めてしまうのが属人化の温床であり、「なんとなく強気に置いた基準価格」が年間を通じて稼働を毀損する典型的な失敗経路だからです。

### 2.2 5つの補正係数

| 係数 | z の定義 | 設計上の要点 |
|---|---|---|
| **z_pace** | (実OTB − 期待OTB) を 1.5室で標準化 | 5室では日別実績の分散が過大。**シーズン×曜日の「日カテゴリ」にプールしたベンチマークカーブ**に対して評価（縮小推定の実務版） |
| **z_comp** | log(競合NAR中央値 ÷ 基準価格) ÷ 0.30 ＋ 0.5×市場逼迫度 | 単純平均でなく**重み付き中央値**。ティア別重み（PRIMARY 1.0／SECONDARY 0.5／ASPIRATIONAL 0.3）で外れ値の影響を遮断 |
| **z_event** | 登録イベントスコアと自動検知スコアの最大値 | §2.4 |
| **z_lead** | リードタイム区分別の固定補正 | **直前は値下げしない**。高付加価値宿の直前割引はブランドを毀損し、早期予約客の不公平感を生む（§2.5） |
| **z_remain** | 販売済率の線形写像 × リードタイム減衰 | リードタイムが長いうちは希少性を効かせない（早期の売り急ぎ／吊り上げ防止） |

各項の対数寄与は **±0.28（約±32%）にクリップ**し、単一シグナルの暴走を防ぎます。

### 2.3 出力例 — 「なぜこの価格か」の完全な分解

参照実装の実出力（2026年11月21日・土曜・紅葉ピーク）：

```
■ 2026-11-21（SAT）紅葉 / PEAK:WEEKEND
  リードタイム 98日 ／ 残室 4室 ／ MLOS 1泊
  基準価格                             136,372 円
   予約ペース（対ベンチマーク）        +8,673 円  (z=+0.15) →   145,045 円
   競合ポジション（NAR中央値比）       -7,551 円  (z=-0.17) →   137,494 円
   需要イベント                       +37,295 円  (z=+0.80) →   174,789 円
   リードタイム                        -5,166 円  (z=-0.15) →   169,623 円
   残室希少性                              +0 円  (z=-0.00) →   169,623 円
  モデル出力                           169,623 円
   ガードレール: 日次変動幅 ±15% で上方制限
  ▶ 推奨価格   152,000 円（現行 132,000 円 / +15.2% / 要承認）
  競合NAR中央値 127,100 円 に対し 1.20 倍 ／ 紅葉ピーク
```

この1画面が本提案の成果物の本体です。担当者が誰であっても、**価格の根拠が円単位で追跡でき、上長が5秒で妥当性を判断でき、1年後に「なぜあの日この値段だったか」を再現できます。**

### 2.4 需要イベントの自動検知 — 「知らなかった」を構造的に潰す

奈良は需要イベントが多く、かつ**全国的な知名度が低いものほど値付けの機会損失が大きい**という特性があります（若草山焼き、修二会・お水取り、正倉院展、鹿の角きり、なら燈花会、紅葉、桜）。

これらをカレンダーに手入力する運用は、必ず記入漏れを起こします。そこで**競合の挙動から需要を逆算検知**します。

> コンペセットの**重み付き売止率が55%超** かつ **NAR中央値が同一日カテゴリの平常時比+25%超** → カレンダー未登録でも「市場イベント」として自動的にイベントスコアを付与

これにより、学会・大型ツアー・臨時イベント・近隣他都市（京都・大阪）からの需要スピルオーバーなど、**カレンダーに載らない需要**を捕捉できます。属人性排除の要の一つです。

### 2.5 直前在庫の扱い — 値下げではなく「価値付加」

残室が出た直前期に価格を下げるのは、短期的には埋まりますが、
①ブランド毀損、②「待てば安くなる」という学習効果、③早期予約客の不公平感、を生みます。

**本提案では直前のリードタイム補正をマイナスにしません。** 代わりに、
- 貸切風呂・客室アップグレード・ウェルカムドリンク等の**非価格特典**
- 自社会員／リピーター限定の**フェンス付き**オファー
- 「1泊の空隙（gap night）」検知による**ピンポイント開放**

で埋めます。値引きの可視性を制御することが、高価格帯施設のADR維持の生命線です。

### 2.6 滞在制約（MLOS）と空隙最適化 — 5室ならではの高効率レバー

5室規模では、価格変更より**滞在制約の設計のほうが収益インパクトが大きい**局面が頻繁にあります。

| 機能 | ロジック | 効果 |
|---|---|---|
| **MLOS設定** | イベントスコア0.6以上 or 対競合1.15倍以上、かつ残室2室以下・リード7日以上 → 最低2泊 | 繁忙日が1泊予約で埋まり前後日に穴が空く「在庫断片化」を防止 |
| **gap night検知** | 前後日が満室近く、当日のみ2室以上空き、リード21日以内 → MLOS解除＋非価格特典 | 連泊客では埋まらない1泊の空隙をピンポイントで充当 |

参照実装の120日シミュレーションでは MLOS設定日 7日 が自動抽出されました。人手では見落とす類の判断です。

### 2.7 ガードレール — 事故を起こさない設計

自動化の最大のリスクは、データ収集エラーによる異常価格の配信です。適用順序を含めて厳密に設計しています。

**適用順序：モデル出力 → 日次変動幅 → 丸め → 絶対境界**（絶対境界を最後に効かせ、他ルールが越えられないようにする）

| ガードレール | 設定値 | 目的 |
|---|---|---|
| 貢献利益フロア | 58,000円 ※仮定 | 食材・リネン・OTA手数料・変動人件費を賄えない価格を出さない。**原価が変われば必ず再計算** |
| 天井 | 240,000円 ※仮定 | ブランドレンジの逸脱防止 |
| 日次変動幅 | ±15% | 顧客・OTAから見た価格の乱高下防止 |
| 自動適用帯 | ±12% | この範囲内は無人で配信 |
| ハードストップ | ±35% | 超過分は**自動棄却＋警告**。データ異常の疑い |
| 丸め単位 | 1,000円 | 価格の見え方の統一 |

これらは参照実装の回帰テスト（22件）でCIゲートとして担保しています。

## 3. 競合データ収集の設計

詳細は **[02_データ収集設計.md](02_データ収集設計.md)** に記載。要点のみ：

### 3.1 Googleマップからのデータ収集について（ご指摘への回答）

ご指摘のとおりGoogle系はデータ源として有効ですが、**用途を正しく分ける必要があります**。

| Google のサービス | 取れるもの | 本件での使い方 |
|---|---|---|
| **Places API** | 施設名・位置・評点・レビュー件数・価格帯記号（$〜$$$$） | ❌ 実勢ADRは**取れない**（4段階の記号のみ）<br>⭕ **コンペセットの発見**と、**レビュー件数の月次増分＝需要トレンドの代理指標** |
| **Google Hotels（ホテル価格）** | 施設 × チェックイン日の**実勢価格・空室状況** | ⭕ **競合レートの主データ源**。SerpApi／DataForSEO 等のAPI経由で取得 |

つまり「Googleマップから価格を取る」のではなく、**Places APIでコンペセットを機械的に発見・監視し、価格はGoogle Hotels から取る**、という二段構えが正解です。

### 3.2 収集コストの圧縮設計

競合8施設 × 120日先を毎日全数取得すると **月28,800リクエスト**（SerpApi $275プラン相当）。これを**取得頻度の階層化**で圧縮します。

| リードタイム帯 | 頻度 | 理由 |
|---|---|---|
| D+0〜14 | 毎日 | 価格変動が最も激しい |
| D+15〜45 | 週2回 | 変動は中程度 |
| D+46〜120 | 週1回 | ほぼ静的 |

→ **月8,297リクエスト（3.5倍の圧縮）**。$150プラン相当（約2〜3万円/月）で運用可能。エリア一括クエリを併用すればさらに1/3程度まで削減できます。

### 3.3 NAR正規化 — 汎用RMSが吸収しきれない部分

収集した価格をそのまま平均しても比較になりません。全社の掲出価格を **「1室2名1泊2食・税サ込のルームナイト総額」** に揃えます。

```
NAR = (掲出価格 × [人数課金なら2]) + (不足する食事のuplift)
```

例：
- 競合A（人数課金・2食付き）33,000円/名 → **66,000円**
- 競合C（室課金・素泊まり）42,000円 → + 夕食26,000 + 朝食8,000 = **76,000円**
- 競合D（室課金・朝食付き）38,000円 → + 夕食26,000 = **64,000円**

この正規化ロジックこそが施設固有の資産であり、**汎用RMSでは吸収しきれないため自社で持つべき**部分です。

### 3.4 コンペティティブセットの定義

| ティア | 定義 | 重み | 例（想定） |
|---|---|---|---|
| PRIMARY | 奈良公園・春日野・ならまち圏の高付加価値小規模宿 | 1.0 | ANDO HOTEL 奈良若草山、奈良公園エリアの小規模旅館、ならまち町家ホテル 等 |
| SECONDARY | 価格帯代替（奈良市内上位・京都南部） | 0.5 | 広域で比較検討される層 |
| ASPIRATIONAL | 目標ポジション（ADR天井の参照点） | 0.3 | 市内ラグジュアリー温泉旅館 |

選定基準は距離・価格帯重複・客室規模・食事形態・レビュー属性（インバウンド比率）を数値化したスコアで行い、**四半期ごとに機械的に再評価**します。「なんとなくあそこが競合」という感覚を排除します。

### 3.5 法務・コンプライアンス（重要）

**自前でのOTAサイトスクレイピングは推奨しません。** 主要OTAの利用規約は自動収集を禁止しているのが通例であり、著作権法30条の4（情報解析目的の利用）は複製の可否に関する規定であって、**契約違反・サーバ負荷・不正競争のリスクを免れるものではありません**。

採用する取得経路は以下に限定します。

1. 商用レートショッパー（メトロエンジン、Lighthouse 等）との正規契約
2. Google Hotels の公式／準公式API（SerpApi、DataForSEO 等）
3. OTAのパートナーAPI（自社データの取得）

その他、景品表示法（二重価格表示：動的価格では「通常価格」表記を避ける）、個人情報保護法（予約者個人データはPMS内に留め、価格エンジンには集計値のみ渡す設計分離）、レートパリティ条項（直販優位は「価格」ではなく「特典・条件」で作る）に留意します。

## 5. チャネル戦略 — 掲出ADRではなく Net ADR で意思決定する

### 5.1 見えない値引きの一元管理

OTAの手数料だけでなく、**ポイント原資・クーポン・会員割引・タイムセール**はすべて実質的な値引きです。これらを控除した**Net ADR（施設手取り）**で比較して初めて、販促参加の可否や直販シフトの価値を定量判断できます。

参照実装の実出力（推奨価格152,000円の日）：

| チャネル | 掲出 | 実質コスト | 手取り | 直販との差 |
|---|---:|---:|---:|---:|
| 自社直販 | 152,000 | 3.5% | **146,680** | — |
| 楽天トラベル | 152,000 | 12.0% | 133,760 | −12,920 |
| じゃらんnet | 152,000 | 12.0% | 133,760 | −12,920 |
| 一休.com | 152,000 | 14.0% | 130,720 | −15,960 |
| Booking.com | 152,000 | 18.0% | 124,640 | −22,040 |
| Expedia | 152,000 | 19.0% | 123,120 | −23,560 |

※コスト率は仮定値。実契約値に置換すること。

**直販1件へのシフトは、実質的にADRを11〜16%引き上げるのと同じ効果**を持ちます。価格を1円も動かさずに得られる収益改善として、これが最大のレバーです。

### 5.2 直販シフトの設計

- 会員制度（リピーター価格ではなく**特典と条件**で差別化 — パリティ条項に抵触しない設計）
- 自社予約エンジンでのみ提供するパッケージ（体験・送迎・アーリーチェックイン等）
- チェックアウト時の次回直接予約導線、CRM（宿泊後のフォロー）
- 目標：直販比率 20% → 35%（→ 年間 約190万円の手取り増）

### 5.3 チャネル別の役割設定

| チャネル | 役割 | 運用方針 |
|---|---|---|
| 自社直販 | 収益の柱・顧客関係の起点 | 最優先。特典で優位を作る |
| 一休.com | 高価格帯の集客・ブランド接点 | ADR維持。タイムセール参加はNet ADRで都度判定 |
| 楽天／じゃらん | 国内量の確保 | ポイント原資込みで採算判定。閑散期の稼働補填に限定運用 |
| Booking／Expedia／Agoda | インバウンド | コスト高。繁忙期は在庫を絞り、閑散期に開放。**為替による実質価格変動を監視** |

## 6. 運用設計 — 属人性排除の本丸

システムだけでは属人性は消えません。**運用のリズムと権限をルール化**して初めて完結します。

### 6.1 運用サイクル

| 頻度 | 所要 | 内容 | 担当 |
|---|---|---|---|
| 日次 | **15分** | ダッシュボード確認、承認キューの処理のみ（自動適用帯の推奨は無人配信済み） | 支配人 |
| 週次 | **60分** | Revenue Meeting（資料は自動生成）：先週の推奨vs実績、ピックアップ、競合動向、次90日のアクション | 支配人＋オーナー |
| 月次 | 90分 | プランミックス・レートフェンス・アップセルの見直し | 支配人＋料飲 |
| 四半期 | 半日 | **基準価格の校正**、コンペセット再定義、係数の再推定 | オーナー＋外部アドバイザー |
| 年次 | 1日 | 予算・シーズンカレンダー・貢献利益フロアの再設定 | 経営 |

### 6.2 権限設計

| 推奨の乖離幅 | 扱い |
|---|---|
| ±12%以内 | **自動配信**（人の関与なし） |
| ±12〜35% | **承認キュー**へ。承認・却下ともに**理由コードの入力を必須**とする |
| ±35%超 | **自動棄却**＋データ異常アラート |

手動オーバーライドは**必ず期限付き**とし、期限到来で自動的にモデル値へ復帰します。「昔誰かが手で入れた価格が塩漬けで残る」という最も典型的な属人化を構造的に防ぎます。

### 6.3 Revenue Playbook と意思決定ログ

- **Revenue Playbook**：判断基準を全て文書化（何を見て、どの閾値で、何をするか）。新任者が1日で運用に入れる状態を作る。
- **意思決定ログ**：全ての価格変更に「日時・変更者・変更前後・理由コード・モデル推奨との乖離」を記録。四半期レビューで、**オーバーライドが収益にプラスだったかマイナスだったか**を検証する。

### 6.4 属人性排除の測定指標

仕組みが機能しているかを、以下で定量的に監視します。

| 指標 | 意味 | 目標 |
|---|---|---|
| 推奨採用率 | 自動配信＋承認された推奨の割合 | 85%以上 |
| オーバーライド率 | 人が推奨と異なる価格を入れた割合 | 15%以下 |
| **オーバーライドのPnL寄与** | 手動介入が収益を改善したか | プラスでなければモデルを直す（人を責めない） |
| 承認キュー滞留時間 | 承認待ちの平均時間 | 24時間以内 |
| データ鮮度 | 競合レートの最終取得からの経過時間 | 24時間以内 |

**「オーバーライドのPnL寄与がマイナス」＝人の勘がモデルに負けている**、**「一貫してプラス」＝モデルに欠けている変数がある**、と読みます。どちらの場合も次の四半期でモデルを更新します。これが、属人的な知見を組織資産へ変換する仕組みです。

## 7. KPI体系

| 階層 | 指標 |
|---|---|
| 収益 | ADR（1室2名2食総額）、OCC、RevPAR、**TRevPAR**、**Net RevPAR（手数料控除後）**、GOPPAR |
| 市場相対 | RateIndex（対コンペセットNAR中央値）、在庫消化指数<br>※コンペの実績は取得不能のため、公開レートベースの擬似ARIで代替 |
| 需要 | ピックアップ、ブッキングペース、ブッキングカーブ、リードタイム分布、キャンセル率 |
| チャネル | チャネルミックス、**直販比率**、チャネル別Net ADR、チャネル別リピート率 |
| プロセス | 推奨採用率、オーバーライド率とPnL寄与、データ鮮度、承認滞留時間 |

**5室では「稼働率」を単独のKPIにしない**ことが重要です。1室で20ポイント動くため経営指標として不安定であり、稼働率を目標にすると値下げのインセンティブが働きます。**RevPAR（さらにNet RevPAR）を主KPI**とし、稼働率は補助指標に留めます。

## 8. 導入ロードマップ

詳細は **[04_導入ロードマップとROI.md](04_導入ロードマップとROI.md)**。

| Phase | 期間 | 内容 | ゲート条件 |
|---|---|---|---|
| **0 診断** | 0〜4週 | 過去2〜3年の予約データ棚卸し、シーズンカレンダー策定、コンペセット定義、**貢献利益フロアの算定**、Baseline確立 | Baseline KPIが確定していること |
| **1 MVP（影響なし運用）** | 5〜12週 | データ基盤＋競合収集＋推奨算出。**配信はせず「推奨のみ」出力**し、人の判断と突き合わせる（シャドーモード） | 推奨と人の判断の一致率が70%超 |
| **2 半自動運用** | 13〜24週 | ガードレール内は自動配信開始。承認キュー運用。MLOS・gap night最適化 | 推奨採用率85%超、事故ゼロ |
| **3 高度化** | 25〜40週 | 需要予測モデルの精緻化、アップセル／TRevPAR最適化、直販シフト施策、多施設展開対応 | RevPAR前年比 +7%超 |

**Phase 1 のシャドーモードは省略しないでください。** いきなり自動配信を始めると、モデルの欠陥が売上毀損として顕在化してからしか分かりません。「推奨を出すが配信はしない」期間で、人の判断と突き合わせてモデルを校正することが、安全かつ現場の納得を得る唯一の道です。

## 9. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 競合データの品質不良（食事条件の誤判定） | 誤った価格ポジション判断 | NAR正規化＋月次のサンプル監査（実際にOTA画面と突合）＋異常値自動除外 |
| データ収集の停止・API仕様変更 | 推奨が古いデータで出る | データ鮮度監視＋鮮度劣化時は自動配信を停止しモデル値を凍結 |
| 値下げ競争への巻き込まれ | 利益毀損 | **貢献利益フロア**（変動費ベース）でハード制限。価格ではなく特典で競争 |
| ブランド毀損 | 中長期のADR低下 | 直前値下げの禁止、フェンス設計、割引の可視性制御 |
| OTA規約・法務 | 契約解除・法的リスク | 公式API／商用データのみ使用。§3.5 |
| 過度なシステム依存 | 異常時に判断できない | Revenue Playbookに手動運用手順（フォールバック料金表）を明記 |
| 小サンプル起因の過学習 | 誤った需要予測 | 日別ではなく**日カテゴリへのプーリング**、複雑なMLモデルを避け解釈可能な加法モデルを採用 |

## 10. 拡張性 — 多施設展開への布石

本提案の設計は、**施設設定ファイル（`config/property.json`、`config/compset.json`、`config/calendar.json`）を差し替えるだけで別施設に適用できる**構造としています。

エンジン本体（正規化・ペース評価・価格算定・ガードレール）は施設非依存です。運営施設が増えるほど、
- 自社ロジックを資産として持つことの投資対効果が上がる
- 施設横断のベンチマーク（日カテゴリ別のペースカーブ等）でサンプル不足が解消される
- グループ全体のポートフォリオ最適化（同一顧客の施設間送客）が可能になる

という逓増効果が働きます。5室単独では「割に合うか微妙」な自社開発が、複数施設で明確に正当化されます。**この点を、初期設計から折り込んでおくことを強く推奨します。**
