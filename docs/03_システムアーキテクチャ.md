## 1. 設計方針

| 方針 | 内容 |
|---|---|
| **運用要員ゼロ前提** | 全てマネージドサービス。サーバの面倒を見る人を置かない |
| **生データ不変** | Raw層は加工せず保存。正規化ロジックの改善に遡って追随できる |
| **意思決定層のみ自社実装** | 収集・蓄積・配信は買う。価格ロジックだけを資産化する |
| **フェイルセーフ** | データ異常・鮮度劣化時は「配信しない」側に倒す |
| **完全な監査可能性** | すべての価格変更に、誰が・いつ・なぜ・モデル推奨との乖離を記録 |

## 3. データモデル（主要テーブル）

```sql
-- 競合レート（生値保存。正規化は下流）
CREATE TABLE fact_comp_rate (
  snapshot_date DATE     NOT NULL,   -- 取得日
  stay_date     DATE     NOT NULL,   -- 宿泊日
  comp_id       STRING   NOT NULL,
  source        STRING   NOT NULL,   -- rate_shopper / google_hotels
  channel       STRING,
  raw_rate      NUMERIC,
  currency      STRING,
  available     BOOL,
  los           INT64,
  ingested_at   TIMESTAMP
) PARTITION BY stay_date CLUSTER BY comp_id, snapshot_date;

-- 自社OTBスナップショット（append only。上書き厳禁）
CREATE TABLE fact_otb (
  snapshot_date       DATE  NOT NULL,
  stay_date           DATE  NOT NULL,
  rooms_otb           INT64,
  room_revenue_otb    NUMERIC,
  current_public_rate NUMERIC,
  cancellations_todate INT64
) PARTITION BY stay_date CLUSTER BY snapshot_date;

-- 推奨結果（説明可能性のため各要因の寄与を列で保持）
CREATE TABLE mart_daily_recommendation (
  run_date          DATE,
  stay_date         DATE,
  day_class         STRING,       -- 例 "PEAK:WEEKEND"
  base_rate         NUMERIC,
  contrib_pace      NUMERIC,      -- 円建て寄与
  contrib_comp      NUMERIC,
  contrib_event     NUMERIC,
  contrib_lead      NUMERIC,
  contrib_remain    NUMERIC,
  model_rate        NUMERIC,      -- ガードレール適用前
  recommended_rate  NUMERIC,      -- 最終
  current_rate      NUMERIC,
  delta_pct         NUMERIC,
  action            STRING,       -- AUTO_APPLY / APPROVAL_REQUIRED / REJECTED_ANOMALY
  guardrail_notes   ARRAY<STRING>,
  comp_median_nar   NUMERIC,
  comp_position     NUMERIC,
  mlos              INT64,
  gap_night         BOOL
) PARTITION BY stay_date CLUSTER BY run_date;

-- 意思決定ログ（監査の中核）
CREATE TABLE log_decision (
  decided_at      TIMESTAMP,
  stay_date       DATE,
  actor           STRING,        -- "system" or ユーザーID
  action          STRING,        -- AUTO_APPLY / APPROVED / REJECTED / MANUAL_OVERRIDE
  model_rate      NUMERIC,
  applied_rate    NUMERIC,
  deviation_pct   NUMERIC,       -- 人の判断がモデルからどれだけ離れたか
  reason_code     STRING,        -- 必須
  reason_note     STRING,
  expires_at      DATE           -- 手動オーバーライドの自動失効日
);
```

### 3.1 `log_decision` が最も重要なテーブルである理由

このテーブルがあることで、四半期レビューで次の問いに**データで**答えられます。

- 人が介入した日の実績は、モデル推奨のままだった場合と比べて良かったか、悪かったか
- 特定の理由コードでの介入が、一貫して収益にプラス／マイナスになっていないか
- 手動オーバーライドが失効せずに残り続けている日はないか

**「オーバーライドが一貫してプラス」＝モデルに欠けている変数がある**というシグナルであり、次期のモデル改善のインプットになります。逆に**「一貫してマイナス」＝人の勘がモデルに負けている**ので、介入ルールを締めます。

これが、属人的な知見を組織の資産へ変換する具体的な機構です。

## 4. ジョブスケジュール（JST）

| 時刻 | ジョブ | 内容 | 失敗時 |
|---|---|---|---|
| 02:00 | `ingest_rate_shopper` | 競合レート（主） | 3回リトライ → アラート |
| 02:30 | `ingest_google_hotels` | 競合レート（階層化スケジュール） | 同上 |
| 03:00 | `ingest_pms` | OTB・予約明細（**append only**） | **失敗したら以降を停止** |
| 03:30 | `ingest_context` | 祝日・天候・為替 | 前日値を流用して継続 |
| 04:00 | `data_quality_check` | 鮮度・カバレッジ・値域・前日比 | **NG なら配信ジョブを停止** |
| 04:30 | `run_pricing` | 推奨算出（D+0〜365） | アラート |
| 05:00 | `distribute` | 自動適用帯のみサイトコントローラーへ配信 | ロールバック＋アラート |
| 05:15 | `notify_queue` | 承認キューをSlack／メール通知 | — |
| 月曜 06:00 | `weekly_pack` | Revenue Meeting 資料の自動生成 | — |
| 四半期初 | `calibrate` | 基準価格・コンペセット・係数の校正レポート | — |

**`data_quality_check` が配信の前段にあることが設計の要**です。データが壊れている日は、価格を配信しません。「古い価格のまま」は損失ですが、「壊れたデータに基づく異常価格」は事故です。

## 5. 配信層の設計

### 5.1 サイトコントローラー連携

現行のサイトコントローラー（TL-リンカーン／手間いらず／ねっぱん／ダイレクトイン等）のAPIに接続します。**各OTAへ個別に接続しない**でください。接続先が増えるほど障害点と保守コストが増え、5室規模では割に合いません。

Phase 1 では API 連携を行わず、**CSV出力 → 手動取り込み**で運用します。API連携は Phase 2 で、シャドーモードによる精度検証を終えてから着手します。

### 5.2 配信の安全機構

| 機構 | 内容 |
|---|---|
| 冪等性 | 同一 (run_date, stay_date) の配信は1回のみ。重複実行しても二重更新しない |
| 差分配信 | 現行価格と同値なら送らない（API呼び出し数とログの節約） |
| ロールバック | 配信前の価格を必ず保存し、1コマンドで巻き戻せる |
| 配信上限 | 1回の実行で変更できる日数に上限（例：60日）を設け、暴走時の影響を限定 |
| ドライラン | `--dry-run` で差分のみ出力し、実配信しないモードを常備 |

## 6. 技術選定

| レイヤ | 採用 | 理由 |
|---|---|---|
| 実行基盤 | Cloud Run Jobs | サーバ管理不要。実行時間のみ課金。日次バッチに最適 |
| スケジューラ | Cloud Scheduler | cron 相当。リトライ内蔵 |
| DWH | BigQuery | この規模なら無料枠〜数千円。スキャン課金でパーティション設計が効く |
| Raw保管 | Cloud Storage | 生データの不変保管。Nearline へ自動階層化 |
| 言語 | Python 3.11+ | データ処理の標準。参照実装は**標準ライブラリのみ**で動作 |
| BI | Looker Studio | 無料。BigQuery 直結 |
| 通知 | Slack Webhook ／ メール | 承認キューとアラート |
| シークレット | Secret Manager | APIキーをコードに置かない |
| IaC | Terraform | 環境の再現性。多施設展開時に効く |
| CI | GitHub Actions | テスト22件をゲート条件に。**テストが緑でなければ配信コードをデプロイしない** |

想定インフラ費用：**月5,000〜15,000円**（データ量が小さいため）。

## 7. セキュリティと個人情報

| 項目 | 方針 |
|---|---|
| 個人データの分離 | **予約者の個人情報は価格エンジンに渡さない**。PMSから取り込む段階で集計値（日次の室数・売上）に落とす |
| アクセス制御 | BigQuery のデータセット単位でIAM。個人情報を含むテーブルは別データセット＋限定権限 |
| APIキー管理 | Secret Manager。リポジトリへの直書き禁止（CIでシークレットスキャン） |
| 監査ログ | Cloud Audit Logs を有効化。誰がどのデータに触れたかを保持 |
| 保持期間 | Raw層は24ヶ月、集計層は無期限。個人情報を含むデータは業務上必要な期間のみ |

**個人情報を価格エンジンに入れない**のは、プライバシー配慮であると同時に設計上の合理性でもあります。価格判断に必要なのは集計値だけであり、個人データを持ち込むと、法的義務・アクセス制御・監査の負荷が全レイヤに波及します。

## 8. Build / Buy 判断マトリクス

| 機能 | Build | Buy | 判定 | 理由 |
|---|---|---|---|---|
| 競合レート収集 | ✗ | ⭕ | **Buy** | 規約・安定性・保守。自前は割に合わない |
| データ基盤 | ✗ | ⭕ | **Buy** | マネージドで十分 |
| **NAR正規化** | ⭕ | ✗ | **Build** | 人数課金・2食付きの施設固有事情を汎用RMSが吸収できない |
| **価格算定ロジック** | ⭕ | ✗ | **Build** | 5室固有の離散性・MLOS・貢献利益フロア。**唯一の差別化資産** |
| **ガードレール／承認** | ⭕ | ✗ | **Build** | 権限設計は事業判断そのもの |
| 需要予測（統計） | △ | △ | **Build（簡素に）** | 小サンプルでは複雑なMLより解釈可能な加法モデルが勝る |
| 配信 | ✗ | ⭕ | **Buy** | 既存サイトコントローラーを活用 |
| BI | ✗ | ⭕ | **Buy** | Looker Studio |

### 8.1 フルSaaS（既製RMS）を主軸にしない理由

既製RMSは優れた製品ですが、本件では次の点で適合しません。

1. **商品単位の不一致** — 多くのRMSは「1室あたりの素泊まり単価」を前提とし、1泊2食・人数課金の総額商品を扱いにくい
2. **貢献利益フロアの不在** — オーベルジュは食材・人件費という高い変動費を持つ。原価を無視した下限では利益を削る
3. **小サンプルへの不適合** — 大規模ホテル向けの需要予測モデルは、年間1,825室のデータでは機能しない
4. **MLOS／gap night** — 5室特有の在庫断片化問題への対応が弱い

一方、**レート収集をSaaSから買うのは完全に正しい判断**です。切り分けが重要であり、「RMSを導入するか／しないか」という二択で考えないことが要点です。

## 9. 参照実装のモジュール構成

```
engine/
├── config/
│   ├── property.json      施設・基準価格・ガードレール・係数・チャネル
│   ├── compset.json       コンペセット定義（ティア・重み・正規化パラメータ）
│   └── calendar.json      シーズン・イベント・祝日・ペースベンチマーク
├── kanoya_rm/
│   ├── config.py          設定読込・カレンダー解決・日カテゴリ
│   ├── normalize.py       NAR正規化
│   ├── compset.py         重み付き中央値・市場逼迫度・イベント自動検知
│   ├── pace.py            ブッキングカーブ評価
│   ├── calibrate.py       基準価格の自動校正
│   ├── pricing.py         対数加法モデル・ウォーターフォール・ガードレール
│   ├── restrictions.py    MLOS・gap night
│   ├── channels.py        Net ADR・直販シフト効果
│   ├── report.py          CSV／説明文／サマリ出力
│   └── cli.py             日次実行エントリポイント
├── scripts/
│   ├── make_sample_data.py   検証用データ生成
│   └── calibrate_base.py     基準価格の校正レポート
└── tests/
    └── test_engine.py     回帰テスト22件（CIゲート）
```

**施設非依存の設計**です。`config/` の3ファイルを差し替えるだけで別施設に適用でき、多施設展開時にエンジン本体の改修は不要です。

## 10. 監視とアラート

| アラート | 条件 | 通知先 | 深刻度 |
|---|---|---|---|
| データ鮮度劣化 | 競合レート最終取得 > 24h | Slack | **高（配信停止）** |
| 収集カバレッジ低下 | PRIMARY取得成功率 < 80% | Slack | 中 |
| 異常推奨 | ハードストップ（±35%）に抵触 | Slack ＋ メール | **高** |
| 配信失敗 | サイトコントローラーAPIエラー | Slack ＋ メール | **高** |
| 承認滞留 | 承認キュー滞留 > 24h | Slack | 中 |
| 競合の急変 | コンペNAR中央値の前日比 ±40%超 | Slack | 中（収集エラー疑い） |
| オーバーライド失効漏れ | `expires_at` 超過の手動価格が残存 | Slack | 低 |

アラートは**必ず「何をすべきか」を本文に含める**こと。「データ鮮度が劣化しました」ではなく「競合レートが26時間更新されていません。自動配信を停止しました。ベンダー側の障害状況を確認してください」と書きます。5室施設の運用者は専任のエンジニアではないため、アラートは行動指示でなければ機能しません。
