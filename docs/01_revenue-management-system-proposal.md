## 0. 本書の前提と読み方

本書は「システム企画書」であり、以下の前提で書かれている。

1. **数値は構造を示すための仮置きである。** 施設の実績ADR・OCC・チャネル構成は未取得のため、本文中の金額・比率はすべて `[要差替]` の仮定値として扱う。Phase 0 で実データに置き換えることを前提に、**計算式と感度は正しく**書いてある。
2. **施設情報は公開情報ベース。** 全5室・奈良公園春日野町・オーベルジュ（大和野菜を主役とした食事提供）・館内にレストランとバーという理解に基づく。相違があれば §3 の診断を再実行する。
3. **本書の核心は「アルゴリズム」ではなく「意思決定の設計」である。** 価格を出す数式はコモディティである。属人性を排除するのは、**誰が・いつ・何を決めてよいかを分離した統治構造**のほうであり、本書は §10 にその重心を置く。

## 1. エグゼクティブ・サマリー

### 1.1 結論

鹿のやに必要なのは「AIが値段を決めてくれるツール」ではない。必要なのは、
**「人間はパラメータを触る。価格は触らない」** という原則を物理的に強制する運用系である。

これを実現する構成を **RM-OS（Revenue Management Operating System）** と呼び、6層で定義する。

```
L6  検証・学習ループ        … 予測精度、Override成績、価格実験の評価
L5  配信レイヤー            … サイトコントローラー経由でOTAへ自動反映
L4  ガバナンスレイヤー      … Pricing Policy Document／ガードレール／承認
L3  最適化エンジン          … Bid Price 動的計画法（5室だから厳密解が解ける）
L2  予測エンジン            … 階層ベイズ需要モデル（少データを市場から借りる）
L1  データ基盤              … 正規化・時系列スナップショット・dbt
L0  データ取得              … 競合レート／Googleデータ／自社PMS／イベント
```

### 1.2 なぜ「小規模だからRMは不要」が誤りか

むしろ逆である。**5室という制約は、レベニューマネジメントの理論的旨味を最大化する。**

- 大型ホテルのRMは「200室をどう埋めるか」＝ 稼働の問題。
- 5室のRMは「**その日の1室を、誰に、いくらで売るか**」＝ 機会費用（Displacement Cost）の問題。
- 1室の売り逃し／安売りが、その日のOCCを20pt動かし、RevPARを直撃する。**判断の1回あたりの重みが40倍**である。

そして技術的には、**5室であるがゆえに在庫最適化の厳密解（動的計画法）が計算可能**になる。大規模ホテルではEMSR等の近似に頼らざるを得ない領域を、鹿のやは正面から解ける。これは規模の劣位ではなく、**規模ゆえの優位**である。

### 1.3 期待効果（仮定値・要差替）

| 指標 | 現状（仮） | 12ヶ月後目標 | 根拠 |
|---|---|---|---|
| ADR | ¥55,000 `[要差替]` | ¥60,500（+10%） | 高需要日の取りこぼし単価回復 |
| OCC | 70% `[要差替]` | 74%（+4pt） | 低需要日のLOS・在庫制御 |
| RevPAR | ¥38,500 | ¥44,770（**+16.3%**） | 上記の積 |
| 年間客室売上 | ¥70.3M | ¥81.7M（**+¥11.4M**） | 1,825室夜（5室×365日） |
| 直販比率 | 25% `[要差替]` | 40% | 手数料10-15% → Net RevPARにさらに寄与 |

> **感度**：RevPAR +5% でも年間 +¥3.5M。システム年間コスト（§16）は 100〜250万円規模であり、**+3%で損益分岐**する。RM投資は「当たれば大きい」ではなく「外しにくい」投資である。

### 1.4 データ収集についての重要な事実確認

ご指摘のとおり Google からのデータ収集は成立する。ただし**種類を分けて理解する必要がある**。

| 欲しいデータ | Googleマップ／Places APIで取れるか | 実際の取得手段 |
|---|---|---|
| 競合の**評点・レビュー件数・写真・属性** | ✅ 取れる（Places API (New) 公式） | Places API。ただし**規約上キャッシュは原則30日**（place_id を除く） |
| 競合の**実売価格・空室状況** | ❌ Places APIでは取れない | **Google Hotels**（検索／マップのホテルモジュール）に表示される公開価格を、SerpApi／DataForSEO 等の商用取得APIで日次取得 |
| 競合の**プラン内容・食事条件・LOS制限** | △ 部分的 | OTA個別（一休・楽天等）＋商用レートショッパー |
| 市場全体の**需要・稼働** | ❌ | 奈良市観光協会 月報、奈良県宿泊統計、観光庁 宿泊旅行統計 |

**Google Hotels に公式の一般開発者向け価格APIは存在しない。** したがって「Googleから価格を取る」＝実務上は商用取得APIのライセンス購入である。ここを曖昧にしたまま自前スクレイパーを組むと、利用規約・著作権・不正アクセス禁止法の三方向でリスクを負う。§6 で法務設計とともに扱う。

## 2. 課題認識 — 「属人性」の正体

「レベニューマネジャーの力量に左右される」という現象を分解すると、実際には**4つの別問題**が混ざっている。

| # | 属人性の正体 | 症状 | 解法（本提案の対応箇所） |
|---|---|---|---|
| A | **情報の属人性** | 競合価格を「見に行った人」しか知らない。見た日と見なかった日がある | L0 自動収集＋履歴保存（§6） |
| B | **判断基準の属人性** | 「この日は高くいけそう」の"そう"が言語化されていない | L4 Pricing Policy Document（§10） |
| C | **計算の属人性** | 残室数と残日数から機会費用を暗算している（＝人間には無理） | L3 Bid Price DP（§9） |
| D | **検証の属人性** | 結果が良かったのか悪かったのか誰も測っていないので、経験が蓄積も否定もされない | L6 学習ループ（§13） |

**重要な認識：A・C・D はシステムで完全に消せる。B は消せない。**

B（＝どういうホテルでありたいか、いくら以下では売らないか、誰に売りたいか）は経営判断であり、機械に委譲してはならない領域である。**属人性排除とは、Bを「個人の勘」から「文書化された経営方針」へ移すこと**を意味する。人を排除するのではなく、**人が担当すべき層を上に押し上げる**。

これが本提案の設計思想の第一原理である。

## 3. 施設特性の診断 — 5室オーベルジュのRM構造

### 3.1 構造的パラメータ

| 項目 | 値 | RM上の含意 |
|---|---|---|
| 客室数 | 5 | 年間販売可能室数 1,825室夜。統計的に**極めてスパース** |
| 1室の重み | 20%/日 | 1件のキャンセルがOCCを20pt動かす。**キャンセル管理がRMの一部** |
| 業態 | オーベルジュ（2食付主体） | ADRに食材原価が乗る。**Room-only ADR と Package ADR を分離管理必須** |
| 立地 | 奈良公園・春日野町（世界遺産隣接） | 需要は**イベント・季節・天候に極端に依存**（正倉院展、若草山焼き、お水取り、紅葉） |
| 客層 | 国内高付加価値層＋インバウンド | チャネル別に価格感度・予約リードタイムが全く異なる |
| レストラン・バー | あり | **TRevPAR（総売上／販売可能室数）で最適化すべき**。客室単体最適化は誤り |

### 3.2 スパース性という中心課題

5室 × 365日のデータで機械学習をすると、ほぼ確実に過学習する。「5月3日は満室だった」という事実から「5月3日は強い」と学ぶのは、n=1 の推論である。

**対処（§8 で詳述）：**
1. **階層ベイズ（partial pooling）** — 奈良市場全体・高価格帯セグメント全体の需要曲線を「親分布」として借り、鹿のや固有の偏差だけを推定する。データが薄い日付ほど市場平均に引き寄せられ、データが厚いほど自施設実績を信じる。これが**自動的に働く**のがベイズの利点である。
2. **外部シグナルで内挿** — 自社の予約データが5室分しかなくても、競合10施設の空室消化速度は50〜1,000室分の情報を持つ。**競合の残室推移は、自社の需要予測に対する最も強力な先行指標**である。
3. **事前分布に業界知見を注入** — 価格弾力性 ε の事前分布を「高級旅館 ε ≈ 1.2〜2.5」で置く。データが語り出すまでは業界常識が支配し、データが増えるにつれ実測に移行する。

### 3.3 5室ゆえの優位：厳密最適化が解ける

在庫制御の本質は「今の¥50,000のリクエストを受けるか、将来の¥80,000を待つか」という機会費用の判断である。これを状態空間 `(残室数 r ∈ {0..5}, 到着までの残日数 t ∈ {0..365})` の動的計画法で**厳密に**解く（§9）。状態数は 6 × 366 = 2,196 に過ぎず、365日分回しても一瞬で終わる。

大規模ホテルが近似せざるを得ない問題を、鹿のやは正解で解ける。**これが本提案最大の技術的差別化点である。**

## 4. 設計思想 — 3原則

### 原則1：Decision Rights の時間軸分離

属人性の排除は、意思決定の階層化によって達成する。

| 層 | 決めること | 決める人 | 頻度 | 形式 |
|---|---|---|---|---|
| **戦略** | ポジショニング、年間RevPAR目標、Comp Set、フロア／シーリング価格、チャネル構成方針 | オーナー／総支配人 | 年1回＋半期見直し | Pricing Policy Document（承認文書） |
| **戦術** | 季節係数、イベントカレンダー、パラメータ調整、実験計画の承認 | 支配人＋RM担当 | 月1回（RM会議） | 変更履歴つきパラメータ表 |
| **実行** | 日別・室タイプ別の価格、MinLOS、在庫開閉 | **システム（自動）** | 毎日 | ガードレール内は無承認で自動配信 |
| **例外** | Override（手動上書き） | RM担当（理由コード必須） | 随時 | 期限付き・監査ログ・月次で成績評価 |

> **標語：「人はパラメータを触る。価格は触らない。」**
> 誰かが価格を直接触りたくなったら、それは「ポリシーが現実を捉えていない」というシグナルである。価格を直すのではなく、**ポリシーを直す**。この規律だけで、属人性の8割は消える。

### 原則2：Explainable by Construction（構造的説明可能性）

ブラックボックスAIは採用しない。価格は必ず**分解可能な乗算モデル**で構成する。

```
最終提示価格 = BASE(室タイプ, 曜日, 季節)
             × f_demand(需要予測 / 残室ペース)
             × f_comp(競合価格インデックス)
             × f_pace(STLY比ピックアップ)
             × f_event(イベント係数)
             ─────────────────────────────────
             → GUARDRAIL でクリップ（下限/上限/日次変動幅）
             → BID PRICE で下限を再確認（機会費用を下回る価格は出さない）
```

各係数が「なぜ今日この価格なのか」を1行で説明する。**説明できない価格はOTAに出さない。** 経営会議で「なぜ4月18日が¥78,000なのか」に3秒で答えられることが、システムの受け入れ条件である。

### 原則3：Human-in-the-loop → Human-on-the-loop への段階移行

初日から全自動にしない。信頼は実績で買う。

```
Phase 1  システムは「見せる」だけ（推奨価格の提示、人が全件判断）
Phase 2  システムが提案 → 人が承認 → 自動配信（Human-in-the-loop）
Phase 3  ガードレール内は自動配信、人は例外のみ介入（Human-on-the-loop）
Phase 4  実験（価格A/B）まで自動、人は方針とレビューのみ
```

移行条件は感覚ではなく**数値で定義**する（例：Phase 2→3 は「30日間のOverride採用率が15%未満、かつ予測MAPEが12%未満」）。

## 6. L0：データ取得設計 — 競合レート自動収集

### 6.1 取得対象の定義

**収集グリッド（1日1回、深夜バッチ）**

| 次元 | 範囲 | 件数 |
|---|---|---|
| 競合施設 | Primary 6施設 ＋ Secondary 8施設 | 14 |
| 宿泊日（stay_date） | 当日 +0 〜 +120日 | 121 |
| 人数 | 2名（基準）※必要に応じ1名も | 1〜2 |
| LOS | 1泊・2泊 | 2 |

→ 日次 約 3,400〜6,800 クエリ。年間 約 124万〜248万レコード。**この「毎日撮る」ことが最重要**である。

> ★ **設計上の最重要ポイント：`as_of_date` × `stay_date` の二次元スナップショット**
> 「今日の12月24日の価格」ではなく、「**11月1日時点で見た12月24日の価格**」「11月2日時点で見た12月24日の価格」…をすべて保存する。
> これにより、**競合がいつ値上げ／値下げしたか、いつ売り切れたか**という「競合の販売ペース」が見える。これは価格そのものより情報価値が高い。競合が90日前に満室になる日は、鹿のやが強気に出るべき日である。単純な価格比較しかしないRMツールは、この情報を捨てている。

### 6.2 データソース別 取得方式と法務設計

| # | ソース | 取得物 | 方式 | 法務・規約上の扱い |
|---|---|---|---|---|
| 1 | **Google Hotels**（検索／マップのホテル価格モジュール） | 競合の日別公開価格・満室有無 | **SerpApi / DataForSEO 等の商用取得APIを契約** | ✅ 推奨。取得責任がベンダ側に移り、契約に基づく利用となる。自前クローラより安全かつ安定 |
| 2 | **Google Places API (New)** | 評点、レビュー件数、レビュー本文、属性、写真 | Google公式API（従量課金） | ✅ 公式。ただし**規約上キャッシュ期間に制限**（place_id 以外は原則30日以内に更新）。設計に反映必須 |
| 3 | **商用レートショッパー**（Lighthouse（旧OTA Insight）／RateGain／メトロエンジン等） | 競合レート・パリティ・マーケットデマンド | SaaSライセンス | ✅ 最も安全。日本のOTA（一休・楽天・じゃらん）カバレッジが強いのが利点 |
| 4 | **自社PMS／サイトコントローラー** | 予約・実績・残室・取消・チャネル・LOS | API or CSV連携 | ✅ 自社データ |
| 5 | **公的統計**（奈良市観光協会 月報、奈良県宿泊統計、観光庁 宿泊旅行統計） | 市場OCC・延べ宿泊者数・国籍構成 | 公開データ取得 | ✅ 公開統計 |
| 6 | **イベント・行事・天候** | 正倉院展、若草山焼き、修二会、紅葉、学会、連休、天気予報 | Web + **Claude API による構造化抽出** | ✅ 一次情報源の公開情報 |
| 7 | OTA個社サイトの直接スクレイピング | 競合レート | — | ⚠️ **非推奨**。多くのOTA利用規約が自動取得を禁止。1・3で代替する |

**法務ポジション（明文化して残すこと）**

- 日本の著作権法第47条の5は、情報解析目的での軽微利用に一定の余地を与えるが、**利用規約に基づく契約上の制約は著作権法とは別軸**で効力を持つ。「著作権法上OK」＝「規約上OK」ではない。
- したがって本提案は、**リスクを自社に取り込まず、商用API／SaaSのライセンス契約に外部化する**方針を採る。年間数十万円のライセンス費は、法務リスクと運用工数の保険料として妥当である。
- 取得したデータは**自社の意思決定にのみ使用**し、第三者への再配布・公開を行わない旨を社内規程に明記する。

### 6.3 競合セット（Comp Set）の科学的選定

「なんとなくあの宿がライバル」は属人性の温床である。**手続きで決める。**

**Step 1｜候補抽出（Places API）**
奈良公園・奈良市中心部 半径3km、宿泊施設カテゴリ、評点4.0以上、レビュー数30件以上。

**Step 2｜3軸スコアリング**

| 軸 | 指標 | 重み |
|---|---|---|
| 価格帯類似度 | 過去12ヶ月の日別価格の**相関係数**（水準ではなく動きの一致度） | 0.4 |
| 商品類似度 | 客室数規模、食事形態（2食付主体か）、Places属性、レビュー本文のLLM分類（「静けさ」「食事」「デザイン」「文化体験」の訴求軸） | 0.35 |
| 顧客重複度 | レビュアーの言語構成、レビュー投稿の季節性の一致 | 0.25 |

**Step 3｜階層化**
- **Primary Comp Set（4〜6施設）**：奪い合いが実在する。価格インデックスの分母。
- **Secondary（6〜10施設）**：市場需要の観測用。価格追随はしない。
- **Aspirational（2〜3施設）**：目指す価格帯。ADR天井の参照。

**Step 4｜四半期ごとの自動再評価**
相関が閾値を割った施設は自動的に降格候補としてRM会議に上程される。**Comp Set の見直しが「誰も言い出さないので放置される」事態を構造的に防ぐ。**

> 奈良公園周辺の高価格帯としては、紫翠 ラグジュアリーコレクションホテル 奈良、ふふ奈良、奈良ホテル、ANDO HOTEL 奈良若草山、料亭旅館系、町家一棟貸し高級業態などが候補群に入ると想定されるが、**確定は Step 1〜3 の機械的手続きに委ねる**。

## 8. L2：需要予測エンジン

### 8.1 モデル定式化

宿泊需要を**非定常ポアソン到着過程**として定義する。宿泊日 d、残日数 t、提示価格 p に対する予約到着率：

```
λ(d, t, p) = λ_base(d) × g(t) × (p / p_ref(d))^(−ε_seg)
```

| 項 | 意味 | 推定方法 |
|---|---|---|
| `λ_base(d)` | 宿泊日 d 固有の需要水準 | 階層ベイズ。曜日・季節・イベント・市場OCC・競合売り切れ率を説明変数とする |
| `g(t)` | 予約リードタイム分布（ブッキングカーブ） | チャネル別に推定（一休/直販は短く、Booking.com/Agoda は長い） |
| `ε_seg` | セグメント別 価格弾力性 | 事前分布 `ε ~ LogNormal(log 1.8, 0.4)`（高価格帯宿の業界レンジ 1.2〜2.5）から出発し、価格実験（§13.3）で更新 |
| `p_ref(d)` | 参照価格 | Primary Comp Set の中央値。**「高いか安いか」は絶対額ではなく市場相対で決まる** |

### 8.2 階層構造（スパース性への解）

```
市場レベル（奈良・高価格帯全体）      θ_market ~ Normal(μ, τ²)
      ↓ partial pooling
施設レベル（鹿のや）                 θ_kanoya ~ Normal(θ_market, σ²)
      ↓
日付レベル（2026-11-03 等）          θ_d      ~ Normal(θ_kanoya + X_d·β, ω²)
```

**この構造の利点：** 鹿のやの実績が薄い日付では推定が市場平均に自動的に引き寄せられ（shrinkage）、実績が厚い日付では自施設の特性を信じる。**「データが足りないときにどうするか」を人間が悩まなくて済む。** これがスパースデータ環境で階層ベイズを選ぶ理由である。

### 8.3 競合の販売ペースを先行指標として使う

自社の5室だけでは需要が見えない。しかし Primary Comp Set 6施設 × 平均40室 = 240室分の消化速度は見える。

```
market_pressure(d, t) = Σ_i w_i × [ 競合iの sold_out フラグ or 価格上昇率 ]
```

**「60日前に競合3施設が売り切れている日」は、統計的に強い需要日である。** 自社の予約がまだ0件でも、この日は強気に出るべきだと機械が判断できる。**人間のRMが「肌感」と呼んでいるものの正体は、多くの場合これである。**

### 8.4 予測出力

| 出力 | 用途 |
|---|---|
| 日別 予測OCC（点推定＋80%信用区間） | ダッシュボード、ペース警告 |
| 日別 λ(p) 曲線 | 最適化エンジンへの入力 |
| 予測ADR / RevPAR | 月次forecast、予算管理 |
| **予測の不確実性幅** | 幅が広い日は価格変更を保守的に（不確実なときは動かさない） |

## 9. L3：最適化エンジン — Bid Price 動的計画法

### 9.1 問題設定

宿泊日 d について、残室数 r、残日数 t の状態における最適期待収益 `V(t, r)` を後ろ向きに解く。

```
V(0, r) = 0                                              （宿泊日到来、残室の価値は0）

V(t, r) = max_p  { λ(d,t,p)·[ p + V(t−1, r−1) ] + (1 − λ(d,t,p))·V(t−1, r) }

制約:  p ∈ [floor(d), ceiling(d)]   ← ガードレール（§10）
       V(t, 0) = 0                  ← 満室
```

**Bid Price（限界機会費用）：**

```
b(t, r) = V(t, r) − V(t, r−1)
```

これは「**残り r 室・残り t 日のとき、1室を今売ることで失う将来価値**」である。
**b(t,r) を下回る価格の予約は、受けてはいけない。** 団体・長期・OTA割引・直前セールの可否判断は、すべてこの1つの数値で機械的に決まる。

### 9.2 なぜこれが「属人性排除」の切り札なのか

現場でRMが最も間違えるのが、まさにこの判断である。

- 「30日前でまだ2室空いている。¥45,000のリクエストが来た。受けるべきか？」
- 人間は「不安だから受ける」か「もったいないから断る」を**気分で**決めている。
- DPは「その日の b(30, 2) は ¥52,300 だから断るべき（期待値ベースで¥7,300の損）」と即答する。

**5室規模だからこそ、この計算が厳密に、瞬時に解ける。** 状態数 6×366=2,196、365日分でも全体で80万状態。ノートPCで数秒である。

### 9.3 LOS（連泊）制御

奈良は「1泊で通過される」土地である。**連泊化はADRを下げずにOCCを上げる最良のレバー**であり、清掃コストも下がる。

```
2泊受注の可否判定:
  2泊の合計収益 ≥ b(t, r) + b(t', r')        ← 各日の機会費用の和
  かつ 2泊目の f_demand が低い日 → 割引を許容（Fenced Discount）

制御手段:
  MinLOS（最低宿泊数）  … 高需要日の前後で1泊予約をブロック
  CTA（Closed To Arrival） … その日の到着を締める（連泊の中日として使う）
  CTD（Closed To Departure）
```

例：土曜が高需要で金曜が弱い → 土曜に MinLOS=2 を設定し、金土の2泊を作りに行く。**この判断も b(t,r) の比較で自動化できる。**

### 9.4 TRevPAR最適化（オーベルジュ固有の論点）

鹿のやはレストラン・バーを持つ。**客室単体のRevPAR最大化は誤った最適化**である。

```
最適化目的 = Σ [ 客室収益 + F&B粗利 − 変動費（食材・清掃・OTA手数料） ]
             ─────────────────────────────────────────────
                        販売可能室数

判断例:
  素泊まりプラン ¥45,000（粗利 ¥40,000）
  vs 2食付プラン ¥62,000（食材原価 ¥9,000 → 粗利 ¥53,000）
  → 2食付が優位。ADRだけ見ると当然だが、
     OTA手数料率がプランで異なる場合、Net で逆転しうる
```

したがってすべての価格判断は **Net Contribution（手数料・原価控除後の貢献利益）** ベースで行う。ダッシュボードの主KPIを「ADR」ではなく「**Net TRevPAR**」に置くこと。これは多くの宿が見落としている論点であり、単価の高いオーベルジュほど効く。


### 10.2 Override（手動介入）の統制設計

**Overrideは禁止しない。禁止すると現場が壊れる。代わりに「測る」。**

| 統制 | 内容 | 狙い |
|---|---|---|
| 理由コード必須 | `VIP_GROUP` / `COMP_ERROR` / `EVENT_MISS` / `MAINTENANCE` / `OWNER_REQUEST` … | 「なんとなく」を不可能にする |
| 期限必須（最大14日） | 期限切れで自動的にシステム価格へ復帰 | **無期限Overrideによる形骸化を防ぐ**（RMツールが死ぬ最大の原因） |
| 全件ログ | §7.1 ④ に記録 | 監査可能性 |
| 月次スコアボード | Override日の実績 vs システム価格を維持した場合の反実仮想推定 | **人と機械のどちらが正しかったかを毎月可視化** |
| 学習ループ | 特定の理由コードのOverrideが繰り返し的中 → **その判断をルール化してモデルに組み込む** | 属人的な暗黙知を、システムの明示知へ昇格させる |

> **最後の行が本提案の思想を最もよく表している。**
> 優秀なRMの勘は捨てるものではなく、**回収して仕様書にするもの**である。RM-OSは「人を置き換える装置」ではなく「**人の判断を資産化する装置**」である。

### 10.3 説明文の自動生成

毎日の価格決定に、人間可読の1行説明を自動付与する（Claude API 等で生成）。

```
2026-11-03（火・文化の日）  ¥98,000  (前日比 +8.0%)
  └ 正倉院展会期 × 紅葉ピーク（f_event 1.22）
    Comp Set 中央値 ¥86,000 に対し RGI 1.14（方針 1.15 に整合）
    残2室・残21日 → Bid Price ¥91,400 を上回るため受注可
    競合6施設中3施設が既に満室（market_pressure 高）
```

**これがあることで、システムは「信用できる同僚」になる。** ブラックボックスは現場に使われず、必ず形骸化する。

## 12. OTA・チャネル戦略

### 12.1 チャネル・ポートフォリオ設計

**5室のOTA戦略は「多く出す」ではなく「正しく選ぶ」。** 5室に10チャネルを繋ぐと、在庫の奪い合いと運用負荷でNet収益が落ちる。

| チャネル | 役割 | 想定手数料 | 目標構成比 `[要差替]` |
|---|---|---|---|
| **自社直販**（公式サイト予約エンジン） | 最重要。Net最大 | 決済手数料のみ（3〜4%） | **40%** |
| **一休.com** | 国内高価格帯の主戦場。奈良の高付加価値層と親和 | 8〜10% | 20% |
| **Relux / 特選旅館系** | ブランド訴求・新規認知 | 10〜15% | 8% |
| **楽天トラベル / じゃらん** | 国内リーチ、ポイント需要 | 8〜12% | 10% |
| **Booking.com / Agoda / Expedia** | インバウンド（奈良公園立地は必須） | 15〜18% | 20% |
| **Trip.com** | 中華圏 | 15%前後 | 2% |

**判断原理：チャネルは「粗利率」ではなく「増分貢献」で評価する。**
Booking.com の手数料15%は高いが、**そのチャネルがなければ埋まらなかった室夜**なら、Net貢献はプラスである。逆に、直販で取れたはずの客がOTA経由に流れているなら（＝カニバリ）、手数料は純損失である。

→ **チャネル別の「増分性」を測る指標**として、チャネルを一時停止した際のOCC変化を年1回、低需要期に測定する（チャネル・ホールドアウト実験）。感覚論争を終わらせる唯一の方法である。

### 12.2 直販比率を上げる具体策

| 施策 | 内容 | 効果 |
|---|---|---|
| **Google ホテル 無料予約リンク（Free Booking Links）** | Googleのホテル検索に自社サイト料金を無料掲載。サイトコントローラー経由で連携可能 | **手数料ゼロで直販導線。5室規模でも費用対効果が極めて高い最優先施策** |
| Google ホテル広告（成果報酬型） | Commission per Stay 型なら固定費リスクなし | OTAより低い実効手数料で直販獲得 |
| 直販限定特典 | 価格を下げず**価値**で差をつける（アーリーチェックイン、館内バー1ドリンク、大和茶のウェルカム、部屋指定） | パリティ問題を回避しつつ直販優位を作る |
| メタサーチでの価格整合 | 自社が最安（または同額＋特典）で表示される状態を常時監視 | 「OTAで見た方が安い」を撲滅 |
| リピーター／CRM | 宿泊後のフォロー、記念日データ保持、非公開先行案内 | LTV最大化。5室規模ならCRMは個別対応が可能＝大手より強い |

> **5室の宿にとって、100人のリピーターは経営を変える。** 1,825室夜のうち、年1泊するリピーターが200人いれば11%が固定需要になる。**RM-OSの最終形は、CRMと統合された「顧客別・機会費用ベースの価格提示」である。**

### 12.3 レートパリティの扱い

日本では公正取引委員会の調査を経て**広域レートパリティ条項は是正が進んでおり、直販を優位に置く余地がある**。ただしOTAとの個別契約条件が優先するため、
1. 各OTAとの契約書のパリティ条項を棚卸しし、
2. PPD の `channel_policy` に「契約上許容される直販優位の範囲」を明記し、
3. システムはその範囲内でのみ自動配信する。

**契約リスクをシステムのルールに落とし込む**ことで、担当者が知らずに違反する事態を防ぐ。

## 13. L6：KPI・検証・学習ループ

### 13.1 KPIツリー

```
Net TRevPAR（最上位KPI）
├── 客室 Net RevPAR
│   ├── ADR
│   │   ├── Package ADR / Room-only ADR
│   │   ├── ARI（ADR Index）= 自社ADR ÷ Comp Set ADR
│   │   └── チャネル別 Net ADR（手数料控除後）
│   ├── OCC
│   │   ├── MPI（Market Penetration Index）= 自社OCC ÷ Comp Set OCC
│   │   ├── ブッキングペース（vs STLY, vs Forecast）
│   │   └── LOS Mix（1泊比率 / 2泊以上比率）
│   └── RGI（RevPAR Index）= ARI × MPI  ← 総合的な市場競争力
├── F&B 収益（レストラン・バー）
│   └── Capture Rate（宿泊客の館内利用率）、Spend per Guest
└── 流通コスト
    ├── 手数料率（加重平均）
    └── 直販比率
```

### 13.2 システム自体の健全性KPI（これが属人性排除の測定装置）

| 指標 | 目標 | 意味 |
|---|---|---|
| 予測MAPE（30日前時点のOCC予測誤差） | < 12% | モデルが信用できるか |
| **Override率** | < 15%（Phase 3） | **人が介入しないと回らない＝属人性が残っている** |
| **Override勝率** | 参考値 | 人の介入が実際に収益を改善したか |
| データ収集成功率 | > 98% | 収集基盤の安定性 |
| 配信成功率（read-after-write一致） | > 99.5% | 配信の安全性 |
| 価格変更頻度 | 適正レンジ内 | 過剰変動はブランド毀損 |

> **Override率は本システムの成功指標そのものである。** これが下がり続けるなら、暗黙知が順調にシステムへ移管されている。下がらないなら、モデルかポリシーに欠落がある。**「使わなくなった」ではなく「使う必要がなくなった」を目指す。**

### 13.3 価格実験（Thompson Sampling）

弾力性 ε はデータからしか分からないが、待っていても分からない。**能動的に探る。**

- 需要が中庸で、リスクの低い日（例：ショルダーシーズンの平日）を対象に、
- 価格を事後分布からサンプリングして提示（Thompson Sampling）、
- 結果（成約 / 不成約）で ε の事後分布を更新する。

**探索は「損」ではなく「情報の購入」である。** 年間で数十室夜を実験に割り当てることで、残り1,700室夜の価格精度が上がる。**ただし PPD のガードレール内でのみ実施**し、ブランド毀損価格は決して出さない。

### 13.4 月次RMレビュー会議のアジェンダ（テンプレート化）

会議も属人化させない。**アジェンダを固定し、資料はシステムが自動生成する。**

1. 前月実績 vs 予算 vs Forecast（RevPAR / Net TRevPAR / RGI）
2. Comp Set に対する ARI・MPI・RGI の推移
3. 今後90日のペース（vs STLY、赤信号日のリスト）
4. **Override スコアボード**（人 vs システム）
5. 予測精度（MAPE）とモデル異常
6. 価格実験の結果と ε の更新
7. **PPDパラメータの変更提案と承認**（← 会議で決めるのはここだけ）
8. Comp Set 見直し（四半期）

**「今日いくらにする？」を会議で議論しないこと。** それは会議の議題ではなく、システムの出力である。

## 付録A：価格算定ロジック 擬似コード

```python
def decide_price(stay_date, room_type, as_of) -> PriceDecision:
    # ---- 1. 入力 ----
    policy   = load_policy()                      # pricing_policy.yaml（承認済み）
    demand   = forecast.get(stay_date, as_of)     # λ曲線, 予測OCC, 信用区間
    comps    = comp_rates.median(stay_date, as_of, tier="primary")
    pace     = pickup.vs_stly(stay_date, as_of)
    state    = inventory.state(stay_date, as_of)  # 残室 r, 残日数 t

    # ---- 2. 乗算モデルで素点を作る（説明可能性の確保）----
    base   = policy.base_price[room_type][season_of(stay_date)][dow_of(stay_date)]
    f_dem  = clip(1 + 0.6 * (demand.occ_forecast - 0.70), 0.85, 1.35)
    f_comp = clip((comps * policy.positioning.target_rgi) / base, 0.85, 1.30)
    f_pace = clip(1 + 0.4 * pace.delta_ratio, 0.88, 1.25)
    f_evt  = events.factor(stay_date)             # イベント係数（1.0〜1.4）

    raw = base * f_dem * f_comp * f_pace * f_evt

    # ---- 3. ガードレール（PPDの強制執行）----
    p = clip(raw, policy.floor(stay_date), policy.ceiling)
    p = limit_daily_change(p, previous_price(stay_date), policy.max_daily_change_pct)
    if days_out(stay_date, as_of) <= 7:
        p = limit_daily_change(p, previous_price(stay_date),
                               policy.max_change_within_7days_of_stay)
    if policy.never_be_cheapest:
        p = max(p, comps_min(stay_date) + 1000)

    # ---- 4. 機会費用チェック（Bid Price DP）----
    bid = bid_price_dp(stay_date, r=state.rooms_left, t=state.days_out, demand=demand)
    if p < bid:
        p = bid                                   # 機会費用を下回る価格は出さない

    # ---- 5. 不確実性が高い日は動かさない ----
    if demand.ci_width > policy.uncertainty_threshold:
        p = blend(p, previous_price(stay_date), w=0.5)

    # ---- 6. LOS制御 ----
    min_los = 2 if demand.occ_forecast > policy.los_policy.min_los_trigger_occ_forecast else 1

    # ---- 7. 説明文生成 & 監査ログ ----
    explanation = llm_explain(base, f_dem, f_comp, f_pace, f_evt, bid, comps, p)
    audit_log.write(...)

    return PriceDecision(price=p, min_los=min_los, explanation=explanation)
```

## 付録B：Bid Price DP 実装スケッチ

```python
import numpy as np

def bid_price_dp(stay_date, r_max, t_max, lambda_fn, price_grid):
    """
    V[t][r] : 残日数t・残室r における最適期待収益
    5室×366日 → 状態数 2,196。厳密解が即座に求まる。
    """
    V = np.zeros((t_max + 1, r_max + 1))

    for t in range(1, t_max + 1):
        for r in range(1, r_max + 1):
            best = -np.inf
            for p in price_grid:                       # ガードレール内の価格候補
                lam = lambda_fn(stay_date, t, p)       # 1期間あたり到着確率
                lam = min(lam, 1.0)
                ev = lam * (p + V[t-1][r-1]) + (1 - lam) * V[t-1][r]
                best = max(best, ev)
            V[t][r] = best
        V[t][0] = 0.0                                  # 満室：以降の収益なし

    # bid price = 1室を今売ることで失う将来価値
    bid = lambda t, r: V[t][r] - V[t][r-1] if r >= 1 else np.inf
    return V, bid
```

**この関数が返す `bid(t, r)` が、鹿のやのすべての受注判断の基準線になる。**
団体照会、旅行会社のアロットメント、直前の値引き要請、連泊割引 —— すべて「bid を上回るか」で機械的に答えが出る。**属人的な「まあいいか」を、数値が置き換える。**

## 20. 総括

鹿のやのレベニューマネジメントを「担当者の力量」から解放するために必要なのは、高度なAIではない。必要なのは次の4つである。

1. **毎日、同じ方法で、競合と市場を観測し続ける仕組み**（L0-L1）
   — 「見た人しか知らない」を消す
2. **5室という制約を、機会費用の厳密計算という優位に転換する数理**（L2-L3）
   — 「暗算できない判断」を機械に渡す
3. **経営方針を文書化し、それをシステムが強制執行する統治構造**（L4）
   — 「勘」を「承認された方針」に昇格させる
4. **人の介入を測り、当たった勘をルールへ回収し続けるループ**（L6）
   — 「経験」を「資産」に変換する

このうち **3が本質であり、1・2・4はその実装手段にすぎない。**
システムを作る前に、**「鹿のやは、どういう価格で、誰に、どう売る宿なのか」を1枚の文書に落とすこと。** そこから始めれば、レベニューマネジメントは属人技能ではなく、経営の再現可能な機能になる。
