## 3-2. データ待ちで止まっているもの

**この2つが無いと、エンジンは本番配信に使えない。** コードの問題ではなく、
入力が無いので答えが出せない。

### P13. 商品形態別の貢献利益フロア

**要るもの：変動費の内訳（出所は社内）**

- 食材原価（夕食・朝食それぞれ、1名1食あたり）
- リネン・清掃・アメニティ（1室1泊あたりの概算）
- OTA各社の実手数料率（契約書の値。掲出率ではなく実際に引かれる率）

**無いとどうなるか**

「いくらまで下げてよいか」が答えられない。現在は**暫定フロア**で動いている。

```
2食付き 58,000円（確定値）
素泊まり 14,000円 ← 58,000 − 食事の売価 44,000 の引き算にすぎない
```

食事に乗っている利益を戻していないため、**貢献利益フロアとしては過小**。
起動時に警告が出るようにしてあり、出力にも `【暫定フロア適用】` と表示される。
**仮値のまま本番配信に使わないこと。**

`scripts/` に「変動費を入力すれば4形態のフロアが出る」計算スクリプトを
用意する形にする（数値の確定は人に残す）。

### P16. コンペセットの再ティア化

**要るもの：競合の実勢価格（出所は SerpApi・月$25〜75）**

**無いとどうなるか**

現在の競合レート（`comp_rates_collected.csv`）は**すべてフィクスチャ**である。
したがって

- 市場ポジションの数値（「競合NAR中央値の1.10倍」など）は意味を持たない
- `z_comp` は実データ検証では0にしてある
- 自社の価格が市場に対して高いのか安いのかは判定不能

P16 自体はティアの重み付けに「商品形態の整合」を足す話だが、その前に
**実勢価格の取得が要る**。順序としては 実勢価格の接続 → P16。

契約プランの見積もりは P6改 で扱う（リード60日に縮めれば Starter 月$25 で
収まる可能性がある。リード60日前時点のOTB充足率は1.4%しかない）。
