# 別冊03｜価格決定エンジン仕様

**— 「誰がやっても同じ答えが出る」ADR算定ロジック —**

---

## 1. 設計思想（3原則）

| 原則 | 内容 | 理由 |
|---|---|---|
| **① 説明可能性を精度に優先する** | ブラックボックスの機械学習ではなく、**乗数分解型のルールモデル**を採用する。すべての推奨価格は「基準価格 × 要因A × 要因B × …」に分解して提示する | 経営者が根拠を検証できなければ、システムは信頼されず使われない。使われないシステムは属人性を排除しない |
| **② 純ADR（手数料控除後）で最適化する** | 表示ADRではなく `ADR × (1 − チャネル実効手数料率)` を目的関数に置く | 手数料8%と20%のチャネルを同じ土俵で比較しないRMは、利益を毀損しながら売上を伸ばす |
| **③ 小標本を前提に「縮小推定」する** | 5室＝データが少ない。データが薄い日は**推奨価格を基準価格側に引き戻す**（shrinkage） | 少ないサンプルの外れ値に振り回されて価格が乱高下することを構造的に防ぐ |

## 2. 変数定義

| 記号 | 定義 |
|---|---|
| `d` | 対象宿泊日（stay date） |
| `t` | 意思決定日 |
| `τ = d − t` | リードタイム（日数） |
| `N = 5` | 総客室数 |
| `OTB(d,t)` | 当該時点の予約済室数（on-the-books） |
| `R(d,t) = N − OTB(d,t)` | 残室数 |
| `seg(d)` | 日区分（平日／週末／連休／イベント／最繁忙） |
| `BAR_base(seg)` | 基準料金（Best Available Rate の基礎値。季節×曜日で定義） |
| `P_comp(d,t)` | コンプセットの正規化価格中央値（2名1室・朝食別・税込） |
| `SO(d,t)` | コンプセット完売率＝完売施設数 ÷ 観測施設数 |
| `E(d)` | イベントスコア（0以上） |
| `Pace(d,t)` | ペース指数（後述） |
| `fee_c` | チャネル `c` の実効手数料率 |
| `Floor, Ceil` | ポリシーで定めた下限・上限 |

## 3. 需要予測：Market-first Forecasting

### 3-1. なぜ自社データから予測しないのか

5室では、ある日の予約は 0〜5件しかない。過去3年でも1日あたり最大15サンプル。これで日次需要を統計的に推定することは不可能である。

そこで、**「市場全体の需要 → 自社の相対競争力 → 自社の需要」**という順で推定する。

```
  Step 1  市場需要水準 M(d) を推定
          ← 奈良市宿泊統計（季節性）＋ イベント ＋ 曜日 ＋ 祝日 ＋ インバウンド動向
  Step 2  当日の市場逼迫度 T(d,t) を観測
          ← コンプセット完売率 SO ＋ コンプセット価格の上昇率 ΔP_comp
  Step 3  自社の相対ポジション S(d,t) を観測
          ← 自社ペース指数 Pace ＋ 価格順位
  Step 4  需要圧力指数 DPI(d,t) を合成 → 価格に変換
```

### 3-2. 需要圧力指数（Demand Pressure Index, DPI）

```
DPI(d,t) = w_so  · z(SO(d,t))
         + w_dp  · z(ΔP_comp(d,t))      # コンプセット価格の直近7日変化率
         + w_pace· z(Pace(d,t))
         + w_ev  · E(d)
         + w_mkt · z(M(d))              # 市場季節性（前年同週比）
```

- `z(·)` は同一 `seg` 内での標準化（ロバストz：中央値とMADを使用）
- 重み `w` の初期値：`w_so=0.30, w_dp=0.15, w_pace=0.30, w_ev=0.15, w_mkt=0.10`
- **重みは四半期ごとに実績で見直す**（3-4章の検証結果に基づく）

### 3-3. ペース指数

過去実績から、`seg` 別の**ブッキングカーブ** `B_seg(τ)`（最終予約数に対する τ 日前時点の累積比率）を作る。5室では単日のカーブが安定しないため、**同一 seg の日をプールして推定**する。

```
Pace(d,t) = OTB(d,t) / ( ExpectedFinal(d) × B_seg(τ) )
```

- `Pace > 1` … 前年同条件より速い＝**値上げ余地**
- `Pace < 1` … 遅い＝要因（価格が高い／市場が弱い／露出不足）を切り分け
- 分母が小さい超長期（τ>180）では不安定なため、`τ ≤ 180` でのみ有効とし、それ以前は `Pace = 1` 固定

### 3-4. 予測の不確実性と縮小推定（Shrinkage）

```
σ(d,t) = 不確実性スコア
        ↑ コンプセット観測数が少ない / データ鮮度が古い / τが長い / イベント係数が未検証
        
κ(d,t) = 1 / (1 + λ·σ(d,t))          # 0 < κ ≤ 1、λ は感度パラメータ

ADR_final = BAR_base + κ · (ADR_raw − BAR_base)
```

**意味**：情報が乏しいほど、推奨価格は基準価格に近づく。これにより「データが1件しか取れなかった日に、その1件に引きずられて価格が暴れる」事故を構造的に防ぐ。**5室運営における最重要の安全装置である。**

## 4. 価格算定式（乗数分解モデル）

```
ADR_raw(d,t) = BAR_base(seg(d))
             × f_pace(Pace)
             × f_comp(P_comp, ARI*)
             × f_event(E)
             × f_inv(R, τ)
             × f_lead(τ, Pace)
```

### 4-1. 各係数の定義

#### f_pace（ペース係数）— 予約の入り具合

```
f_pace = clip( 1 + α_pace · (Pace − 1),  0.88,  1.35 )      # α_pace 初期値 0.45
```

#### f_comp（競合係数）— 市場価格への追随

**追随率 β で部分的に追随する**。100%追随すると値下げ競争の増幅器になるため、必ず 1 未満とする。

```
ADR_comp_target = P_comp × (ARI* / 100)          # ARI* = 目標単価指数（鹿のや初期値 115）
f_comp = clip( 1 + β · ( ADR_comp_target / BAR_base − 1 ),  0.90,  1.25 )   # β 初期値 0.50
```

> **鹿のやの ARI\* を 115 に置く根拠**：奈良公園内・春日大社隣接という代替不可能な立地、全5室の希少性、オーベルジュ形態。市場並み（100）に置くのは資産価値の過小評価である。

#### f_event（イベント係数）

```
f_event = clip( 1 + Σ_e lift_e · relevance_e,  1.00,  1.60 )
```

- `lift_e`：行事ごとのリフト率（初期値は仮置き、実績で毎年自動更新）
- `relevance_e`：施設との距離・客層適合度（若草山焼きは徒歩1分＝relevance 1.0）

**初期値の例（Phase 0 で実績検証のうえ確定）**

| 行事 | lift 初期値 |
|---|---|
| 正倉院展 会期中の週末 | +25% |
| 若草山焼き 当日 | +40% |
| お水取り 3/12（籠松明） | +30% |
| 紅葉ピーク（11月中〜下旬の週末） | +30% |
| 桜ピーク（3月末〜4月上旬） | +25% |
| 春日大社 万燈籠 | +15% |
| なら燈花会 期間中 | +15% |

#### f_inv（在庫希少性係数）— 5室特有の設計

残室が減るほど値上げする。ただし**ペースが遅れている日には発動させない**（＝売れていないのに値上げする事故を防ぐ）。

| 残室 R | 係数 | 発動条件 |
|---|---|---|
| 5 | 1.00 | — |
| 4 | 1.03 | Pace ≥ 0.9 |
| 3 | 1.08 | Pace ≥ 0.9 |
| 2 | 1.16 | Pace ≥ 0.9 |
| 1 | 1.28 | Pace ≥ 0.9 |

> 5室では1室の販売が在庫の20%を消費する。**最後の1室は「翌年の基準価格を教えてくれる観測装置」**でもある。高値で売れれば来期の BAR_base を上げる根拠になる。

#### f_lead（リードタイム係数）と「値下げ禁止則」

ラグジュアリー小規模宿における最大の構造的リスクは、**直前値下げによるブッキングカーブの後ろ倒し**である。一度「待てば安くなる」と学習されると、翌年以降のADRが恒久的に下がる。

```
値下げ禁止則（Rate Integrity Rule）:
  IF τ ≤ 14:
      値下げは原則禁止。
      例外的に許容する条件（すべて満たす場合のみ）:
        - R ≥ 3（残室が多い）
        - Pace < 0.7（明確に遅れている）
        - 値下げ幅 ≤ 8%
        - 実施は当該日につき1回限り
        - Floor を下回らない
      それでも埋めたい場合は「価格」ではなく「価値」で埋める:
        → 直販限定の付加価値（館内クレジット / レイトアウト / 貸切利用）
        → 会員・既存顧客への クローズド配信
```

`f_lead` 自体は τ>60 で 1.00 とし、短期での過度な変動を抑制する係数として作用させる。

## 5. ガードレール（暴走防止の二重装置）

推奨価格は必ず以下の順で加工されてから配信される。

```
1. clip(ADR_raw, Floor, Ceil)                     # 絶対上下限
2. shrinkage 適用（κ）                             # 不確実性による引き戻し
3. 日次変動幅の制限: |ΔADR| ≤ max_daily_change     # 初期値 15%
4. 価格ラダーへの丸め: round_to_ladder(...)        # 心理価格・1,000円刻み等
5. サニティチェック                                 # 下記
6. 自動配信 or 承認キューへ
```

### 5-1. Floor（下限）の設計

```
Floor = max( 変動費フロア, ブランドフロア )

変動費フロア = (客室変動費 + F&B原価 + 清掃/リネン + アメニティ) / (1 − fee_c)
ブランドフロア = 経営が定める「この価格では売らない」ライン
```

**ラグジュアリーでは、ほぼ常にブランドフロアが上回る。** 変動費だけで下限を決めると、埋めるために価格を壊す。**フロアを守ることこそが、5室の宿にとって最大のRM施策**である。

### 5-2. サニティチェック（配信直前の最終防衛線）

| チェック | 条件 | 違反時 |
|---|---|---|
| 上下限 | Floor ≤ price ≤ Ceil | 配信中止・アラート |
| 変動幅 | 前日比 |Δ| ≤ 15% | 承認キューへ |
| データ鮮度 | コンプセットデータが48時間以内 | 自動配信停止（手動モードへ縮退） |
| コンプセット網羅 | 一次コンプセットの60%以上を観測 | 承認キューへ |
| 桁ミス検知 | 前日比 ±50% 超 | 即時ブロック＋人へエスカレーション |
| **Kill Switch** | 手動フラグ | 全自動配信を即時停止し現行価格を維持 |

## 6. 在庫制限（LOS制御）と滞在日数最適化

価格だけでは最適化できない。**「いつ、何泊から受けるか」**が5室では極めて効く。

### 6-1. MinLOS（最低宿泊日数）の自動発動

```
IF 予測需要率 D(d)/N ≥ 1.4                       # その日は需要過多
AND 隣接日の予測需要率 ≤ 0.8                      # 前後は空きそう
AND τ ≥ 21                                       # 直前ではない
THEN MinLOS(d) = 2
```

**根拠**：需要過多の日に1泊客を入れると、前後日の空室が固定化する。2泊必須とすることで前後日を同時に埋め、**2日間合計の純RevPARを最大化**する。5室では1件の判断が全体の20%を動かすため、この効果は大規模ホテルより大きい。

### 6-2. CTA / CTD（到着・出発の締切）

| 制限 | 用途 |
|---|---|
| **CTA**（Closed to Arrival） | 満室日の翌日に到着させたくない場合など、滞在パターンの整流化 |
| **CTD**（Closed to Departure） | 高需要日の朝に出発する予約を抑え、当該日の在庫を確保 |

### 6-3. 逸失分析（Displacement Analysis）

```
2泊予約（受入時の純収益 = 純ADR(d1) + 純ADR(d2)）
 vs
1泊予約×2件の期待値（= 純ADR(d1) + P(d2が別途売れる) × 純ADR(d2)）
```

エンジンはこの比較を自動で行い、MinLOS の是非を判断する。**人の直感では最も間違えやすい領域**であり、システム化の価値が最も高い。

## 7. チャネル別・純ADR最適化

### 7-1. 純ADR換算

| チャネル | 実効手数料（目安） | 表示100,000円の純ADR | 直販換算係数 |
|---|---|---|---|
| 公式サイト（直販） | 決済手数料 約3.5% | 96,500円 | 1.00 |
| 一休.com / 楽天トラベル | 8〜12%程度 | 88,000〜92,000円 | 1.05〜1.10 |
| じゃらんnet | 8〜10%程度（ポイント原資含む） | 90,000〜92,000円 | 1.05〜1.07 |
| Booking.com | 15%〜（露出強化で20%超も） | 80,000〜85,000円 | 1.14〜1.21 |
| Expedia | 18%〜（掲載順位施策で更に上昇） | 75,000〜82,000円 | 1.18〜1.29 |

> ※実効手数料は契約・販促プログラム参加状況で大きく変わるため、**Phase 0 で自社の実測値を確定させる**こと。

### 7-2. エンジンへの実装

1. すべての意思決定は **純ADR** で評価する
2. **在庫が逼迫した日ほど、高手数料チャネルを絞る**（クローズ or 上位料金のみ提供）

```
IF DPI(d,t) ≥ high_demand_threshold:
    高手数料チャネル（実効15%超）は BAR + 上乗せ率 のみ提供、または在庫を絞る
    直販・低手数料チャネルは通常価格で維持
    → 同じ稼働率でも純RevPARが向上する
```

3. 低需要日は逆に全チャネルを開放し、**露出＝在庫の掃き出し**に使う（ただし Floor 厳守）

### 7-3. 直販シフトの設計

価格差ではなく**特典差**で誘導する（法務論点は別冊02 L6参照）。

| 施策 | 内容 | 期待効果 |
|---|---|---|
| Google 無料予約リンク掲出 | Hotel Center 経由で公式価格をGoogleに掲出（掲載無償） | OTA経由の一部を直販へ。**費用対効果が最も高い施策のひとつ** |
| 会員限定価格 | クローズドユーザーグループ | パリティ条項の影響を受けにくい |
| 直販限定の付加価値 | 館内クレジット、レイトチェックアウト、貸切利用の優先枠 | 実質的な価格差を、価格を下げずに作る |
| 滞在後のリピート導線 | チェックアウト時の次回予約特典（直販限定） | 獲得コストゼロの再販 |

**目標**：直販比率 25% → 40%。ADR 8万円・年1,278泊で試算すると、**15ptの直販シフトは年間約120万円の手数料削減**に相当する（手数料差10ptの場合）。

## 8. 例外承認ワークフロー（Human-in-the-Loop）

```
推奨価格の算出
   ├─ 変動 ≤ ±10%  かつ 全サニティチェック合格 → 自動配信（通知のみ）
   ├─ 変動 > ±10%  または 網羅率不足           → 承認カードを Slack/LINE へ
   └─ サニティチェック違反                      → 配信中止・エスカレーション
```

### 承認カードの必須項目（これが「経験の代替」になる）

1. 対象日・日区分・イベント有無
2. 現在価格 → 推奨価格（変動率）
3. **要因分解**（どの係数が何%寄与したか）
4. コンプセットの状況（各社価格・完売状況）
5. 自社の残室とペース
6. 想定される純RevPARへの影響
7. 選択肢：`承認` / `据置` / `金額指定`

> **重要**：据置・金額指定を選んだ場合、**理由の選択を必須にする**（選択式で可）。この蓄積が、翌四半期のパラメータ改定の一次データになる。人の介入自体を「学習データ」に変える設計であり、**属人的な勘を組織の資産に転換する仕組み**である。

## 9. 効果検証：ホールドアウト日法

「導入したら売上が上がった」は市場全体の変動と区別できないため、証明にならない。以下2つを併用する。

### 9-1. ホールドアウト日（Randomized Holdout Dates）

毎月、**ランダムに全体の8〜10%の日付を「ポリシー凍結日」**に指定し、旧来の固定料金表で運用する。同一 seg 内で処置群（エンジン適用）と対照群（凍結）を比較し、純RevPAR差を測定する。

- 長所：市場変動の影響を受けない、因果的な効果測定が可能
- 留意：**最繁忙日は対照群に含めない**（機会損失が大きすぎる）。平日・中需要日に限定する

### 9-2. 市場調整済み差分（Difference-in-Differences）

```
効果 = (自社RevPAR前年比) − (コンプセットRevPAR前年比)
     ≒ RGI（収益指数）の改善幅
```

市場が下落した局面でも、**RGIが改善していれば施策は成功している**と判断できる。経営報告にはこの指標を用いる。

## 10. パラメータ自動更新（毎年の学び直し）

人の記憶に頼らないための機構。四半期ごとにバッチで実行する。

| 更新対象 | 更新方法 |
|---|---|
| イベント係数 `lift_e` | 実績の「完売までのリードタイム」「実現ADR」から逆算。早期完売した行事は係数を引き上げ |
| `BAR_base(seg)` | 前年実績の実現ADR分布と目標ARIから再設定 |
| ブッキングカーブ `B_seg(τ)` | 直近24ヶ月の予約明細で再推定 |
| DPI の重み `w` | ホールドアウト検証の結果に基づき調整 |
| 追随率 `β`、ペース感度 `α` | 同上 |

### 早期完売アラート（安売り検知）

```
IF 完売 AND τ ≥ 45:
    → 「その日は安すぎた」と判定
    → 翌年同条件日の BAR_base を +8〜15% 引き上げ候補としてRM委員会に上程
```

**この1本のルールだけで、ADRは構造的に上がっていく。** 人手の運用では、満室＝成功として見過ごされ続ける領域である。

## 11. 疑似コード

```python
def recommend_rate(d, t, policy, data) -> Recommendation:
    seg   = classify_segment(d, data.calendar, data.events)
    base  = policy.bar_base[seg]

    # --- 1) 観測 -------------------------------------------------
    comp  = normalize_competitor_rates(data.rate_observations(d, t))  # 2名1室/朝食別/税込
    otb   = data.on_the_books(d, t)
    R     = policy.total_rooms - otb
    tau   = (d - t).days
    pace  = otb / max(expected_final(d, data) * booking_curve(seg, tau), 1e-6)
    E     = event_score(d, data.events)

    # --- 2) 需要圧力 ---------------------------------------------
    dpi = (policy.w.so   * z(comp.sold_out_ratio, seg)
         + policy.w.dp   * z(comp.price_trend_7d, seg)
         + policy.w.pace * z(pace, seg)
         + policy.w.ev   * E
         + policy.w.mkt  * z(market_index(d, data), seg))

    # --- 3) 乗数分解 ---------------------------------------------
    f_pace  = clip(1 + policy.alpha_pace * (pace - 1), 0.88, 1.35)
    f_comp  = clip(1 + policy.beta * (comp.median * policy.ari_target/100 / base - 1), 0.90, 1.25)
    f_event = clip(1 + E, 1.00, 1.60)
    f_inv   = policy.inventory_ladder[R] if pace >= 0.9 else 1.0
    f_lead  = lead_factor(tau, pace, policy)

    raw = base * f_pace * f_comp * f_event * f_inv * f_lead

    # --- 4) 不確実性による縮小推定 -------------------------------
    sigma = uncertainty(comp.coverage, comp.freshness_hours, tau, E.confidence)
    kappa = 1.0 / (1.0 + policy.lam * sigma)
    price = base + kappa * (raw - base)

    # --- 5) ガードレール -----------------------------------------
    price = clip(price, floor_for(d, policy), policy.ceiling[seg])
    price = limit_change(price, data.current_rate(d), policy.max_daily_change)
    price = apply_rate_integrity_rule(price, data.current_rate(d), tau, R, pace, policy)
    price = round_to_ladder(price, policy.ladder)

    # --- 6) 在庫制限 ---------------------------------------------
    minlos = decide_minlos(d, data, policy)      # 逸失分析に基づく
    restr  = decide_cta_ctd(d, data, policy)

    # --- 7) 出力（必ず根拠を添える） -----------------------------
    return Recommendation(
        date=d, price=price, minlos=minlos, restrictions=restr,
        factors={"base": base, "pace": f_pace, "comp": f_comp,
                 "event": f_event, "inventory": f_inv, "lead": f_lead,
                 "shrinkage": kappa},
        evidence={"compset": comp.detail, "otb": otb, "pace": pace, "dpi": dpi},
        auto_publish=within_auto_band(price, data.current_rate(d), policy)
                     and sanity_checks_pass(...),
    )
```

**動作する実装は `poc/` を参照。** 合成データ上で90日分の推奨価格と要因分解を出力する。
