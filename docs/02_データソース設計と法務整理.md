# 別冊02｜データソース設計と法務整理

**— 近隣競合のOTA情報を「自動で・継続的に・合法に」収集する設計 —**

---

## 1. 必要データの全体像

RM の判断に必要なデータを4象限に整理する。**どれか1つが欠けても、価格判断は勘に戻る。**

```
                  外部 ─────────────────────────────► 内部
        ┌──────────────────────────┬──────────────────────────┐
   価格 │ ① 競合レート・在庫        │ ② 自社レート・在庫        │
   在庫 │  ・OTA別の販売価格        │  ・チャネル別公開価格      │
        │  ・残室有無 / 完売状況     │  ・残室 / ブロック         │
        │  ・プラン条件・キャンセル規定│  ・レートパリティ状態      │
        ├──────────────────────────┼──────────────────────────┤
   需要 │ ③ 市場需要シグナル        │ ④ 自社実績・ピックアップ   │
        │  ・宿泊統計 / 稼働率      │  ・On-the-books（予約残高） │
        │  ・イベント・行事         │  ・ピックアップ / ブッキングカーブ │
        │  ・インバウンド / 航空座席  │  ・リードタイム / LOS / 客層 │
        │  ・検索・関心量           │  ・キャンセル率 / F&B付帯率  │
        └──────────────────────────┴──────────────────────────┘
```

## 2. 競合レート取得の「調達方針」— 3段階の優先順位

**この順序を組織のルールとして固定すること。**「取れるから取る」を許すと、法務リスクと保守コストが青天井になる。

| 優先 | 手段 | 位置づけ | 承認 |
|---|---|---|---|
| **第1** | **公式API**（各OTA・Googleの公式提供） | 原則これのみで設計する | 不要（規約遵守） |
| **第2** | **ライセンス済み第三者データ**（レートショッパーSaaS、商用SERP API） | 第1で埋まらない領域を補完。**法的責任を提供事業者と分担できる**点が本質的価値 | 購買承認 |
| **第3** | **自社スクレイピング** | 最終手段。他に代替がない場合のみ | **法務承認＋技術要件遵守を必須** |

## 3. 具体的データソース一覧

### 3-1. ① 競合レート・在庫

| ソース | 取得できるもの | 手段 | 更新頻度 | 概算コスト | 法務リスク | 評価 |
|---|---|---|---|---|---|---|
| **楽天トラベル 空室検索API**（楽天ウェブサービス） | 施設番号・緯度経度・地区コードから、**実在庫のある部屋の料金・プラン名・定員・食事条件**をリアルタイム取得。全国2万軒超が対象 | 公式REST API（アプリID登録） | 日次〜複数回/日 | **無料**（利用規約に基づくレート制限あり） | **低** | ★★★ **日本市場の主力データソース**。奈良公園周辺の競合が高確率で網羅される |

| **Google Hotels 系 商用API**（SerpApi / DataForSEO / Bright Data 等） | **Googleのホテル検索結果に表示される実売価格**（チェックイン/アウト・人数指定）、価格提示元（OTA名）、評価・レビュー数 | 商用API（有料） | 日次 | 月 $50〜$250 程度〜（クエリ数依存。無料枠あり） | **中**（利用規約・提供事業者の法的保証範囲を確認） | ★★★ **「Googleマップからデータを集めたい」というご要望の実装解**。国内外OTAを横断した価格が1リクエストで取れる |

| **Booking.com / Expedia 各パートナーAPI** | 自社の在庫・料金の配信、一部レポート | 公式（契約先のみ） | — | 契約に含まれる | 低 | ★★ 主に配信用途 |

| **レートショッパーSaaS**（Lighthouse、RateGain、メトロエンジン等） | コンプセットの価格・在庫・パリティ監視をパッケージで | SaaS | 日次〜複数回 | 月3〜10万円規模 | 低（事業者が担保） | ★★★ 予算が許すなら第2優先の本命 |

### 3-4. ④ 自社データ（最も価値が高く、最も放置されやすい）

| データ | 取得元 | 用途 |
|---|---|---|
| 予約明細（予約日・宿泊日・室数・人数・単価・チャネル・プラン・LOS） | PMS／サイトコントローラー | ピックアップ、ブッキングカーブ、リードタイム分析 |
| キャンセル履歴 | PMS | 実効在庫の推定（オーバーブッキング判断） |
| F&B 売上・付帯率 | POS | TRevPAR最適化、厨房キャパ管理 |
| 公式サイトのアクセス・検索日付・離脱 | GA4／予約エンジン | **「探されたが売れなかった日」＝価格が高すぎた/在庫がなかった日**の特定（Denied/Regret 分析） |
| レビュー・NPS | OTA各社／Google | 品質と価格の整合性検証 |

> **Denied & Regret 分析**は小規模施設で特に効く。予約エンジンで「その日付が検索されたが予約に至らなかった」ログを残すだけで、**需要はあったのに取れなかった日**が可視化される。これは競合価格データよりも直接的な値付けシグナルである。実装コストも低い。

## 4. 「Googleマップからデータ収集」の実務 — 何が取れて、何が取れないか

ご指摘の通りGoogle経由の収集は有力である。ただし**Googleの提供口ごとに取れるものが全く異なる**ため、正確に切り分ける。

| Googleの提供口 | 客室の販売価格 | 評価・レビュー | 混雑・人気時間帯 | 位置・属性 | 用途 |
|---|---|---|---|---|---|
| **Places API (New)**（＝いわゆるGoogleマップAPI） | ✕ **取得不可** | ◎ | △（一部） | ◎ | コンプセット候補抽出、評判モニタリング |
| **Google Hotels（ホテル検索UI）** | ◎ 表示される | ◎ | — | ◎ | **人が見る分には最良。ただし公式API提供なし** |
| **商用SERP API（SerpApi等）経由の Google Hotels** | ◎ **取得可** | ◎ | — | ◎ | **競合価格の日次自動収集の実装解** |
| **Google Travel Partner API** | 自社分の配信・レポート | — | — | — | 承認パートナー向け。**競合価格の取得用途ではない** |
| **Hotel Center / 無料予約リンク** | 自社価格の掲出 | — | — | — | **直販の集客導線**（重要だが収集ではなく配信側） |

### 結論（Google活用の設計）

1. **競合の実売価格** → 商用SERP API（SerpApi/DataForSEO/Bright Data 等）で Google Hotels を日次取得。**国内外のOTA価格を横断で1回で取れる**のが最大の利点（一休・楽天・Booking・Expedia・Agoda を個別に見に行かなくてよい）
2. **競合の評判・話題性** → Places API (New) でレビュー数・評点の推移を週次取得。**レビュー数の増加ペースは「その施設が実際に売れているか」の代理指標**になる
3. **自社の露出** → Hotel Center に接続し、**Google 無料予約リンクへ自社公式価格を掲出**。これは収集ではなく直販比率改善の施策だが、費用対効果が極めて高い（掲載自体は無償）ため Phase 1 での実施を強く推奨

## 5. 最大の技術的難所：レート正規化（Same-Basis Comparison）

**「競合が8万円、うちが9万円」— この比較は、条件を揃えなければ全て無意味である。**

多くのRM施策が失敗する最大の技術的原因がここにある。以下の軸を必ず正規化する。

| 正規化軸 | ありがちな不整合 | 正規化ルール（推奨基準） |
|---|---|---|
| **人数** | 1名料金 vs 2名合計 vs 1名あたり | **2名1室・1室あたり合計**に統一 |
| **食事条件** | 素泊まり／朝食付／1泊2食 | **朝食別（Room Only）**に統一。食事分は別途控除（例：朝食6,600円/人） |
| **税・サービス料** | 税別表示／税込／サービス料10%別 | **税込・サ込の総額**に統一 |
| **部屋タイプ** | 最安室 vs スイート | グレード階層マスタで対応付け（スタンダード相当に正規化） |
| **キャンセル条件** | 返金可 vs 返金不可（15〜20%安い） | **返金可（Flexible）**を基準。返金不可は係数補正 |
| **滞在日数** | 1泊 vs 2泊平均 | **1泊（LOS=1）**基準。MinLOS制限日は「在庫なし」ではなく「制限あり」として別フラグ |
| **通貨・為替** | 海外OTAの外貨表示 | 取得日レートでJPY換算し、レートも保存 |
| **在庫状態** | 「満室」なのか「その条件のプランがない」のか | `sold_out` / `restricted` / `not_offered` を区別 |

> **実装指針**：収集した生データ（raw）は**一切加工せず永久保存**し、正規化は別レイヤで行う。正規化ルールは必ず改定されるため、raw を残しておけば遡って再計算できる。これを怠ると、ルール変更のたびに過去との比較が不能になる。

## 6. 法務・コンプライアンス整理

> 以下は一般的な整理であり、最終的には顧問弁護士の確認を前提とする。

### 6-1. 論点マップ

| # | 論点 | 概要 | 実務対応 |
|---|---|---|---|
| L1 | **著作権法 第30条の4（情報解析目的の利用）** | 日本法は情報解析目的での著作物利用に比較的寛容で、解析目的の複製は原則許容される。ただし但書により「著作権者の利益を不当に害する場合」は対象外 | **解析目的に限定**。収集した競合レートを**そのまま第三者に販売・公開しない**（元の市場と競合する利用は但書に抵触しうる） |
| L2 | **サイト利用規約（契約上の義務）** | 多くのOTAは自動収集を規約で禁止。規約違反は著作権法とは別に**債務不履行・不法行為・契約解除**のリスク | 規約を実際に読み、禁止されている先は**自前収集の対象外とする**。取引先OTAは特に慎重に（**契約関係にある相手の規約違反は事業リスクが跳ね上がる**） |
| L3 | **業務妨害（サーバ負荷）** | 過度なアクセスは業務妨害に問われうる（過去に図書館システムへの高頻度アクセスが刑事事件化した例がある） | アクセス間隔の下限設定、同時接続数の制限、深夜帯実行、robots.txt の尊重、User-Agent の明示 |
| L4 | **取得データの再配布** | 収集データを外部提供する行為は別論点 | **社内利用に限定**。系列他社との共有も契約整理を要す |
| L5 | **個人情報** | レビュー本文には個人に関する記述が含まれうる | レビューは**集計値（評点・件数・トピック）に加工して保持**、本文の長期保存は避ける |
| L6 | **競争法（レートパリティ）** | OTA契約の価格同等性条項は競争法上の論点。契約類型により許容範囲が異なる | 契約条項を法務レビューし、**直販優位化は「特典差」から着手**（別冊01 第4-2章） |
| L7 | **第三者API利用時の責任分界** | 商用SERP APIは提供事業者側で法的枠組みを整備している場合が多い | **契約書の免責・保証範囲を必ず確認**。ここを確認したうえで購入すれば、自前収集よりリスクが小さい |

### 6-2. 運用ルール（技術要件として実装する）

```yaml
collection_policy:
  priority:                          # 調達優先順位（違反不可）
    1: official_api                  # 楽天ウェブサービス等
    2: licensed_third_party          # 商用SERP API / レートショッパー
    3: own_scraping                  # 法務承認が下りた対象のみ

  own_scraping_requirements:         # 第3手段を使う場合の必須要件
    legal_approval: required         # 対象サイトごとに個別承認
    respect_robots_txt: true
    min_interval_seconds: 5          # 同一ホストへの最小間隔
    max_concurrent_per_host: 1
    execution_window: "02:00-05:00 JST"
    user_agent: "明示（連絡先URL付き）"
    on_429_or_403: "即時停止しアラート"   # 拒否シグナルには必ず従う

  data_handling:
    raw_retention: "永久（社内限定・暗号化）"
    redistribution: prohibited        # 外部提供・販売の禁止
    purpose_limitation: "自社の価格分析目的に限定"
    review_text_retention_days: 90    # レビュー本文は短期のみ
```

### 6-3. 「安全側」の推奨構成

鹿のやの規模と、OTAが**取引先でもある**という関係性を踏まえると、以下の構成が最も合理的である。

```
競合価格   ← 楽天トラベル空室検索API（公式・無料） 
           + 商用SERP API 経由の Google Hotels（ライセンス済み）
           + （予算が付けば）レートショッパーSaaS
競合評判   ← Google Places API (New)（公式）
一棟貸し   ← AirDNA / AirROI（ライセンス済み）
市場需要   ← 官公庁オープンデータ（完全に自由）
自社データ ← PMS / 予約エンジン / GA4（自社所有）

自前スクレイピング  ← 原則ゼロで設計する
```

**この構成であれば、自前スクレイピングを一切行わずに必要データの大部分が揃う。** 法務リスクを負ってまで自前収集する必然性は乏しい、というのが本提案の立場である。

## 7. データ品質SLOと監視

収集基盤は「静かに壊れる」。壊れたことに気づかないまま古い価格で判断することが最大の危険である。

| 監視項目 | SLO | 逸脱時のアクション |
|---|---|---|
| 収集ジョブ成功率 | 99%以上（日次） | 2日連続失敗で自動配信を停止し手動モードへ縮退 |
| コンプセット網羅率 | 一次コンプセットの90%以上を毎日取得 | 未取得施設をアラート表示、判断時に「欠損あり」を明示 |
| データ鮮度 | 24時間以内 | 48時間超のデータは推奨価格の算出に使用しない |
| 価格の異常値検知 | 前日比±50%超を検知 | 自動採用せず必ず人の確認へ回す（収集バグの可能性） |
| 正規化失敗率 | 5%未満 | マッピングマスタの見直しをタスク化 |
| 自社レートのパリティ整合 | 乖離0件 | 検知即アラート（サイトコントローラーの配信失敗を示唆） |
