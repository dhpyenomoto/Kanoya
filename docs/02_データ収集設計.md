# データ収集設計書

競合OTA情報の自動収集と、需要シグナルの取得設計。**[企画提案書](01_企画提案書.md) §3 の詳細版。**

---

## 1. データ源の全体像

レベニューマネジメントに必要なデータは3層に分かれます。重要度は上から順であり、**多くの施設が層3（競合レート）に注目しすぎて層1（自社データ）の整備を怠ります**。層1が汚れていると、どれだけ競合データを集めても正しい判断はできません。

| 層 | 内容 | 取得元 | 重要度 |
|---|---|---|---|
| **層1 自社データ** | OTB、予約明細、キャンセル、リードタイム、チャネル別実績、単価構成 | PMS／サイトコントローラー | ★★★ |
| **層2 需要シグナル** | イベント、天候、祝日、訪日統計、検索トレンド、レビュー速度 | 各種公開データ／Places API | ★★ |
| **層3 競合レート** | 競合の掲出価格・空室状況 | レートショッパー／Google Hotels API | ★★ |

---

## 2. 層1：自社データ（最優先）

### 2.1 必要な粒度

| データ | 粒度 | 用途 |
|---|---|---|
| 予約明細 | 1予約1行 | リードタイム分布、チャネル別分析、LOS分析 |
| **日次OTBスナップショット** | 宿泊日 × 取得日 | **ブッキングカーブの構築（最重要）** |
| キャンセル | 1件1行（発生日・宿泊日・理由） | キャンセル率、ポリシー設計 |
| 掲出価格履歴 | 宿泊日 × 取得日 × プラン × チャネル | 推奨と実配信の突合、パリティ監視 |
| F&B・アップセル | 予約単位 | TRevPAR |

### 2.2 最重要ポイント — OTBスナップショットの蓄積を「今日から」始める

**ブッキングカーブ（何日前に何室売れているのが正常か）は、過去に遡って復元できません。** 多くのPMSは「現在の予約状況」しか持たず、「30日前時点で何室売れていたか」を保持していないためです。

したがって、**Phase 0 の初日から、毎日のOTBスナップショットをBigQueryへ蓄積し始めてください。** これは他のどの作業よりも先行して着手すべき事項です。予約明細に予約日が入っていれば過去分をある程度再構成できますが、キャンセル済み予約が抜けるため精度は落ちます。

```
毎日 03:00 JST
  → PMS から「宿塊日ごとの現在OTB」を D+0〜D+365 で取得
  → fact_otb テーブルへ snapshot_date 付きで append（上書きしない）
```

## 3. 層3：競合レート

### 3.1 取得経路の比較

| 経路 | 精度 | 安定性 | 法務 | コスト | 判定 |
|---|---|---|---|---|---|
| **A. 商用レートショッパー**<br>（メトロエンジン、Lighthouse 等） | 高 | 高 | ◎ 正規契約 | 月3〜8万円 | **推奨（主）** |
| **B. Google Hotels API**<br>（SerpApi、DataForSEO 経由） | 中〜高 | 中 | ○ | 月2〜4万円 | **推奨（従・補完）** |
| **C. OTAパートナーAPI** | 高（自社のみ） | 高 | ◎ | 無料〜 | 自社データ取得に使用 |
| **D. 自前スクレイピング** | 中 | 低 | **✗ 規約違反リスク** | 開発工数大 | **不採用** |

**A と B を併用**します。Aを主データ源とし、Bで①Aのカバレッジ外施設、②クロスチェック（データ品質監査）、③インバウンド向け価格の把握、を補完する構成です。単一ベンダー依存を避ける意味もあります。

### 3.2 D（自前スクレイピング）を採らない理由

- 主要OTAの利用規約は、自動化された手段によるアクセス・データ収集を禁止しているのが通例です。
- 著作権法30条の4は「情報解析の用に供する場合」の**複製**を許容する規定であり、**サイト利用規約という契約上の義務**を免除するものではありません。
- 加えて、アクセス頻度によっては業務妨害の問題、取得データの利用態様によっては不正競争防止法上の論点が生じ得ます。
- 収集の安定性も低く（HTML構造変更・Bot対策で頻繁に破綻）、**運用要員を置けない5室施設では現実的な選択肢ではありません**。

法務判断は最終的に貴社顧問弁護士の確認を要しますが、**リスクとコストの双方から、正規経路のみで構成することを強く推奨します。**

### 3.3 収集スケジュールの階層化

全数を毎日取得するのはコストの無駄です。**価格が動く場所にだけリクエストを割り当てます。**

| リードタイム帯 | 対象日数 | 頻度 | 日あたり実効リクエスト（8施設） |
|---|---:|---|---:|
| D+0〜14 | 15日 | 毎日 | 120 |
| D+15〜45 | 31日 | 週2回 | 71 |
| D+46〜120 | 75日 | 週1回 | 86 |
| **合計** | 120日 | — | **277／日（月 8,297）** |

全数毎日取得なら月28,800リクエスト。**3.5倍の圧縮**になります。

さらに以下の優先度調整を重ねます。

- **週末・イベント日は1段階上の頻度**へ引き上げ（価格変動が集中するため）
- **競合が売止に転じた日は翌日も必ず再取得**（イベント自動検知の精度に直結）
- **平日・閑散期の遠い日付は隔週へ落とす**

### 3.4 取得データのスキーマ

```
fact_comp_rate
  snapshot_date    DATE      -- 取得日
  stay_date        DATE      -- 宿泊日
  comp_id          STRING    -- 競合施設ID
  source           STRING    -- rate_shopper / google_hotels
  channel          STRING    -- 掲出元OTA
  raw_rate         NUMERIC   -- 掲出価格（そのまま保存）
  currency         STRING
  pricing_basis    STRING    -- per_person / per_room（施設マスタから解決）
  meal_included    STRING    -- none / breakfast / dinner_breakfast
  available        BOOL      -- 在庫有無
  los              INT64     -- 対象泊数
  ingested_at      TIMESTAMP
```

**raw_rate は必ず生値のまま保存**し、正規化は下流で行います。正規化ロジックは改善され続けるため、生データを保持していれば遡って再計算できます。逆に正規化後の値だけを保存すると、ロジック変更時に過去分が再現できなくなります。

## 4. Google系サービスの正しい使い分け

ご指摘の「Googleマップからのデータ収集」について、用途を明確に分けます。

### 4.1 Places API — 価格ではなく「発見」と「需要トレンド」

| 取れるもの | 本件での用途 |
|---|---|
| 施設名・住所・座標・カテゴリ | **コンペセットの機械的発見**（半径2km・宿泊カテゴリを全列挙） |
| 評点（rating）・レビュー件数 | **レビュー件数の月次増分＝宿泊需要の代理指標**（"レビュー速度"） |
| price_level（$〜$$$$） | ❌ 4段階の記号のみ。**実勢ADRとしては使えない** |
| 営業状態・写真・属性 | 新規開業／閉業の検知（コンペセットの鮮度維持） |

**レビュー速度**は見落とされがちですが有用です。競合のレビュー件数が前月比で急増していれば、その施設は稼働を伸ばしている＝エリア需要が強いか、その施設が自社から客を奪っている、のいずれかです。価格データを補完する独立したシグナルとして月次で監視します。

### 4.2 Google Hotels — 実勢価格の取得

Google Hotels は施設 × チェックイン日の**実勢価格と空室状況**を保持しており、これが競合レートの実質的な取得先です。直接のパブリックAPIは提供されていないため、SerpApi・DataForSEO 等のAPIサービス経由で取得します。

**注意**：Google の Hotel Center／無料予約リンクは、**自社の価格をGoogleへ出稿する**ための仕組みであり、競合価格を取得するためのものではありません。混同されやすい点です（ただし自社の露出施策としては別途価値があり、直販強化の文脈で導入を検討すべきです）。

### 4.3 コンペセット自動発見のフロー

```
月次バッチ
 1. Places API: 施設座標から半径2km・lodging カテゴリを全列挙
 2. 各施設の rating / user_ratings_total / price_level / 客室数（別途） を取得
 3. 類似度スコアを算定
      score = w1·距離近接 + w2·価格帯重複 + w3·規模近接
              + w4·評点近接 + w5·食事形態一致
 4. 上位N件を候補として提示 → 四半期レビューで人が最終承認
 5. 新規開業・閉業を差分検知してアラート
```

**完全自動にせず「候補提示＋四半期承認」とする**のは、競合認定が事業判断を含むためです。ただし候補の生成を機械化することで、「気づいたら近隣に強力な新規開業があった」という取りこぼしを防ぎます。

## 5. 層2：需要シグナル

| シグナル | 取得元 | 更新頻度 | 用途 |
|---|---|---|---|
| 祝日・連休 | 内閣府 祝日CSV | 年1回 | 基準価格の連休前夜補正 |
| 奈良の年中行事 | 各社寺・奈良市観光協会の公開情報 | 四半期 | イベントスコア |
| 天候予報 | 気象庁／天気API | 日次 | 直前期の需要補正（Phase 3） |
| 訪日外客数 | 日本政府観光局（JNTO）統計 | 月次 | インバウンド需要トレンド |
| 為替 | 公開API | 日次 | **海外OTA掲出価格の実質水準監視** |
| レビュー速度 | Places API | 月次 | エリア需要と競合の勢い |
| 検索トレンド | Google Trends | 週次 | 先行指標（Phase 3） |

### 5.1 為替を監視する理由

インバウンド比率が高い施設では、円建て価格を据え置いても、**為替次第で海外顧客から見た実質価格が10〜20%変動**します。円安局面では実質値下げが起きており、値上げ余地があります。逆に円高局面では、円建てを据え置くと海外需要が落ちます。

海外OTA向けの価格判断には、**USD／CNY／EUR建ての自社価格の推移**をダッシュボードに常設し、円建てだけを見て判断しないことを推奨します。

## 6. データ品質管理

自動収集の最大のリスクは「壊れたデータに気づかないまま価格を配信すること」です。以下を必須の防御線とします。

| チェック | 内容 | 違反時の挙動 |
|---|---|---|
| 鮮度 | 競合レートの最終取得から24時間以内 | 超過で**自動配信を停止**、モデル値を凍結 |
| カバレッジ | PRIMARY施設の取得成功率 80%以上 | 下回れば当日の comp 項を無効化（他の項のみで算定） |
| 値域 | NAR が 20,000〜600,000円 の範囲内 | 範囲外は母数から自動除外 |
| 前日比 | 競合NAR中央値の前日比が ±40% 以内 | 超過でアラート（収集エラーの疑い） |
| 突合監査 | 月1回、無作為10件をOTA画面と目視突合 | 乖離があれば正規化パラメータを是正 |

**月次の目視突合は省略しないでください。** 食事条件や人数課金の設定が実態とズレていると、正規化後の価格が体系的に歪み、しかもエンジン内では正常値に見えます。自動化されたパイプラインで唯一、人間の目でしか検出できない種類の誤りです。

| 本書の節 | 実装 |

### 8.1 実装で判明した設計上の要点

**① 削減効果の内訳を正しく分けること**

当初「全数毎日 28,800 → 階層化 8,297 で3.5倍圧縮」と見積もりましたが、
実装してみると削減の大半は**エリア一括検索**（1リクエストで複数施設が返る）から
来ており、階層化はそこからさらに2〜3倍を削るという構造でした。

| 水準 | 月間リクエスト | 月額 |
|---|---:|---:|
| ①施設別 × 毎日 | 43,200 | $648 |
| ②エリア一括検索 | 3,600 | $54 |
| ③②＋階層化 | 約1,400 | 約$21 |

`--plan-only` はこの3水準を並べて表示します。効果を過大に見せないためです。

**② 遠い日付の繁忙日を毎日取りに行かないこと**

「週末・イベント日は頻度を上げる」を無条件に適用すると、120日先の紅葉シーズン
全17日を毎日取得することになり、費用だけが増えてカバレッジは改善しません。
リードタイム上限（週末60日／イベント45日）を設けています。

**③ 収集した日のデータだけを見てはいけない**

階層化収集では、遠い宿泊日は毎日は更新されません。「今日取得した行」だけで
判断しようとすると、対象120日のうち78日がデータ無しになりました。
**(宿泊日, 競合) ごとに基準日以前で最新の観測を採用**し、経過日数を鮮度として
持つのが正しい実装です。

**④ 欠測と売止を区別すること**

Google Hotels のレスポンスに施設が現れない場合、それは「売止」です。
これを欠測として無視すると市場逼迫度の判定が壊れるため、
計画に含まれるが結果に現れなかった施設は `available=0` として明示的に記録します。

**⑤ 施設名の名寄せで一般語を落としすぎないこと**

表記ゆれ対策として「ホテル」「奈良」等の一般語を除去したところ、
『奈良ホテル』が空文字になり、どの施設とも突合できなくなりました。
業態語や地名は施設の識別に効く情報です。落とすのは区切り記号と空白のみとします。
