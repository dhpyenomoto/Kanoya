# PoC — 価格決定エンジン試作実装

別冊03『価格決定エンジン仕様』のロジックを、そのまま動く形にした試作である。
実データ接続前に、**算定ロジックとガードレールの挙動を検証・議論するため**のもの。

## 実行

```bash
pip install pyyaml
python3 poc/demo.py                      # 90日分の推奨レートを出力
python3 poc/demo.py --days 30 --detail 5 # 30日分＋承認カード5件の詳細表示
python3 poc/demo.py --converge 1         # 収束させず「初回移行時」の挙動を見る
```

## 構成

| ファイル | 内容 |
|---|---|
| `policy.yaml` | **Rate Policy as Code**。経営が決める唯一のパラメータファイル |
| `pricing_engine.py` | 推奨価格の算定ロジック（副作用なしの純粋関数群） |
| `demo.py` | 合成データによるデモ実行。奈良の主要行事を模した需要配置 |

## 実装されているもの

- 需要圧力指数 DPI（コンプセット完売率・価格トレンド・自社ペース・イベント・市場季節性の合成）
- 乗数分解モデル（基準 × ペース × 競合 × イベント × 在庫希少性 × リードタイム）
- **縮小推定**（データが薄い日は基準価格へ引き戻す＝5室運営の最重要安全装置）
- ガードレール（ブランドフロア／シーリング／日次変動上限／価格ラダー丸め）
- **値下げ禁止則**（直前値下げによるブッキングカーブ後ろ倒しの防止）
- MinLOS 自動判定（逸失分析）
- 高需要日の高手数料チャネル絞り込み（純ADR最大化）
- 承認カード生成（要因分解つきの根拠テキスト）
- 早期完売検知・ホールドアウト日の決定的選定

## デモ出力の読み方

```
 自動配信率  初回移行時 15%  →  定常運用時 82%（要承認 15 件）
```

日次変動上限（±15%）があるため、**導入直後は多くの日が上限に張り付き「要承認」**になる。
数日かけて段階的に価格が収束すると自動配信率が上がる。これは仕様どおりの挙動であり、
価格の急変で顧客の信頼を損なわないための設計である。

```
 平均ADR   合成データ上の現行 96,463円 → 推奨 133,634円 (+38.5%)
```

⚠️ **これは効果推定ではない。** 合成データの「現行レート」は季節・曜日のみで決めた
平板な値であり、実際の鹿のやの料金設定ではない。実効果の測定は、実データ接続後に
ホールドアウト日法（別冊03 第9章）で行う。

## 実装時に差し替えるもの

| 箇所 | 現在 | 実装時 |
|---|---|---|
| コンプセット | `COMPSET = ["comp_a"...]` | Phase 0 で確定した実施設ID |
| 観測データ | `synth_day()` の合成生成 | 楽天トラベルAPI／商用SERP APIからの実収集 |
| イベント | `EVENT_CALENDAR` のハードコード | `event_master` テーブル |
| ブッキングカーブ | 線形近似 | PMS実績から seg 別に推定 |
| 標準化 `_z()` | 固定の中心・スケール | 同一 seg 内のロバストz（中央値・MAD） |
| 基準価格 `bar_base` | 仮置き | Phase 0 で実績から確定 |

## 設計上の注意

`pricing_engine.py` は**副作用を持たない**。収集も配信もしない。
これはテスト容易性のためであり、価格という不可逆な意思決定を扱う以上、
ロジックが単体で検証可能であることを最優先とする。
