# 奈良春日 鹿のや — レベニュー・インテリジェンス

全5室の宿の値付け判断を、毎日1行に落とすための小さなシステム。
Google Places の公開データだけを入力に、コンプセットの**需要**を推定し、
「今日は上げるのか、下げるのか、据え置くのか」を出力する。

```
python -m kanoya report --out dist/index.html
```

## 何をするものか（そして何をしないか）

| する | しない |
| --- | --- |
| コンプセットの相対的な需要推定 | 競合レートの取得 |
| 自社PMS実績によるキャリブレーション | 日次の需要予測 |
| ルール逸脱時のシグナル出し | OTA画面のスクレイピング |

**このシステムはレートを推定しない。** Google Places API は競合施設の宿泊料金を
返さないし、OTA画面やGoogleホテル検索画面のスクレイピングは規約違反なので実装していない。
実レートが要るなら、正規ライセンスのレートショッパー（メトロエンジン等）を別途契約し、
そこで得たレートを本システムの需要判断と突き合わせる。ここで出るのは需要だけ。

## 推定の仕組み

Places API は個別レビューを最大5件しか返さないので、90日分の投稿タイムスタンプは
原理的に取れない。そこで **`userRatingCount` を毎日スナップショットし、その差分**
を需要シグナルとして使う。

```
                 実効レビュー増分
推定販売室数 = ──────────────────      実効 = 増分 × (1 − 外来クチコミ比率)
                  レビュー投稿率

                  推定販売室数
推定稼働率  = ──────────────────
                客室数 × 日数
```

投稿率は**自社PMS実績との突合で実測**する（同梱フィクスチャでは 261日・923室・
実効95件 → 10.3%）。この実測値を競合にも適用する。つまりここで出る絶対値は
「競合も自社と同じ割合でレビューを書かれる」という仮定に全面的に依存している。
読むべきは絶対値ではなく、**施設間の相対差**と**モメンタム**。

処理の順序：

1. **投稿遅延の巻き戻し** — レビューは滞在から平均10日遅れて出るので、増分を10日前に戻す
2. **不安定な尾の切り落とし** — 直近10日はまだ投稿が出揃っていないので集計窓から外す
3. **外来クチコミの控除** — オーベルジュ・レストラン併設施設は外来客のレビューが混ざる
4. **90日窓での集計** — 全5室では日次稼働は 0/20/40/60/80/100% しか取らないため

## 精度の実態

これは正直に書いておく必要がある。**レビューの発生はポアソン過程なので、5室規模では
90日で60件程度しか出ず、相対標準誤差は 13% 前後、稼働率にして ±9pt（1σ）になる。**

その帰結として、実装は次のようにしてある。

- **前期比は有意差検定を通す。** 2標本ポアソン検定（両側5%）で有意でない増減は
  灰色で表示し、シグナルにも上げない。5室で「前期比 +8pt」はほぼ全部ノイズであり、
  そこに反応すると毎回ノイズに値付けを振り回されることになる。
- **据え置き帯はその日の推定精度で決まる。** 固定の3ptではなく `1σ` を下限として広がる。
  ただし 95%（1.96σ）にすると帯が ±18pt まで開いて何も判断できなくなるため、既定は 1σ。
  値付けは仮説検定ではなく可逆な意思決定なので、1σの証拠で動かしてよい、という判断。
  厳しくしたければ `rules.band_sigma` を上げる。
- **バックテストを毎回回す。** 過去6期について「推定した自社稼働 vs PMS実績」の平均絶対
  誤差を出し、その大きさに応じて「水準の議論に使える／方向性の議論のみ／参考値」を
  ダッシュボードに明記する。これはイン・サンプル検証（投稿率を全期間で実測しているため）
  なので、手法の上限精度であって将来の誤差保証ではない。

**推定稼働率の絶対値を投資家向け資料やオーナー報告にそのまま転載しないこと。**
用途は自社の値付け判断に限る。

## 使い方

依存パッケージなし（Python 3.11+ / 標準ライブラリのみ）。

```bash
# 1. エリアの母集団を台帳化する（初回のみ／年に数回）
GOOGLE_MAPS_API_KEY=... python -m kanoya discover

# 2. 当日のスナップショットを1件追記する（毎日 cron）
GOOGLE_MAPS_API_KEY=... python -m kanoya collect

# 3. ダッシュボードを生成する
python -m kanoya report --out dist/index.html

# 4. 判断とシグナルだけを標準出力に（要対応シグナルがあれば exit 1）
python -m kanoya check
```

`collect` は日次で回し続けないと増分が取れない。1日落としても
欠測区間に均等配分するようになっているが、連続で落とすと窓が痩せる。

### 実データを入れる前に

`config.json` の `place_id` はサンプル値なので、実運用では次を差し替える。

1. **`property.place_id` / `comp_set[].place_id`** — 実際の Place ID
2. **`property.restaurant_review_share`** — 外来クチコミ比率。**推定値なので感度分析が必須。**
   ここを 0.45 と置くか 0.30 と置くかで推定稼働は 27% 変わる。予約実績と食事のみの
   来店実績の比率から出すのが本筋。
3. **`property.rating_floor`** — この評価を下回ったらBAR引き上げを凍結する線
4. **`data/pms_daily.csv`** — 自社PMSの日次実績（`date,rooms_sold,rooms_available`）

同梱の `data/` は `tools/make_fixture.py` が生成した検証用の合成データで、実データではない。
実データに切り替えるときは中身を消してから `collect` を回す。

## 判断ルール

`kanoya/signals.py` にすべて入っている。ここだけが「で、どうするか」を決める。

| ルール | 内容 |
| --- | --- |
| 今日の判断 | 自社稼働 vs 競合中央値。差が据え置き帯の内側なら据え置き |
| 品質ゲート | 評価が `rating_floor` を下回っていたら引き上げを凍結（判断より優先） |
| 競合モメンタム | 自社より上の水準で、有意に伸びている競合だけを拾う |
| シェア縮小 | エリア内クチコミシェアが前半比で15%以上縮んだら警告 |
| 需要暦 | 45日以内の催事は在庫の締め方を先に決めるよう促す |

品質ゲートを判断より優先させているのは、露出（Googleの並び）と成約率がレビュースコアに
効くため。スコアが落ちている局面でBARを上げると、稼働を落としたうえにスコア回復も遅れる。

## 構成

```
kanoya/
  config.py     config.json の読み込み
  places.py     Google Places API (New) クライアント
  store.py      スナップショット台帳・PMS実績の入出力
  series.py     累計→増分、投稿遅延の巻き戻し、移動合計
  estimate.py   キャリブレーション・稼働推定・バックテスト
  signals.py    判断ルール
  render.py     ダッシュボードHTML
  cli.py        discover / collect / report / check
tools/
  make_fixture.py   検証用の合成データ生成（本番からは呼ばれない）
```

## テスト

```bash
python -m unittest discover -s tests
```

中心はノイズなしの合成データからの復元テスト。真の投稿率・真の稼働率を置いた
データを作り、推定器がそれを誤差 0 で復元できることを確認している。ここが合って
いれば、実データでのズレはノイズか前提のズレであって実装バグではない、と切り分けられる。
