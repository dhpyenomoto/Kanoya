# 奈良春日 鹿のや — レベニューマネジメント基盤

全5室オーベルジュ「奈良春日 鹿のや」を対象とした、**レベニューマネージャーの経験・力量に依存しない**ダイナミックプライシング基盤の企画書と参照実装。

近隣競合のOTA掲出情報を自動収集・正規化し、需要シグナルと組み合わせて日次の最適ADRを算出、ガードレール内は自動でOTAへ配信、逸脱分のみ人が承認する——という運用を設計しています。

>
> 推奨部屋代（実売室夜で重み付け）の中央値は実績の -2.3%。ただしこれは

## 中核となる考え方

| 原則 | 実装 |
|---|---|
| **判断のコード化** | 値付けを「基準価格 × 5つの補正係数」の決定論モデルとして外部化 |
| **説明可能性の強制** | 全推奨価格を「基準価格＋各要因の円建て寄与」に分解して出力 |
| **例外管理への転換** | ガードレール内は自動配信、逸脱分のみ承認キューへ（日次運用15分） |
| **記入漏れの構造的排除** | イベント表への人手入力に頼らず、競合の売止・価格急騰から需要を逆算検知 |
| **属人判断の自動校正** | 最も属人的な「基準価格をいくらに置くか」を市場整合×予算整合の2条件から機械的に解く |

## 提示価格の日次記録（rate_log）

**「その日その宿泊日をいくらで出していたか」を残します。** 実績データには
成約価格しか残らないため、これが無いと値付けの良否が測れません。

実際にこれで損をしています。2026年6〜7月に意図的な値上げ実験が行われましたが、
提示価格が残っていないため定量評価ができませんでした。リードタイム構造から
「早期54,910円で9件、直前37,824円で20件」と推定するのが限界でした。

もう一つ、**承認区分が機能しません。** `delta_pct` は推奨と現行掲出価格の比なので、
`current_public_rate` が0だと全日が「自動配信」に落ちます。実データ検証で
自動配信100%と出たのは較正が良いからではなく、比べる相手が無いからでした。

```bash
cd engine
python3 scripts/log_rates.py --show          # いまの提示価格を見る
python3 scripts/log_rates.py                 # 変更分だけ入力する
python3 scripts/log_rates.py --set 11/14-11/30=62000
python3 scripts/log_rates.py --import export.csv   # サイトコントローラーから
```

実体は `Kanoya-data/rate_log.csv`（顧客の予約に紐づく情報のため Private 側）。
場所は `engine/config/sources.json` の `rate_log` で設定します。

### 記録は「変更履歴」＋「実行記録」です

5室 × 4形態 × 120日を毎日書き写す運用は続きません。続かない記録は無いのと
同じです。そこで**値が変わった日だけ行を足す**形にしてあります。ある行は、
より新しい行に上書きされるまで有効であり続けます。

- 変更が無い日は **Enter だけ**で終わります（価格の行は1行も増えません）
- 表示は同じ値が続く区間にまとめます（42日分が5行になります）
- 入力は区間指定（`11/14-11/30=62000`）。変えたところだけ書きます
- 閉館日は自動で飛ばします
- **ネットワークへは一切アクセスしません**

### なぜ「実行記録」が別に要るのか

変更履歴だけだと、**行が無い日が2つのことを同時に意味します**。

| | |
|---|---|
| (a) | 人が確認したうえで「変わっていない」 |
| (b) | 誰も見ていない（実行していない） |

**(b) を (a) と読むと、確認していない日に「価格を据え置いた」という事実でない
記録が残ります。** しかもその誤りは、あとから区別する手がかりがありません。

そこで実行そのものを `rate_log_runs.csv` に残します。1行は「この日に、この
宿泊日範囲を確認した」という意味で、**価格が変わらなくても1行増えます**。

```csv
run_date,stay_from,stay_to,product_type,channel,note
2026-09-18,2026-09-18,2027-01-15,room_only,,変更なしを確認
```

`current_public_rate` を解決するときは、**実行記録に裏付けられた値だけ**を
使います。最後の確認から `max_unconfirmed_days`（既定3日）を超えた宿泊日は、
記録があっても使いません（**据え置きを仮定しません**）。分からないことを
分かっているように見せるほうが、値が無いことより危ないためです。

確認した範囲は、入力の仕方より広く言い切りません。

| 入力 | 確認済みとして記録する範囲 |
|---|---|
| 対話（Enter だけを含む） | 画面に出した期間ぜんぶ（人が見ている） |
| `--set` | 名指しした区間だけ |
| `--import` | ファイルに入っていた宿泊日だけ |
| `--show` / `--dry-run` | 記録しない |

### ⚠️ 記録開始前の期間は復元できません

**2026年2月〜9月の提示価格は失われています。遡って埋めないでください。**

推定値を実測と混ぜると、あとから区別できなくなります。当時の提示価格は
どこにも残っておらず、成約価格から逆算しても「売れた価格」しか分かりません
（売れなかった価格こそが知りたい情報です）。

この期間の `current_public_rate` は0のままとし、承認区分は判定不能として
扱ってください。1日遅れるごとに1日分の記録が失われます。費用はゼロです。

## 競合施設の実名は Private 側にあります

本リポジトリは Public のため、**競合施設を同定できる情報は
`Kanoya-data`（Private）へ分離しています**。削除ではなく移動であり、
情報は失われていません。

| 置き場所 | 内容 |
|---|---|
| `engine/config/compset.json`（Public） | `comp_id`・ティア・重み・課金方式・食事条件・uplift — **価格計算に必要な属性** |
| `Kanoya-data/compset_names.json`（Private） | 実名・`place_id`・緯度経度・距離・評価・レビュー数・スコア内訳 |
| `Kanoya-data/compset_overrides.json`（Private） | 人が確定した施設属性（施設名がキー） |
| `Kanoya-data/fixture_facilities.json`（Private） | フィクスチャ生成に使う実在施設の一覧と座標 |

**突き合わせは `comp_id`（auto01 など）で行います。表示名では行いません。**
施設が改名した瞬間に静かに外れ、その施設だけ匿名表示に戻るうえ、
誰も気づかないためです。

対応表が無くてもエンジンは動きます。見つからなければ警告を出し、競合を
`comp_id` のまま表示して続行します。価格計算に必要な属性は `compset.json`
側に残っているため、**推奨価格は変わりません**。対応表にない `comp_id` が
あれば、その施設だけが匿名表示になります。

場所は `engine/config/sources.json` の `compset_names` で設定します。

```jsonc
"compset_names": {
  "path": "../../Kanoya-data/compset_names.json",
  "fallback_paths": ["../../kanoya-data/compset_names.json"]
}
```

### 匿名化を解除する（将来 Private 化した後に戻す手順）

リポジトリを Private にしたあと実名を本体側へ戻したくなった場合は、
`compset_names.json` を `compset.json` へマージし直します。

```bash
cd engine
python3 - <<'EOF'
import json, pathlib
compset = pathlib.Path("config/compset.json")
names = pathlib.Path("../../Kanoya-data/compset_names.json")

data = json.loads(compset.read_text(encoding="utf-8"))
table = json.loads(names.read_text(encoding="utf-8"))["competitors"]

for comp in data["competitors"]:
    comp.update(table.get(comp["id"], {}))       # comp_id で突き合わせる
data.pop("_anonymized", None)
compset.write_text(json.dumps(data, ensure_ascii=False, indent=2) + "\n",
                   encoding="utf-8")
EOF
python3 -m unittest discover -s tests          # 推奨価格が変わらないことを確認
```

同様に、`Kanoya-data/compset_overrides.json` を
`engine/config/compset_overrides.json` へ、
`Kanoya-data/fixture_facilities.json` を
`engine/config/fixture_facilities_sample.json` へ上書きコピーすれば、
再生成の経路も本体側だけで完結します。

戻したあとは `engine/tests/test_compset_names.py` の
`NoRealNamesInTheRepoTest` が落ちます（実名が本体側にある状態を検知する
テストのため）。Private 化を確認したうえで、そのテストを外してください。

## 運用モデル：定休日は固定ではない

**定休日は固定ではなく、需要に応じた例外営業が通年で発生する。稼働率の分母は
事後的に変わりうるため、稼働率・RevPAR には必ず分母を併記すること。**

鹿のやは従業員数の都合で火曜・水曜を閉館日としていますが、需要があれば
その日を開けます。繁忙期に限った話ではありません。

```
2026-02-06 〜 2026-09-17（暦日224日）
  閉館日（火・水）          64日
  うち例外営業              8日  = 12.5%
  営業日                  168日  （160日 + 8日）
```

これが効いてくるのは、**同じ期間の稼働率が後から変わる**ためです。

| 分母 | 室夜 | 稼働率 |
|---|---|---|
| 暦日 224日 × 5室 | 1,120 | 21.2% |
| 曜日ルール 160日 × 5室 | 800 | 29.6% |
| 実績 168日 × 5室 | 840 | **28.2%** |

同じ実売237室夜を指しているのに3つの数字が出ます。どれが正しいかではなく、
**どの分母で割ったかを書かなければ意味が定まらない**、というのが要点です。
`kanoya_rm/capacity.py` がこの分母を数え、出力に必ず `営業168日 × 5室 =
840室夜` の形で添えます。

将来期間は例外営業がまだ決まっていないため、営業日数は**下限**です。
そのため稼働率を単一値ではなく幅で出します（上限は
`closed_days.exception_rate`・既定0.125＝実績由来）。

### 設定のしかた（他施設へ展開する場合）

`engine/config/calendar.json` の `closed_days` に置きます。火曜・水曜は
コード側の既定値ではなく、この設定ファイルの値です。

```jsonc
"closed_days": {
  "closed_weekdays": ["TUE", "WED"],        // 定休日なしなら []、週1定休なら1つ
  "extra_open":  [{"date": "2026-08-11", "source": "actual",  "note": "火・お盆"}],
  "extra_closed": [{"date": "2027-01-15", "source": "planned", "note": "改装"}],
  "exception_rate": 0.125                   // 将来の例外営業の発生率
}
```

- 優先順位は **日付指定 > 曜日指定**。両方に書かれた日は営業（休むほうを
  既定にすると売り逃す）
- `source` は必須。`actual` は実績から確認した日、`planned` は人が入れた予定。
  混ざると稼働率の分母を後から検証できなくなります。書き忘れは `planned` 扱い
- **連泊のまたぎは `extra_open` に入れない**。在館者はいても販売していない日は
  営業日ではありません（例: 2026-02-18(水) は 2/17 チェックイン2泊の2泊目）。
  該当日は「閉館日に在館者がいます」として起動時に知らせます
- 季節休業がある施設は `extra_closed` に期間を並べます

## サイトとして見る

`site/` に静的サイトを生成済みです。**ホスティング側でのビルドは不要**で、そのまま配信できます。

```bash
cd engine && pip install markdown && python3 scripts/build_site.py   # 文書を更新したら再生成
```

| 置き場所 | 手順 |
|---|---|
| ローカル | `site/index.html` をブラウザで開く |
| Vercel | `vercel.json` 同梱済み。Framework は自動判定させず `site/` を配信 |
| 社内ファイルサーバ | `site/` をそのままコピー |

ビルド工程を持たせない方針です。ビルドが無いものは壊れません
（`_config.yml` を Vercel が Jekyll と誤検出して失敗した経緯があります）。

**`site/` は誰でも見られる状態で配信されます。** 閲覧者を限定するには、
Vercel の Deployment Protection を設定するか、社内ネットワーク内に置いてください。
全ページに `noindex` を入れてありますが、これは検索避けであってアクセス制限ではありません。

## 参照実装

企画書の数式・ガードレール・出力フォーマットは、すべて動作するコードとして `engine/` に実装されています（標準ライブラリのみ、依存パッケージなし）。

### 調査条件の入力

「**いつ時点で**（本日）」「**どの宿泊日を**（対象期間）」調べるかは、
`engine/config/survey_request.json` の1か所で指定します。CLI引数でも上書きできます。

```bash
python3 scripts/survey_report.py --from 2026-11-01 --to 2026-11-30
python3 scripts/survey_report.py --from 2026-11         # 11月まるごと
python3 scripts/survey_report.py --from +30d --days 14  # 30日後から2週間
```

`as_of`（基準日）と `target`（対象期間）は独立した別概念です。
詳細は [収集パイプライン運用手順 §1.5](docs/05_収集パイプライン運用手順.md)。

### 収集パイプライン（発見 → 収集 → ADR判断）

```bash
cd engine
./scripts/run_pipeline.sh                               # APIキー不要のオフライン実行
FROM=2026-11-01 TO=2026-11-30 ./scripts/run_pipeline.sh  # 期間を絞る
```

| 工程 | スクリプト | 内容 |
|---|---|---|
| ① 発見 | `discover_compset.py` | Places API で**半径5km**内の宿泊施設を全列挙し、5軸類似度スコアでティア分類 |
| ② 確定 | `config/compset_overrides.json` | **人手**で客室数・課金方式・食事条件・uplift を確定（APIからは取得不可） |
| ③ 収集 | `collect_rates.py` | Google Hotels から階層化スケジュールで実勢価格を収集 |
| ④ 判断 | `survey_report.py` | NAR正規化して市場ポジションを算出、3シグナル合議でADR判断 |
| ⑤ 可視化 | `adr_matrix.py` | 施設×日付のADRマトリクス（端末／CSV／HTMLヒートマップ） |

実データで動かす場合は環境変数にAPIキーを設定します（コードには書きません）。

```bash
export GOOGLE_PLACES_API_KEY='...'
export SERPAPI_API_KEY='...'
SOURCE=serpapi ./scripts/run_pipeline.sh
```

## 注意事項

- 同梱のサンプルデータは**決定論的な擬似データ**であり、実データではありません。
- 施設の実績数値は非公開のため、企画書中の経営数値は公開情報と同規模施設の一般的水準から置いた**仮定値**です（「※仮定」と明記）。Phase 0 で実データに差し替える前提です。
- 競合施設名・属性も公開情報ベースの想定であり、Phase 0 で確定します。
- 競合レートの取得は、商用レートショッパーおよび公式／準公式APIに限定する設計です（OTAサイトの自前スクレイピングは規約・法務リスクから採用しません）。詳細は [データ収集設計 §3.2](docs/02_データ収集設計.md)。
- 社外へ資料を共有する必要が生じた場合は、`adr_matrix.py --anonymize` で競合名を「競合A/B/…」に伏せた版を生成できます。
