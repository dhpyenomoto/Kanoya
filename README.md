# 奈良春日 鹿のや ｜ レベニュー・インテリジェンス

Google Places API のクチコミ件数の増分から、コンプセット（自社＋競合 5 施設）の
**需要**を推定し、毎日の値付け判断を 1 枚のダッシュボードに落とす。

**レートは推定しない。** Places API は競合の宿泊料金を返さないし、OTA 画面や
Google ホテル検索画面のスクレイピングは規約違反なので実装していない。実レートは
正規ライセンスのレートショッパーで別途取得し、ここで出る需要判断と突き合わせて使う。

---

## 使い方

```bash
pip install -r requirements.txt

# API キーなしで合成データを作り、ダッシュボードまで通す
python -m kanoya.cli demo --as-of 2026-08-15

# 本番: 毎日 1 回観測を積む（cron 向け）
export GOOGLE_PLACES_API_KEY=...
python -m kanoya.cli poll

# 溜まった観測からダッシュボードを生成する
python -m kanoya.cli report --out dist/index.html
```

`make demo` / `make test` も用意してある。

---

## なぜ毎日観測する必要があるのか

Places API は 1 施設あたり**最大 5 件**しかレビューを返さない。「過去 90 日に
何件レビューが増えたか」を 1 回の呼び出しで知る方法はない。

そこで `userRatingCount`（クチコミ総数）を毎日記録し、その差分を需要の代理指標に
する。`data/snapshots.jsonl` がこのシステム唯一の時系列データ源であり、
**観測を始めた日より前には遡れない**。導入初日には何も出ない。90 日窓の数字が
埋まるまで約 3 か月、前期比が出るまで約 7 か月かかる。

---

## 推定の道筋

```
クチコミ総数の日次差分
  → 外来（レストラン利用のみ）レビューを控除     restaurant_review_share
  → 投稿遅延ぶん日付を引き戻して滞在日ベースに    review_lag_days
  → 投稿率で割って販売室数に                    自社 PMS 実績から実測
  → 客室数 × 日数 で割って稼働率
```

投稿率は自社 PMS の販売実績とレビュー発生を突合して**実測**し、同じ率を競合にも
当てる。競合の投稿率が自社と違えば推定は系統的にずれる。これは避けようのない
仮定なので、自社での当てはまりを backtest で数値化してダッシュボードに出している。

### 境界の切り方が効く

2 か所、間違えると投稿率が過小に出る（そして全施設の稼働が過大に出る）。

- **観測開始前の日を分母に入れない。** レビュー 0 件として数えてしまう。
- **観測終了の直前の日を分母に入れない。** まだ投稿されていないレビューを
  0 件として数えてしまう。`review_lag_days + unstable_tail_days` ぶん手前で切る。

同じ理由で、集計窓の右端も `as_of` から `review_lag_days + unstable_tail_days`
だけ手前に置いてある。今日の需要は今日には見えない。

## この推定で何が言えて、何が言えないか

精度はレビュー件数だけで決まる。件数 n の相対標準誤差は 1/√n なので:

| 窓内レビュー | 稼働率 75% での 95% 区間 |
|---|---|
| 30 件 | ±27pt |
| 120 件 | ±13pt |
| 500 件 | ±6.6pt |
| 2000 件 | ±3.3pt |

**全 5 室・投稿率 10.5% の施設は、90 日で 35 件前後しかレビューが立たない。**
つまり稼働率の水準は ±25pt 程度でしか分からない。5pt の差で値付けを動かす根拠には
ならない。合成データでの実測でも、5 室の施設の推定は標準偏差 11pt、40 室の施設で
4.8pt だった（系統誤差はいずれも 3pt 以内）。

ダッシュボードは信頼度の欄に必ず `±N` を出す。**この幅より小さい差は誤差と
区別できない**。判断ロジックも、閾値を超える差であってもそれが計数誤差の内側なら
「据え置き」を返す。誤差でレートを動かすのが、この種の推定でいちばんやりやすい失敗。

### 誤差には 2 種類ある

- **計数誤差**（施設ごとに独立）… 施設間の比較でも消えない。信頼度の `±` はこれ。
- **投稿率の誤差**（全施設に共通）… 投稿率を 1 割高く見積もれば全施設が揃って
  1 割低く出るので、**順位や差の議論では相殺される**。水準を語るときだけ効く。

だからこのシステムは、水準よりも順位・シェア・モメンタムのほうが信用できる。
エリア合計のクチコミ量（窓内 1000 件超）と自社シェアは相対的に締まった数字になる。

### 前期比は季節性を差し引いて読む

前期比は 1 つ前の同じ長さの窓との比較なので、季節性をまるごと含む。90 日窓なら
桜シーズンと初夏を比べることになり、全施設が揃って 2 桁のマイナスになる。これを
競争力の低下と読むと必ず間違える。

ダッシュボードはエリア全体の増減を併記し、各施設の括弧内に**市場調整後**の値を出す。
見るべきはこちら。市場が -11% のときに自社が -25% なら、季節ではなくシェアを
失っている。本来は前年同期比が正しいが、それには 15 か月ぶんの観測が要る。

## 出力の読み方

| セクション | 何を見るか |
|---|---|
| 01 今日の判断 | 自社と競合中央値の差。差が誤差の内側なら動かさない |
| 02 需要リボン | エリア全体の需要量と、そのうち自社の取り分。帯が細ればシェア喪失 |
| 03 コンプセット推定稼働 | 絶対値ではなく順位とモメンタム。`±` より小さい差は読まない |
| — 前期比 | 素の値は季節性を含む。**括弧内の市場調整後の値**で読む |
| 04 推定の土台 | 投稿率が実測か固定値か、実績との誤差が何 pt か |
| 05 シグナル | ルール逸脱時のみ人が介入する項目 |

判断ロジックは自社と競合中央値（自社を含めない）の差だけで決める。既定は
「動かさない」。評価が `rating_floor` を割っている間は、値上げ余地があっても
引き上げを凍結する。低評価のまま単価を上げると露出と稼働の両方を失うため。

## 設定

`config.json`。主なもの:

| キー | 意味 |
|---|---|
| `window_days` | 集計窓の長さ。短くすると誤差が急に広がる |
| `estimation.review_lag_days` | 滞在から投稿までの平均遅延日数 |
| `estimation.unstable_tail_days` | 遅延分布のばらつきを吸収する猶予 |
| `estimation.high/medium_confidence_margin_pt` | 信頼度の区切り（区間の半幅） |
| `review_rate.mode` | `calibrated`（自社実績で実測）/ `fixed`（固定値） |
| `properties[].restaurant_review_share` | 外来レビューの推定比率。感度分析が必要 |
| `pricing_rules.rating_floor` | これを下回る間は値上げを凍結 |
| `pricing_rules.raise_gap_pt` / `cut_gap_pt` | 判断を分ける差（ポイント） |

自社 PMS 実績は `date,rooms_sold` の CSV（既定 `data/pms_actuals.csv`）。

## 構成

```
kanoya/
  config.py       設定の読み込みと検証
  places.py       Places API クライアント（rating と userRatingCount のみ）
  store.py        スナップショットの永続化（JSONL、追記のみ）
  reviews.py      差分 → 外来控除 → 滞在日ベースの時系列
  calibration.py  投稿率の実測、Wilson 区間、backtest
  occupancy.py    稼働率の推定と 95% 区間
  signals.py      ルール逸脱の検出
  verdict.py      今日の判断
  render.py       ダッシュボード HTML
  pipeline.py     観測 → レポートの一本道
  demo.py         合成データ生成（手法そのものの検証用）
  cli.py          poll / report / demo
```

`demo.py` は本番と逆向きに動く。真の稼働率を置いてレビューを発生させ、投稿遅延を
与えて累計に積む。推定側がその真値をどれだけ復元できるかで手法を検証できる
（`tests/test_pipeline_render.py`）。

## 運用上の注意

- 推定稼働率の絶対値を投資家向け資料やオーナー報告にそのまま転載しないこと。
  用途は自社の値付け判断に限る。
- `poll` は 1 施設の失敗で全体を落とさない。欠測日は後段が線形に按分するが、
  連続して落ちると推定が鈍る。cron の失敗は監視すること。
- 施設が改称・統合されると `place_id` が変わることがある。`userRatingCount` が
  不連続に動いたら設定を確認する。
