# 奈良春日 鹿のや ｜ レベニュー・インテリジェンス

全5室の宿の値付け判断のために、コンプセットの**需要**を推定する。
Google Places の累計レビュー件数を毎日記録し、その増分から各施設の稼働を逆算する。

**レートは推定しない。** Places API は競合の宿泊料金を返さないし、OTA 画面の
スクレイピングは規約違反なので実装していない。実レートは正規ライセンスの
レートショッパーで別途取得し、ここで出る需要判断と突き合わせて使う。

```
                    毎日 1 回
Places API ──────────────────▶ snapshots.jsonl   累計レビュー件数の記録
                                     │
                                     ▼
                              日次増分を取る          delta = count[d] - count[d-1]
                                     │
                                     ▼
                          投稿日 → 滞在日に引き戻す    -10 日
                                     │
                                     ▼
                            外来レビューを控除        × (1 - restaurant_review_share)
                                     │
        PMS 実績 ────▶ 投稿率 p を実測 ──┤            p = 自社レビュー ÷ 自社実売室数
                                     ▼
                     推定稼働 = レビュー ÷ p ÷ (客室数 × 90)
                                     │
                                     ▼
                      判断・シグナル ──▶ dist/index.html
```

## なぜ「毎日記録」なのか

Places API はレビュー本文を**最大 5 件**しか返さない。過去 90 日のレビュー時系列を
API から直接取ることはできない。取れるのは `userRatingCount`（累計件数）と `rating` だけ。

したがって時系列は自分で作るしかない。`poll` を毎日走らせ、累計件数の差分を蓄積する。
**この蓄積を始めた日より前には遡れない。** 導入初日にダッシュボードは出ない。
90 日窓が埋まるまで信頼度は「低」のままになる。

## 使い方

```bash
# 毎日 1 回（cron 推奨）。1 日飛ばすとその日の増分が失われる
export GOOGLE_MAPS_API_KEY=...
python -m kanoya poll

# ダッシュボードを書き出す
python -m kanoya build              # → dist/index.html

# 端末で判断だけ見る
python -m kanoya report

# 投稿率とバックテストを確認する
python -m kanoya calibrate
```

`--date` で基準日を指定できる（過去日での再現・検証用）。

### cron の例

```cron
# 毎朝 4:05 に取得し、4:10 にダッシュボードを更新する
5 4 * * *  cd /srv/kanoya && GOOGLE_MAPS_API_KEY=... python -m kanoya poll >> log/poll.log 2>&1
10 4 * * * cd /srv/kanoya && python -m kanoya build >> log/build.log 2>&1
```

`poll` は 1 施設が失敗しても他を止めない（全滅時のみ終了コード 1）。
欠測日が出た場合、その区間の増分は日数で等分される。

## 入力

### `config.json`

| 項目 | 意味 |
|---|---|
| `property` / `comp_set` | 施設定義。`rooms` は推定の分母、`place_id` は poll の対象 |
| `restaurant_review_share` | レビューのうち外来客（レストラン・宴会）由来と見なす比率。この分を控除する |
| `estimation.window_days` | 集計窓。既定 90 日 |
| `estimation.review_lag_days` | 滞在から投稿までの平均遅延。既定 10 日 |
| `estimation.calibration_days` | 自社 PMS と突合して投稿率を実測する日数 |
| `estimation.confidence_*_rse` | 信頼度 高/中 の境界（推定稼働率の相対標準誤差） |
| `rules.hold_band_pt` | この pt 差までは「据え置き」。誤差の範囲で BAR を動かさないため |
| `rules.rating_floor` | 評価がこれを下回ったら引き上げを凍結する |
| `demand_events` | 需要暦。リボンの縦線とリードタイム通知に使う |

### `data/pms_actuals.csv`

自社の日次実売室数。`date,rooms_sold,rooms_available`。
**これがないと投稿率を実測できず、システム全体が成立しない。**

## 推定の中身

### 投稿率 p

```
p = 自社の突合レビュー数 ÷ 自社の実売室数
```

競合にも同じ p を当てる。区間は Wilson スコア区間（Wald 近似だと p が小さいとき
下限が負に振れる）。サンプルデータでは `p = 178 / 929 = 19.2%`、95%CI 16.8〜21.8%。

### バックテスト

投稿率を検証しないかぎり、競合の推定稼働率は「それらしい数字」でしかない。
突合窓の中に**本番と同じ 90 日**の区間を等間隔で 6 本取り、各区間の投稿率を
leave-one-out で求めて実績と突き合わせる。

検証区間を本番より短く取ってはいけない。レビュー件数の計数誤差は区間が短いほど
効くので、ダッシュボードが一度も使わない粒度で誤差を測ることになる。
（区間は重複するため 6 本は独立ではない。誤差の**大きさの目安**として読む。）

平均誤差が推定値の用途を決める:

| 平均誤差 | 使ってよい範囲 |
|---|---|
| ≤ 3pt | 水準の議論に使える |
| ≤ 7pt | 相対比較のみ |
| > 7pt | 方向感のみ |

**サンプルデータでの実測は 4.8pt、つまり「相対比較のみ」。**
全5室・90日で約 65 件のレビューしか出ないため、計数誤差だけで相対 12% 前後
（稼働率にして ±9pt 前後）が乗る。これは手法の限界であって実装の不備ではない。
施設間の順位とモメンタムは読めるが、稼働率の水準そのものは主張できない。

### 信頼度

推定稼働率の相対標準誤差から決まる。誤差源は 2 つ:

```
相対誤差 = √( (1/√レビュー件数)²  +  (投稿率の相対標準誤差)² )
             計数のゆらぎ            全施設に共通して効く分
```

窓の被覆率が 8 割を切る施設は、件数によらず「低」。

## 判断ルール

自社と競合中央値の差で決まる。差が `hold_band_pt` 未満なら動かさない
（推定の相対誤差が 15% 前後あるので、小さな差を根拠に動かすとノイズを追う）。

- 差 ≥ +8pt → **強気**（引き上げ）
- −8pt 〜 +8pt → **据え置き**
- 差 ≤ −8pt → **需要獲得**（レートより先に露出・写真・最低泊数を点検）

以下は判断を上書きする:

- **評価が下限割れ** → 引き上げを凍結。露出を失う損失のほうが大きい
- **信頼度が「低」** → 差を根拠にしない

## 開発

```bash
pip install pytest
python -m pytest tests -q
```

外部依存なし（標準ライブラリのみ）。テストは Places API を叩かない。

### サンプルデータ

```bash
python scripts/generate_sample_data.py
```

決定的（固定シード）。`data/` を再生成する。合成の因果の向きは実際と同じで、
まず PMS の実売室数を作り、そこから投稿率で間引いてレビューを生成する。
逆向きに作ると較正とバックテストが構造的に当たってしまい検証にならない。

レビューの日次配分には多項分布を使う。最大剰余法だと、1 日あたりの期待値が
1 を下回る系列では配分が「重みの大きい順に上位 N 日」へ退化し、稼働の高い日に
レビューが集中して較正が壊れる。

## 限界

1. 推定するのは**需要**であり**レート**ではない。
2. OTA・Google ホテル検索のスクレイピングは実装していない（規約違反）。
3. 投稿遅延は一律 10 日で引き戻している。実際は分布を持つので、直近 10 日の
   推定は不安定。基準日は「今日 − 10 日」に置いてこの区間を窓から外している。
4. `restaurant_review_share` は推定値。感度分析が必要。
5. 全5室では日次稼働は 0/20/40/60/80/100% しか取らない。**90 日窓の集計でのみ
   意味を持つ。日次の需要予測には使えない。**
6. 推定稼働率の絶対値を投資家向け資料やオーナー報告に転載しないこと。
   用途は自社の値付け判断に限る。
7. レビュー削除は累計件数を減らす。負の増分は 0 に丸めるため、削除が多い施設は
   需要を過小に見積もる。
