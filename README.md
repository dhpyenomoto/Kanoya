# 奈良春日 鹿のや ｜ レベニュー・インテリジェンス

Google Places の公開クチコミの**増分**から、コンプセット（自社＋競合5施設）の
**需要＝推定稼働率**を日次で追い、値付け判断を1枚のHTMLに落とすシステム。

全5室の宿にレベニューマネージャーは置けない。置けない代わりに、
「今日、価格を動かすべきか」への答えを毎朝1行で出すのがこのシステムの役目。

```
python -m kanoya seed-demo      # デモデータ生成（APIキー不要）
python -m kanoya report         # dist/index.html を生成
open dist/index.html
```

生成済みのサンプルは [`dist/index.html`](dist/index.html)。

---

## 何を推定し、何を推定しないか

推定するのは**需要**であって**レート**ではない。ここは曖昧にしない。

| | 扱い |
|---|---|
| 競合の推定稼働率 | 推定する（本システムの中心） |
| エリア需要の総量とその取り分 | 推定する |
| 競合の販売レート | **推定しない**。Places API は返さない |
| OTA画面・Googleホテル検索のスクレイピング | **実装しない**。規約違反 |

実レートが必要なら、正規ライセンスのレートショッパー（メトロエンジン等）を
別系統で契約し、このダッシュボードの需要判断と突き合わせる。
本システムは需要側だけを担当する。

## 推定の仕組み

```
   毎日の userRatingCount   ──差分──▶  投稿日ベースの日次レビュー数
                                              │
                            外来客ぶんを控除（restaurant_review_share）
                                              │
                            投稿遅延ぶん巻き戻し（review_lag_days）
                                              ▼
                                    滞在日ベースの日次レビュー数
                                              │
                                        ÷ 投稿率
                                              ▼
                                       推定販売室数
                                              │
                                    ÷（客室数 × 日数）
                                              ▼
                                       推定稼働率
```

**Places API は日次のレビュー件数を返さない。** 返すのは現時点の累計件数と
直近5件の本文だけである。したがって増分は「毎日取得して差分を取る」以外に
得る方法がない。`snapshots` テーブルがこのシステムの唯一の一次記録であり、
収集を止めた期間は永久に復元できない。

**投稿率は仮定ではなく実測する。** 自社PMSの日次販売室数（`data/pms_actuals.csv`）と
自社のレビュー増分を突き合わせ、`宿泊客由来レビュー ÷ 実販売室数` として算出する。
デモデータでは 261日 / 929室 / 178件 → **10.5%**（95%CI 8.5〜12.6%）。
この率を競合にも適用する。

**そして、その推定が当たっているかを毎回検証する。** 突合期間を6分割し、
各区間で推定稼働と自社実績を比べた平均絶対誤差を出す。誤差が大きければ
ダッシュボードは自分から「この数字は水準比較に使うな」と言う。

| 平均絶対誤差 | 使ってよい範囲 |
|---|---|
| ≤ 3.0pt | 水準の議論に使える |
| ≤ 6.0pt | 推移の議論に限る |
| > 6.0pt | 方向感のみ（判断保留） |

## 値付けルール

判断は自社の推定稼働と競合中央値の差だけで決める。

| 条件 | 判断 |
|---|---|
| 差 ≥ +8pt | 引き上げ検討 |
| −8pt < 差 < +8pt | **据え置き** |
| 差 ≤ −8pt | 要注意（引き下げ検討） |
| 評価 < 4.6 | 引き上げを凍結（露出が先に落ちるため） |
| 推定精度が「方向感のみ」 | 判断保留 |

毎日なにか動かす理由を探すダッシュボードはレベニュー管理では害になる。
差が閾値内なら「据え置き」とはっきり言う。シグナルも平常時は空でよい。

## コマンド

| コマンド | 用途 |
|---|---|
| `python -m kanoya collect` | 日次スナップショット取得（`GOOGLE_PLACES_API_KEY` 必須） |
| `python -m kanoya report -o dist/index.html` | ダッシュボード生成 |
| `python -m kanoya calibrate` | 投稿率・推定精度・推定投稿遅延を表示 |
| `python -m kanoya seed-demo` | デモ用データ生成（APIキー不要） |

`collect` は1日1回、cron で回す。1日1点に正規化されるので重複実行は安全。

```cron
15 4 * * * cd /srv/kanoya && GOOGLE_PLACES_API_KEY=... python -m kanoya collect >> log/collect.log 2>&1
30 4 * * * cd /srv/kanoya && python -m kanoya report -o /var/www/kanoya/index.html
```

`calibrate` は投稿遅延を自社データから推定して表示する（PMS実績とレビューの
相互相関のピーク）。`config.json` の `review_lag_days` と食い違ったら設定を直す。

## 設定（config.json）

推定ロジックに定数を直書きしていない。触るのは全部ここ。

- `restaurant_review_share` — 外来客レビューの推定比率。**感度分析が必要な最重要パラメータ。**
  オーベルジュや料理旅館では 0.2〜0.55 程度になる。ここを外すと稼働推定がそのままずれる。
- `review_lag_days` — 滞在から投稿までの平均遅延。この日数ぶん、直近は判断に使わない。
- `window_days` / `ribbon_days` — 集計窓とリボンの表示期間。
- `pricing_rules` — 上表の閾値。レベニュー担当が直接触る想定。
- `demand_events` — 需要暦。リボンに縦線が入り、`event_lead_days` 前にシグナルが出る。

## 構成

```
kanoya/
  places.py      Google Places API (New) クライアント
  store.py       スナップショット保管庫（SQLite）— 唯一の一次記録
  collect.py     日次収集ジョブ
  timeline.py    累計差分 → 日次系列（外来控除・遅延巻き戻し）
  calibrate.py   投稿率の実測・バックテスト・遅延推定
  occupancy.py   推定稼働率とエリアシェア
  signals.py     シグナル判定
  verdict.py     今日の判断
  ribbon.py      需要リボンの SVG
  render.py      HTML描画
tools/
  make_fixtures.py  デモ用データ生成
```

依存は標準ライブラリのみ。テストのみ pytest を使う（`python -m pytest`）。

## 限界

1. **レートは分からない。** 稼働が高い＝適正価格、ではない。安く売って埋めている
   可能性は常にある。値付けの最終判断には実レートを併せて見る。
2. **母数が小さい。** 全5室では日次稼働は 0/20/40/60/80/100% しか取らない。
   本手法は90日窓の集計でのみ意味を持ち、日次の需要予測には使えない。
3. **投稿遅延は施設ごとに違う。** 自社でしか実測できないため、競合には同じ遅延を
   仮定している。直近 `review_lag_days` 日ぶんは判断から除外している。
4. **外来客レビューの控除は推定。** `restaurant_review_share` は実測値ではない。
5. **エリア合計は追跡中の施設の合計。** エリア全施設ではない。`compset` を
   足し引きするとシェアの水準が動くので、変更したら過去分と比べない。
6. **絶対値を外に出さない。** 推定稼働率をそのまま投資家向け資料やオーナー報告に
   転載しないこと。用途は自社の値付け判断に限る。

`data/` 以下のデモデータは `seed-demo` が生成する合成データであり、
実在の施設の稼働ではない。
