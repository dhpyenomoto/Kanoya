# 奈良春日 鹿のや ｜ レベニュー・インテリジェンス

Google Places のクチコミ累計件数の推移だけを入力に、コンプセットの**需要**を推定し、
今日の値付け判断を 1 枚の静的 HTML にまとめる。

推定するのは需要であってレートではない。Places API は競合の宿泊料金を返さないし、
OTA 画面や Google ホテル検索画面のスクレイピングは規約違反なので実装していない。
実レートが要るなら正規ライセンスのレートショッパーを別系統で用意し、この需要判断と突き合わせる。

```
python3 -m kanoya demo                     # デモ用の履歴を合成（初回はこれで挙動を見る）
python3 -m kanoya render -o dist/index.html
open dist/index.html
```

依存は標準ライブラリだけ。Python 3.11 以上。

---

## 仕組み

```
Places API (userRatingCount)
        │  毎日 1 回スナップショット
        ▼
   SQLite 履歴                      store.py
        │  連続スナップショットの差分 → 日次増分
        │  投稿日を review_lag_days 引き戻して滞在日へ
        │  restaurant_review_share を控除
        ▼
   滞在日ベースのクチコミ系列        series.py
        │
        ├─ 自社 PMS 実績と突合 → レビュー投稿率        calibrate.py
        │
        ▼
   推定販売室数 = クチコミ ÷ 投稿率                    estimate.py
   推定稼働率   = 推定販売室数 ÷ (客室数 × 窓日数)
        │
        ▼
   判断とシグナル                                      decide.py
        ▼
   静的 HTML                                           render.py
```

**Places API は過去に遡れない。** 返るのはその時点の累計件数だけで、日次の推移は返らない。
つまり履歴は毎日取り続けて初めて貯まる。導入初日には何も出ない。cron で回す:

```cron
15 4 * * *  cd /srv/kanoya && GOOGLE_PLACES_API_KEY=... python3 -m kanoya snapshot
30 4 * * *  cd /srv/kanoya && python3 -m kanoya render -o /var/www/kanoya/index.html
```

## コマンド

| コマンド | 用途 |
|---|---|
| `demo` | 合成のスナップショット履歴と PMS 実績を作る。seed 固定で再現する |
| `snapshot` | Places API から現在値を 1 回取得して保存する。cron から毎日叩く |
| `calibrate` | レビュー投稿率の実測値と、その検証結果を JSON で出す |
| `estimate` | コンプセットの推定稼働を表で出す（`--json` あり） |
| `render` | ダッシュボード HTML を書き出す |

共通オプションは `--config`（既定 `config.json`）と `--db`。
`--db` を省くと `data/snapshots.db`、無ければ `data/snapshots.demo.db` を使う。
`--as-of` で基準日を指定できる（過去日を指定すればその日のダッシュボードが再現する）。

## 設定

`config.json` に全部入っている。最低限やることは 2 つ。

1. `property` と `comp_set` の `place_id` を実際の Place ID に置き換える
2. `data/pms_actuals.csv` を自社 PMS の実績で置き換える（`date,rooms_sold[,rooms_available]`）

主なつまみ:

| キー | 意味 |
|---|---|
| `rooms` | 客室数。推定稼働率の分母 |
| `restaurant_review_share` | 外来客レビューの混入率。オーベルジュ併設なら必須。**推定値なので感度分析が要る** |
| `estimation.review_lag_days` | 滞在から投稿までの平均日数。窓の終端もこの分だけ手前に引く |
| `estimation.confidence_*_band_pt` | 信頼度 高／中 の境目。推定幅（pt）で決める |
| `rules.rating_floor` | この評価を割ったら BAR 引き上げを凍結する |
| `rules.raise_threshold_pt` / `cut_threshold_pt` | 競合中央値との差が何 pt で動くか |
| `calibration.usable_mae_pt` | 検証誤差がこれ以下なら「水準の議論に使える」と表示する |

## 精度について（読む前に必ず）

クチコミ件数は計数値なので、推定稼働率には **±1.96/√(件数)** の相対誤差が乗る。
`tests/test_pipeline.py` は合成データの真の答えと突き合わせてこれを実測している。
系統誤差はほぼ無い（平均 −2pt 前後）が、施設ごとのばらつきは規模で決まる:

| 施設 | 90日窓のクチコミ | 推定幅（95%） | 実測誤差 |
|---|---|---|---|
| 40室のフルサービス | 約 250 件 | ±8pt | 0〜1pt |
| 15室のブティック | 約 100 件 | ±14pt | 1〜3pt |
| **5室の自社** | **約 40 件** | **±17〜28pt** | **10〜15pt** |

つまり **5室規模では、自社の稼働率をクチコミから読むことはできない。**
±25pt の幅を持つ数字で 5pt の値上げ判断はできない。この事実は隠さず、
表の信頼度列と `04 推定の土台` に幅をそのまま出している。判断ロジックも、
競合中央値との差がノイズ幅の内側なら「据え置き」に倒す（`decide.py`）。

その代わり、この手法が効くのは次の 2 つ:

- **規模の大きい競合の水準とモメンタム。** 件数が多いほど幅は狭くなる。40室級なら ±8pt で読める
- **エリア全体の需要の形。** 全施設を合算した需要リボンは件数が多く、季節とイベントの山が素直に出る

自社の稼働率は PMS を見ればよい。このダッシュボードが答えるのは
「**周りがどうなっているか**」であって「自社がどうか」ではない。

### 投稿率のキャリブレーション

投稿率は自社 PMS 実績とクチコミ系列の突合で実測する。全体に効く係数なので、
どこから来た数字か・実績とどれだけずれるかを必ず添えて表示する。

- 係数は**現在の窓より前**の期間だけで作る。窓内の実績はホールドアウトとして検証に使う
- バックテストは leave-one-out（自分を含まない係数で自分を当てにいく）
- 実績が無ければ `config.default_review_rate` にフォールバックし、その旨をシグナルに出す
- 投稿率自体の不確かさは全施設に同じ倍率で効くので、**施設間の比較には影響せず、水準の議論にだけ影響する**

## テスト

```
python3 -m unittest discover -s tests -v
```

`tests/test_pipeline.py` が本体。合成データを真の答えとして、
系統誤差・区間の妥当性・規模と精度の関係を実際に測っている。

## 限界

1. Places API は宿泊料金を返さない。推定するのは需要であってレートではない
2. OTA・Google ホテル検索画面のスクレイピングは規約違反。実装していない
3. 投稿遅延の分布は施設ごとに違う。固定の `review_lag_days` で引き戻しているので直近は不安定
4. `restaurant_review_share` は推定値。オーベルジュ併設の競合ほど誤差が乗る
5. 全5室では日次稼働は 0/20/40/60/80/100% しか取らない。日次の需要予測には使えない
6. Google がレビューを削除すると累計が減る。減少分は 0 に切り捨てて記録している
7. **推定稼働率の絶対値を投資家向け資料やオーナー報告に転載しないこと。** 用途は自社の値付け判断に限る
