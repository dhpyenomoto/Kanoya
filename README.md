# 鹿のや レベニュー・インテリジェンス

奈良春日 鹿のや（全5室）の値付け判断のために、Google Places の公開シグナルから
コンプセットの**需要**を推定する。レートは推定しない。

```
kanoya snapshot   # 毎日1回。累計レビュー件数を台帳に追記する
kanoya report     # 台帳から推定してダッシュボードHTMLを出す
kanoya check      # 設定と台帳の健全性を確認する
kanoya demo       # 合成台帳を生成する（本番データが貯まるまでの検証用）
```

依存ライブラリなし。Python 3.11 以上。

---

## このシステムが答える問い

> 今日、BAR を上げるか、据え置くか、下げるか。

答えるのは 1 問だけ。ダッシュボードの他の節はすべてこの判断の根拠でしかない。

## このシステムが答えない問い

**競合がいくらで売っているか。** Google Places API は宿泊料金を返さない。
OTA 画面や Google ホテル検索画面のスクレイピングは規約違反であり、実装していない。
実レートは正規ライセンスのレートショッパー（メトロエンジン等）で別途取得し、
ここで出した需要判断と突き合わせること。

推定しているのは**需要**であって**レート**ではない。この区別が崩れた瞬間に、
このダッシュボードは害になる。

---

## 手法

```
推定稼働率 = レビュー増分 ÷ レビュー投稿率 ÷ 客室数 ÷ 日数
```

### 1. なぜ「増分」なのか

Places API が返すレビュー本文は 1 施設あたり最大 5 件。本文をいくら集めても
発生速度は測れない。測れるのは `userRatingCount`（累計件数）を毎日記録した差分だけ。

**この手法は過去に遡れない。** 昨日の累計件数は、昨日記録していなければ
永久に手に入らない。だから `kanoya snapshot` を止めてはいけない。
台帳が 90 日ぶん貯まるまで、このダッシュボードは動かない。

### 2. 投稿率は自社実績で実測する

「泊まった人の何%がレビューを書くか」は施設によって違う。業界の一般値を
借りてくると、その誤差がそのまま全競合の推定値に乗る。

`data/pms_actuals.csv`（`date,rooms_sold,rooms_available`）を投入すると、
自社の販売室数と自社のレビュー増分を突合して投稿率を実測する。
95% 信頼区間は Wilson スコア区間。この実測値を競合にも適用する。

PMS 実績が無い場合はフォールバック値で動くが、そのときは
「投稿率が未実測」のシグナルが立ち、稼働率の絶対値を読んではいけない状態になる。

### 3. 投稿の遅延を引き戻す

レビューは滞在から平均 10 日遅れて投稿される（`review_lag_days`）。
増分をこの日数だけ過去にずらして滞在日に割り当てる。
その結果、台帳の末尾はまだ投稿が出そろっていないので、直近 10 日
（`unstable_tail_days`）は窓から外す。8/15 に走らせた推定窓は 5/8〜8/5 になる。

### 4. レストラン併設施設を補正する

オーベルジュや食事処を持つ施設は、外来客のレビューが宿泊客のそれに混ざる。
`restaurant_review_share` でその比率を控除する。**これは推定値であり、
感度分析が必要**。鹿のやの 0.45 という値を疑うところから運用を始めること。

### 5. 前期比はエリア調整済み

奈良の需要は季節差が大きい。90 日窓を 90 日ずらすと、桜と真夏を比べることになる。
素の前期比は毎年夏に全施設が二桁マイナスになり、判断に使えない。

そこでエリア全体（信頼度が確保できた全施設）の前期比の中央値を差し引き、
「市場に対して取れているか」だけを残している。表の値は市場との差分であって、
自社の実数の増減ではない。

### 6. 信頼度

レビュー件数 k のカウント過程の相対標準誤差は 1/√k。

| 信頼度 | 相対標準誤差 | 意味 |
|---|---|---|
| 高 | 15% 未満 | 水準の比較に使える |
| 中 | 25% 未満 | 順位とモメンタムのみ |
| 低 | それ以上 | 読まない。中央値の算出からも除外する |

月に数件しかレビューが立たない施設は、数字が出ていても読んではいけない。

### 7. 後方検証

投稿率を自社実績で決めている以上、全期間の平均は定義上ほぼ一致する。
意味があるのは「窓を切ったときに月ごとにどれだけ振れるか」で、
その振れ幅がそのまま競合の推定値に乗る誤差の下限になる。

平均誤差が 5pt を超えたら、推定稼働率の**絶対水準は議論に使えない**。
その場合は判断ロジックが自動的にモメンタムのみに切り替わる。

---

## 判断ルール

自社と競合中央値（信頼度「低」を除く）の差を pt で見る。

| 条件 | 判断 |
|---|---|
| 自社の信頼度が「低」 | 判断保留。動かさない |
| 比較できる競合が無い | 判断保留 |
| 後方検証の誤差が 5pt 超 | 水準では判断しない。モメンタムのみ |
| 差 ≥ +6pt かつ 評価 ≥ 下限 | **引き上げ** |
| 差 ≥ +6pt だが 評価 < 下限 | **据え置き（凍結）** |
| 差 ≤ −6pt | **引き下げ検討** |
| それ以外 | **据え置き** |

**評価が下限を下回るあいだは引き上げを凍結する。** 評価が落ちている状態での
値上げは、露出低下と稼働喪失を同時に招く。ただし凍結するのは引き上げだけで、
引き下げ判断は止めない。

## 使い方

### 初期設定

```bash
cp config.example.json config.json
```

`config.json` の `place_id` を実際の Google Place ID に差し替える。
プレースホルダのままでも構文は通るが、Places API が 404 を返す。

`config.json` は `.gitignore` されている。GitHub Actions で日次観測を回すなら、
自分の設定を明示的にコミットすること（API キーは含まれない。Secrets に置く）。

```bash
export GOOGLE_PLACES_API_KEY=...
```

### 毎日

```bash
kanoya snapshot
```

同じ日に二度走らせても重複記録しない。1 施設が失敗しても他は記録し、
終了コードは 0 のまま（日次ジョブを 1 施設の欠測で止めないため）。
`.github/workflows/snapshot.yml` に GitHub Actions 版がある。

### 判断するとき

```bash
kanoya report
open dist/index.html
```

端末に判断と推定稼働の要約が出る。HTML を開かずに判断だけ見てもよい。

### 台帳が貯まるまで

```bash
kanoya --config config.demo.json demo
kanoya --config config.demo.json report
open dist/demo.html
```

`config.demo.json` は本番設定とは別系統で、`data/*.demo.*` にしか書かない。
本物の観測台帳が合成データで汚れることはない。

生成される数字は実在の施設のものではない。`place_id` が `demo-` で始まっている限り
出力は合成データであり、端末にもその旨が出る。逆に、実 `place_id` を指す設定で
`demo` を走らせようとすると `--force` なしでは止まる。

## 設定

| キー | 意味 |
|---|---|
| `property.rooms` | 客室数。推定稼働の分母 |
| `property.restaurant_review_share` | 外来客レビューの控除率 |
| `property.rating_floor` | これを下回るあいだ引き上げを凍結する |
| `estimation.window_days` | 推定窓（既定 90 日） |
| `estimation.review_lag_days` | 滞在→投稿の平均遅延（既定 10 日） |
| `estimation.unstable_tail_days` | 窓から外す直近日数（既定 10 日） |
| `decision.raise_threshold_pt` | 引き上げに必要な対中央値の差 |
| `decision.share_drop_alert_pt` | シェア低下の警告しきい値 |
| `demand_events` | 需要暦。判断には使わず、仕込みの期限として表示する |

---

## 限界

1. **全5室では日次の稼働率は 0/20/40/60/80/100% しか取らない。**
   この手法は 90 日窓の集計でのみ意味を持つ。日次の需要予測には使えない。
2. **投稿率は施設ごとに違う。** 自社の実測値を競合に適用しているが、
   客層・言語・OTA 構成が違えば投稿率も違う。競合間の比較には
   この仮定の誤差が乗っている。
3. **投稿遅延の分布も施設ごとに違う。** 単一の平均値で引き戻している。
4. **推定稼働率の絶対値を投資家向け資料やオーナー報告に転載しないこと。**
   用途は自社の値付け判断に限る。

## テスト

```bash
python3 -m unittest discover -s tests
```

`tests/test_pipeline.py` が統合テスト。`demo.py` は「投稿率 10.5% の世界」を作り、
`calibrate.py` はそれを知らないまま自社 PMS 実績から投稿率を推定し直す。
両者が一致することが、遅延の引き戻し・レストラン控除・窓の切り方が
互いに矛盾していないことの証明になっている。
