判断の記録

「なぜそうしなかったか」は、コードにも設定にも残らない。あとから見た人が 善意で同じ検討をやり直し、同じ結論に辿り着けないまま逆の変更を入れる。 ここはそのための文書である。

1. min_expected_rooms = 1.0 を維持する

決定

内部需要シグナルの無効化しきい値 min_expected_rooms を 1.0室のまま 維持する。下げない。

根拠

閾値を 0.2 / 0.3 / 0.5 / 0.7 / 1.0 と振って測った（docs/08 に全表）。 決め手は「閾値を下げて動いた日が、実績に近づいたのか離れたのか」である。

閾値 動いた日 近づいた 離れた 誤差の平均変化
0.2 77日 39日 38日 +156円
0.3 77日 39日 38日 +156円
0.5 45日 22日 23日 +204円

近づく日と離れる日がほぼ半々で、誤差の平均はむしろ広がっている。 これは情報が増えていないことの直接の証拠である。閾値を下げると有効帯は 広がるが、広がった帯が運んでいるのはノイズであって需要ではない。

集計値では判定できない — 見直すときの注意

推奨部屋代の中央値（実売室夜で重み付け）は、

閾値 0.5 → 42,000円（実績比 -2.3%）
閾値 1.0 → 42,000円（実績比 -2.3%）

でまったく差が出ない。集計値だけを見ていたら「0.5でも問題ない」と 判断してしまう。実際には45日分の推奨が平均6,200円動いており、その動きは 改善22日・悪化23日とほぼ相殺されているだけである。

将来この閾値を見直すときは、集計値ではなく日ごとの改善率で判定すること。 集計値では「ノイズを足しているだけの状態」と「正しく効いている状態」を 区別できない。

再現は python3 scripts/sweep_min_expected.py（測定専用・設定は変更しない）。

2. 検証方法そのものの限界

「実績価格との一致は、正しさの証明ではない」

推奨部屋代（実売室夜で重み付け）42,000円が実績43,001円の -2.3% に 収まっている。これを精度が高いと読んではいけない。

比較対象の「実績」は、過去の値付け判断の結果である。そこには

  • 2026年6〜7月の失敗した値上げ実験 （早期54,910円で2ヶ月9件 → 31%下げた37,824円で20件成約）
  • 満室の土曜を38,071円で売った日（2026-03-28・PEAK）
  • 季節係数と逆転した実勢（PEAK 47,001円 < HIGH 51,685円。docs/07）

が含まれている。

実績を再現できたということは、過去の判断を再現できたということであって、 最適な価格に近づいたことの証明ではない。 仮に過去の値付けが systematically 安すぎたなら、それに一致するエンジンもまた安すぎる。

いま何が判定不能か

外部の基準がない。競合レート（comp_rates_collected.csv）は今もフィクスチャで、 実データなのはOTBだけである。したがって

  • 自社の価格が市場に対して高いのか安いのか
  • 稼働28%が値付けの結果なのか、需要の上限なのか

のどちらも判定できない。競合の実勢価格が接続されるまで、エンジン出力の 良否は原理的に判定不能である。

現在の -2.3% は「エンジンが過去の自社の値付けと同じ土俵に乗った」ことを 示すに留まる。それ以上でも以下でもない。

次の一歩は P16（コンペセットの再ティア化）ではなく、その前提となる 競合実勢価格の取得である（SerpApi 月$25〜75）。

3. git 履歴は書き換えない

決定

競合施設の実名は HEAD から除去した（docs / site / tests / 設定を含む 追跡ファイル89件でヒット0件）。ただし過去のコミットには残っている。

これに対し、git filter-repo 等による履歴の書き換えは行わない。

理由

  1. 全コミットのハッシュが変わる。 既存のPR・ブランチ・セッションログ・ コミットへの参照がすべて壊れる。本リポジトリは変更の経緯そのものが 資産であり、それを切り離す代償が大きい
  2. Private 化すれば履歴ごと非公開になる。 目的（社外から読めない状態）は Private 化だけで達成される。履歴書き換えはその上に追加の破壊を加えるだけで、 達成される状態は同じ
  3. 書き換えても、すでにクローン・フォーク・キャッシュされたものには届かない

対応方針

対応方針は「Private 化」であり「履歴書き換え」ではない。

HEAD からの除去は、Private 化までの間の露出を減らすためと、Private 化後も 「実名は1か所（Kanoya-data）にしか無い」という構造を保つためである。 分離した情報の戻しかたは README の「匿名化を解除する」に書いてある。

社内資料。競合施設の実名・価格ポジション・収益前提を含みます。 取り扱いにご注意ください。
