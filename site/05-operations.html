収集パイプライン 運用手順書

近隣競合の発見 → OTA掲出価格の収集 → ADR判断 までを回すための実務手順。 設計思想は データ収集設計、実装は engine/kanoya_rm/sources/ および engine/scripts/。

1. パイプラインの全体像

 ①発見                    ②人手確定              ③収集                  ④判断
 discover_compset.py  →  compset_overrides  →  collect_rates.py  →  survey_report.py
 Places API              食事条件・客室数        Google Hotels        市場ポジション
 近隣宿泊施設を列挙        （人が確定）           階層化スケジュール      ＋ADR推奨
      ↓                       ↓                      ↓                    ↓
 compset.generated.json   compset.json         comp_rates_*.csv    market_survey.csv

②を飛ばしてはいけません。 Places API も Google Hotels も、 「その価格が素泊まりなのか2食付きなのか」「人数課金なのか室課金なのか」を返しません。 ここを人が確定しないままNAR正規化すると、価格ポジション判断が体系的に歪み、 しかもエンジン内では正常値に見えます。検出できない種類の誤りです。

1.5 調査条件の入力（「本日」と「調べたい日程」）

入力口は engine/config/survey_request.json の1か所です。全スクリプトがこれを読みます。

{
  "as_of": "today",
  "target": { "from": "today", "to": "+120d" },
  "conditions": { "adults": 2, "los": 1, "target_position": 1.15 }
}

1.5.1 2つの日付は別概念

混同しやすいので明示的に分けています。

項目 意味 例
as_of（調査基準日＝本日） いつ時点で見た市場か。データの取得日 今日／1週間前の時点を再現
target.from / to（調査対象期間） どの宿泊日を調べたいか 11月の紅葉期だけ／直近2週間

この2つは独立しています。「今日の時点で、11月の紅葉期だけを調べる」は正当な要求であり、 以前は対象期間の入口が無く常に「先120日」固定でした。

1.5.2 日付の書き方

固定日を書くと毎日書き換えることになるため、相対指定を使えるようにしています。

書き方 意味
today / 本日 調査基準日そのもの
2026-11-01 絶対日付
2026-11 月指定。from に書けばその月まるごと（月初〜月末）
+90d +12w +3m +1y 基準日からの相対
-7d 過去方向。as_of に書けば1週間前の時点を再現

1.5.3 その場で上書きする

設定ファイルを書き換えずに一度だけ別期間を見たい場合は、CLI引数が常に優先されます。

python3 scripts/survey_report.py --from 2026-11-01 --to 2026-11-30
python3 scripts/survey_report.py --from 2026-11              # 11月まるごと
python3 scripts/survey_report.py --from +30d --days 14       # 30日後から2週間
python3 scripts/collect_rates.py --as-of 2026-08-15 --from 2026-11 --plan-only

3スクリプト（discover_compset / collect_rates / survey_report）で 引数名は共通です。以前は同じ「本日」に --run-date と --snapshot の 2つの名前があったため、--as-of に統合しました（旧名も当面は動作します）。

1.5.4 期間を絞ると収集の挙動が変わる

62日以下の期間を明示指定した場合、階層化せず期間内の全宿泊日を取得します。 「11月を調べたい」に対し、週1スロットで4日分しか返さないのは要求に応えていないためです。 広い期間では従来どおり階層化します。--full / --tiered で明示的に上書きできます。

期間を絞ると費用も下がります（実行前に必ず表示されます）。

今回の収集     : 30 宿泊日（対象期間 30日中）
  今回の概算費用 : $0.45（30 リクエスト）

1.5.5 入力の検証

不正・危険な入力は実行前に止めるか、警告します。

入力 挙動
終了日 < 開始日 エラー。スタックトレースではなく直せる指示を表示
開始日が基準日より過去 基準日へ自動切り上げ＋警告（過去日は販売できない）
対象期間が全て過去 エラー
対象期間が収集ホライズンの外 警告（超過分はデータが存在しない旨を明示）
解釈できない書式 エラー＋使える形式の一覧を表示
基準日が実際の今日より未来 警告（再現・検証用途以外では設定ミスの可能性）

解決後の条件は全スクリプトの冒頭に必ず表示されます。何を調べているのかが 出力を見れば常に分かる状態にしています。

── 調査条件 ──────────────────────────────────────────────
  調査基準日（本日）: 2026-08-15
  調査対象期間      : 2026-11-01 〜 2026-11-30  （30泊分 / リードタイム 78〜107日）
  条件              : 2名1室 1泊 ／ 目標ポジション 1.15倍
  入力元            : survey_request.json（CLI引数があればそちらが優先）

2. 事前準備

2.1 APIキー

コードには一切書かず、環境変数から読みます。

export GOOGLE_PLACES_API_KEY='...'    # 施設発見・レビュー速度
export SERPAPI_API_KEY='...'          # 競合レート（主）
# 任意（セカンダリ／クロスチェック用）
export DATAFORSEO_LOGIN='...'
export DATAFORSEO_PASSWORD='...'

キーが無い状態でも、--source fixture で全工程をオフライン実行できます （擬似データのため判断には使えませんが、設計検証・デモ・CIには十分です）。

2.2 Places API 側の設定

  • Google Cloud プロジェクトで Places API (New) を有効化
  • APIキーに HTTPリファラ制限ではなく IP制限 をかける（サーバ実行のため）
  • 課金アラートを設定（フィールドマスクの階層で単価が変わるため）

sources.json の discovery では Pro ティア相当のフィールド （rating / userRatingCount / priceLevel）までを取得しています。 websiteUri 等の Enterprise ティアは単価が上がるため既定では取得しません。

3. 手順

① 近隣宿泊施設の発見（四半期に1回）

cd engine
python3 scripts/discover_compset.py --source places --radius 5000

半径5km内の宿泊施設を Places API で全列挙し、5軸類似度スコア （距離22% / 価格帯32% / 規模20% / 評判16% / レビュー量10%）で PRIMARY / SECONDARY / ASPIRATIONAL に分類します。

API上限への対処：searchNearby は1リクエスト最大20件しか返しません。 密集エリアでは「近い順に20件で打ち切られ、遠方の重要な競合が落ちる」という 取りこぼしが起きるため、探索円を同心リング上の小円群でタイル分割して網羅します （places.py の _ring_centers）。

出力は config/compset.generated.json。この時点では本番投入しません。

② 施設属性の人手確定（四半期に1回）

config/compset_overrides.json に、APIからは取得できない項目を確定して書きます。

項目 なぜ人手か
rooms Places API は客室数を返さない
pricing_basis 人数課金か室課金かは掲出画面を見ないと分からない
meal_included 素泊まり／朝食付き／2食付きの別
dinner_uplift / breakfast_uplift 素泊まり掲出の宿を2食付き基準へ揃える補正額

confirmed: true を立てるまで、survey レポートは 「要人手確認」セクションに当該施設を出し続けます。

upliftの決め方：①競合施設のレストラン公開価格、②近隣同格店の客単価、 ③自社の食事原価と提供価値からの逆算 — の3点を突き合わせます。 四半期に1度、実際のOTA画面と突合して検証してください。

確定後、レビューを経て昇格：

python3 scripts/discover_compset.py --source places --write   # compset.json へ昇格

③ 競合レートの収集（日次）

# まず計画とコストを確認（ネットワークに出ない）
python3 scripts/collect_rates.py --plan-only

# 実行
python3 scripts/collect_rates.py --source serpapi

日次バッチ（03:30 JST 想定）で Cloud Run Jobs から起動します。

④ ADR判断（日次）

python3 scripts/survey_report.py --explain 2026-11-21

⑤ ADRマトリクス（施設 × 日付の一覧）

python3 scripts/adr_matrix.py --from 2026-11-14 --to 2026-11-30
python3 scripts/adr_matrix.py --from 2026-11 --open   # 11月まるごと、ブラウザで開く

survey レポートは日ごとの「判断」を出しますが、値付けの現場で実際に見たいのは 「この日、競合各社がいくらで出しているか」を横並びにした表です。 価格が1社だけ突出しているのか、市場全体が上がっているのかは、 中央値だけを見ていても分かりません。

出力は3系統。

出力 用途
端末 千円単位の一覧。その場で確認する
out/adr_matrix.csv Excel等での再加工
out/adr_matrix.md GitHub上でそのまま表示される。社内共有向け
out/adr_matrix.html ヒートマップ＋日程の切替UI。ブラウザで開く

HTML版は調べたい日程を画面上で変えられます。 収集済みの全期間をページ内に 埋め込んであるため、日付を変えるたびに Python を再実行する必要がありません。 現場で「11月を見て、次は年末を見て」という確認をするのは HTML版が最も速い一方、 --from/--to は日次バッチや特定期間の収集で使う、という住み分けになります。

表の作りには意図があります。

  • 行の並びは類似度スコア降順（似ている競合が上）。半径5kmに広げても、 価格帯・規模が近い宿が上位に来るので、上から数行を見れば足ります
  • 自社を最上段に固定し、直下に市場中央値を置く。縦方向に読むだけで 「自社が市場のどこにいるか」が分かります
  • 売止（満）とデータなし（·）を別記号にする。同じ記号にすると 「競合が高くて売れている」のか「単に取得できていない」のか区別できません
  • 濃淡は単一色相の明度のみで表現。色相を混ぜると大小関係が読めなくなります
                       11/14 11/15 11/16 ...      平均    類似度
                         SAT   SUN   MON
奈良春日 鹿のや                 132   118   118          122
└ エンジン推奨                 152   131   136          134
------------------------------------------------------------
市場中央値（NAR）               129   100    91          101
------------------------------------------------------------
月日亭                      141   105    91          106   1.00
ふふ奈良                     197   164   136          159   0.94
江戸三                      143   104    98          108   0.92

期間を指定して収集してから実行してください。 階層化収集のままだと 遠い日付は毎回は取得されないため、マトリクスに ·（データなし）が並びます。

python3 scripts/collect_rates.py --from 2026-11-14 --to 2026-11-30   # 全日取得
python3 scripts/adr_matrix.py    --from 2026-11-14 --to 2026-11-30

4. コスト管理

4.1 3つの水準

--plan-only は削減効果を3段階で表示します（効果を過大に見せないため）。

水準 月間リクエスト 月額（$0.015/req）
①施設別 × 毎日（最も素朴） 43,200 $648
②エリア一括検索 3,600 $54
③②＋階層化スケジュール（本設計） 約1,400 約$21

削減の大半は「エリア一括検索」から来ています（1リクエストで複数施設が返る）。 階層化はそこからさらに2〜3倍を削る、という理解が正確です。

4.2 階層化スケジュールの仕組み

リードタイム 頻度 理由
D+0〜14 毎日 価格変動が最も激しい
D+15〜45 3日ごと 変動は中程度
D+46〜120 7日ごと ほぼ静的

各宿泊日には安定したスロット番号（stay_date.toordinal() % N）が割り当てられ、 run_date.toordinal() % N == slot の日に取得されます。これにより ①各宿泊日はきっかりN日ごとに更新され、②負荷が日々に均等分散されます。

週末・イベント日は1段階上の階層へ引き上げますが、 リードタイム上限（週末60日／イベント45日）を設けています。 遠い日付は繁忙日でも日々は動かないため、無制限に引き上げると 費用だけが増えてカバレッジは改善しません。

4.3 上限の強制

sources.json > budget.monthly_search_cap を超える計画は、 collect_rates.py が実行前に停止します。設定ミスによる想定外課金を防ぐためです。

5. 生データの扱い

すべての生レスポンスは data/raw/{source}/{取得日}/{hash}.json へ不変保存されます。

  • 再実行してもキャッシュヒットとなり、二重課金は発生しません
  • APIキーはキャッシュに書き込まれません（キー生成時・保存時の両方で除外）
  • 正規化は必ず下流で行い、生データには手を入れません （正規化ロジックは改善され続けるため、生値があれば遡って再計算できます）

6. 障害時の挙動

事象 挙動 対処
APIキー未設定 起動時に明示エラー＋設定方法を表示 環境変数を設定、または --source fixture
HTTP 4xx（429以外） リトライせず即座に失敗 リクエスト内容の誤り。設定を確認
HTTP 429 / 5xx / タイムアウト 指数バックオフで4回まで再試行 継続失敗ならベンダー障害を確認
月次上限超過の計画 実行前に停止 collection.tiers の頻度を下げる
名寄せ不能な施設 破棄せず unmatched として報告 新規開業なら ① を再実行
収集が数日止まった survey が「最大経過日数」を表示 10日超が増えたら収集を復旧

設計方針：壊れたデータで価格を配信するより、止まるほうが安全。 data_quality_check を配信ジョブの前段に置き、鮮度劣化時は自動配信を停止します （システムアーキテクチャ §4）。

7. 判断ロジック — 3シグナルの合議

survey レポートは、価格・在庫・予約ペースの3シグナルのうち 2つ以上が揃った日にだけ強い判断（値上げ／値下げ）を出します。

シグナル 値上げ側 値下げ側
価格 競合NAR中央値比が目標倍率未満 目標倍率の1.15倍以上（割高）
在庫 競合売止率 40%以上 競合売止率 15%以下
ペース 予約ペースが前倒し 予約ペースが遅れ

単一シグナルでは動かしません。 5室規模では1件の予約でペースが反転し、 1施設の売止で市場逼迫度が跳ねるため、単一シグナルは簡単に裏切られます。

有効サンプルが3件未満の日は「判断不可」とし、推測で埋めません。

7.1 市場判定とエンジン推奨が食い違う日

「市場比では割高だが、需要イベントと予約ペースは値上げを支持する」という日が生じます。 survey はこれを★要確認として別建てで表示し、自動配信の対象外とします。

矛盾を平均して丸めてしまうと、判断の根拠が消えます。 食い違いそのものが、人が見るべき情報です。

8. オフライン実行（APIキー不要）

cd engine
./scripts/run_pipeline.sh          # 発見→収集→判断→テスト を一気通貫

フィクスチャは実APIと同じ形のJSONであり、実コネクタと同じパーサを通ります。 「オフラインでは動くが本番のレスポンス形では壊れる」という事故を防ぐためです。

施設名・所在は公開情報に基づく実在の施設ですが、価格は完全な擬似値です。 survey レポートはフィクスチャ由来のデータに対して必ず警告バナーを表示します。
