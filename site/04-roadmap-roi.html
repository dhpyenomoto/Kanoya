2. Phase 0：診断（0〜4週）

2.1 成果物

# 成果物 内容
1 実績データ棚卸し報告 過去2〜3年の予約明細・キャンセル・チャネル別実績・リードタイム分布
2 Baseline KPI ADR／OCC／RevPAR／Net RevPAR／直販比率の現状値（月別・日カテゴリ別）
3 貢献利益フロアの算定 1室2名2食あたりの変動費（食材・リネン・アメニティ・変動人件費・OTA手数料）から下限価格を確定
4 シーズンカレンダー 12〜16区分のシーズン定義（実績と市場から策定）
5 コンペセット定義書 PRIMARY／SECONDARY／ASPIRATIONAL と重み、各社の正規化パラメータ（食事uplift・課金方式）
6 チャネル契約条件の整理 各OTAの手数料率・ポイント原資・パリティ条項・販促プログラムの実質コスト
7 OTBスナップショット蓄積の開始 ★最優先。初日から毎日蓄積を始める

2.2 Phase 0 の落とし穴

「データがないので分析できない」で止まらないこと。 この規模の施設ではデータが整備されていないのが常態です。重要なのは、

  1. 今日からOTBスナップショットの蓄積を始める（過去に遡って復元できない唯一のデータ）
  2. 過去データは「あるものだけ」で Baseline を作り、精度は後から上げる
  3. 貢献利益フロアの算定だけは、データの有無にかかわらず必ず今やる（これがないと安全に自動化できない）

の3点です。完璧なデータ整備を待つと、Phase 0 が半年になります。

2.3 コンペセットの食事uplift をどう決めるか

競合が素泊まりで売っている場合、「その施設に泊まる客が夕食にいくら使うか」を推定する必要があります。実務的には、

  • 競合施設のレストラン公開価格（コース単価）
  • 近隣の同格レストランの客単価
  • 自社の食事原価と提供価値からの逆算

を突き合わせて、四半期に1度見直します。この値が誤っていると競合ポジション判断が体系的に歪むため、Phase 0 で現地確認を含めて丁寧に置いてください。

3. Phase 1：MVP／シャドーモード（5〜12週）

3.1 やること

  • データ基盤構築（GCS／BigQuery／Cloud Run Jobs／Scheduler）
  • Google Hotels API 経由の競合レート収集開始（まずは単一ソースで開始）
  • PMS連携（OTB日次スナップショット）
  • 価格エンジンの実装・設定投入・基準価格の初回校正
  • 推奨価格の算出のみ（配信しない）／ CSV・ダッシュボード出力
  • シャドーモード検証：毎日、推奨価格と実際に人が付けた価格を並べて記録

3.2 シャドーモードを省略してはいけない理由

いきなり自動配信を始めると、モデルの欠陥が売上毀損として顕在化してからしか分かりません。5室では1件の判断ミスが月次業績に見える規模で効きます。

シャドーモードでは、 - 推奨と人の判断が乖離した日を毎週レビューし、どちらが正しかったかを検証する - 乖離の原因が「モデルに欠けている変数」なら、モデルを直す - 「人が見落としている要因」なら、人の運用を直す

これを8週間続けると、モデルの信頼度と現場の納得の両方が積み上がります。現場が納得していない自動化は必ず形骸化します（手動オーバーライドだらけになり、結局属人運用に戻る）。技術的な理由以上に、組織的な理由でこの期間が必要です。

3.3 Gate 条件

条件 基準
推奨と人の判断の一致率（±10%以内） 70%超
データ収集成功率 PRIMARY施設 90%超
乖離事例のレビュー完了 全件
回帰テスト 全件パス

4. Phase 2：半自動運用（13〜24週）

4.1 やること

  • サイトコントローラーAPI連携（ドライラン → 一部日付 → 全期間の3段階で開始）
  • 自動適用帯（±12%）内の推奨を自動配信
  • 承認キュー運用開始（Slack通知 → 支配人が理由コード付きで承認／却下）
  • MLOS・gap night 最適化の有効化
  • Revenue Playbook の確定（判断基準の全文書化）
  • 意思決定ログの運用開始
  • 週次 Revenue Meeting の定例化（資料は自動生成）

4.2 段階的な配信開始

いきなり365日分を自動配信しないでください。

段階 対象 期間
① ドライラン 配信せず差分だけ出力 1週
② 近日のみ D+0〜30 のみ自動配信 2週
③ 中期まで D+0〜90 2週
④ 全期間 D+0〜365 以降

各段階で事故ゼロを確認してから次へ進みます。

5. Phase 3：高度化（25〜40週）

  • 需要予測モデルの精緻化（1年分の自社OTBデータが蓄積された段階で着手）
  • 天候・検索トレンド等の先行指標の組み込み
  • アップセル最適化（客室アップグレード・飲料ペアリング・レイトチェックアウト・送迎）→ TRevPARへ主KPIを拡張
  • 直販シフト施策（会員制度・自社限定パッケージ・CRM）
  • 商用レートショッパーの追加導入判断
  • 多施設展開への対応（設定ファイルの分離は初期設計で済んでいる）

5.1 需要予測を Phase 3 まで待つ理由

需要予測モデルは魅力的ですが、学習データがなければ機能しません。年間1,825室というサンプルサイズでは、1年分でようやく日カテゴリごとに数十サンプルです。

Phase 1〜2 は「ルールベース＋競合連動」で十分な効果が出ます（RM導入効果の大半は、価格解像度を上げること自体から得られます）。予測モデルはその上積みであり、順序を間違えるとデータ不足のモデルに振り回されて信頼を失います。

7. 運用体制

7.1 RACI

業務 オーナー 支配人 外部アドバイザー システム
日次の推奨確認・承認 I R/A — R（自動配信）
週次 Revenue Meeting A R C R（資料自動生成）
月次プランミックス見直し A R C I
四半期 基準価格校正 A C R R（校正レポート）
四半期 コンペセット再定義 A C R R（候補提示）
年次 予算・貢献利益フロア R/A C C I
ガードレール設定変更 A C C —

R=実行 / A=承認 / C=相談 / I=報告

日次業務の負荷が支配人の「15分」に収まっていることが設計の要件です。ここが30分を超えるようなら、自動適用帯を広げるかモデルを改善します。運用負荷は監視すべきKPIの一つです。

7.2 週次 Revenue Meeting のアジェンダ（60分・資料は自動生成）

時間 内容
10分 先週の実績（ADR／OCC／RevPAR／Net RevPAR／チャネルミックス）
10分 ピックアップとブッキングペース（次90日の対ベンチマーク進捗）
10分 競合動向（NAR中央値の推移、自社ポジション、売止状況）
15分 要判断事項（承認キューの積み残し、MLOS設定日、gap night、閑散日の対策）
10分 先週のオーバーライドのレビュー（正しかったか）
5分 アクション確認

「オーバーライドのレビュー」を毎週やることが、属人的な勘を組織知に変える具体的な仕掛けです。 誰かの判断が良かったならモデルに取り込み、悪かったなら次回から控える。この往復を回し続ける限り、担当者が変わっても知見は失われません。

8. 成功の定義

Phase 3 完了時点で、以下がすべて満たされていれば成功です。

# 条件 意味
1 RevPAR 前年比 +7%超 収益効果が出ている
2 日次運用時間 15分以下 運用が回っている
3 推奨採用率 85%超 モデルが信頼されている
4 直販比率 35%超 手取りが改善している
5 支配人が3日不在でも価格運用が止まらない 属人性が解消されている
6 新任者が Playbook を読んで1週間で運用に入れる 知見が組織に残っている

5番が本件の本質的なゴールです。RevPARの改善は結果であり、「特定の個人がいなくても、質の高い値付けが毎日継続される状態」を作ることが、自社運営でレベニューマネジメントを内製化する本当の目的です。
